一句话理解

LLM 是检索策略控制器，Semantic Scholar 是论文搜索引擎。LLM 产生工具调用、阅读摘要并打相关性分数；Semantic Scholar 返回真实论文及其相似论文、参考文献关系。

AI Researcher 不是一个自主 Agent

整个系统是一个由 Python 预先规定步骤的 LLM Pipeline；LLM 不会自主规划完整研究任务，也不决定模块顺序。

整体系统

预定义工作流

文献检索 → Idea 生成 → 去重 → Proposal → 排名与过滤。执行顺序和停止条件都写在代码中。

Literature 模块

受限的 Agentic Loop

查询阶段的 LLM 根据主题、当前高分论文和历史查询选择一个检索动作；Python 执行动作、保存论文库并判断是否继续。

准确定位：AI Researcher = 模块化 LLM Pipeline；Literature 模块 = LLM 控制动作选择的受限检索循环，而不是完整的 ReAct Agent。

Literature 模块的一轮，究竟发生了什么？

① LLM 读取

本轮 Prompt 上下文

研究主题；Idea 模式下还包括完整 Idea；当前 Paper Bank 中得分最高的 Top-K 论文及其摘要；此前执行过的查询；三个工具的使用说明。

② LLM 选择

只返回一个动作

KeywordQuery("关键词")、PaperQuery("paperId") 或 GetReferences("paperId")。它不直接访问网络，也不执行工具。

③ Python 执行

检索、过滤、评分、更新

Python 解析动作并调用 Semantic Scholar，过滤缺少摘要及部分综述论文；随后另一次 LLM 调用给新论文打 1–10 分，再更新 paper_bank 和 all_queries。

④ Python 决定

继续还是结束

若论文数仍小于 max_paper_bank_size 且扩展次数未达到 10，Python 重新构造下一轮 Prompt；否则排序、去重并保存结果。

主题 / Idea + Top-K 论文 + 历史查询 → LLM 选择动作 → Semantic Scholar → LLM 评分 → 更新 Paper Bank → 判断是否继续

没有隐藏的对话记忆：LLM 每次调用基本无状态。所谓“记忆”是 Python 保存的 paper_bank、all_queries、iter 和 total_cost，下一轮只把其中需要的部分重新写进 Prompt。初始查询是例外：主题模式直接使用主题文本，Idea 模式才先让 LLM 提炼关键词。

它在整个 AI Researcher 中的位置

文献模块是整条 Idea 生成流水线的第一站：先建立一个相关论文库，再用它为 Idea 生成提供背景，并在最后检查 Idea 是否与已有论文重复。

生成之前

提供研究背景

grounded_idea_gen.py 从高分论文中抽取若干篇，放进提示词，作为 Idea 生成时的背景知识。

生成之后

检查新颖性

novelty_check.py 针对具体 Proposal 再搜相似论文，让 LLM 逐篇判断是否已经存在相同问题与方案。

文献 Agent 的核心机制

代码并没有使用复杂的 Agent 框架。它用普通 Python 循环，把 LLM 输出解析成三个固定函数之一，然后执行，再把检索结果反馈给 LLM。

决策层

LLM Agent

  • 根据主题提出初始关键词
  • 阅读当前高分论文和历史查询
  • 选择下一种检索动作
  • 根据标题和摘要打 1–10 分
⇄查询向右
论文向左
执行层

Semantic Scholar

  • Graph API：关键词、论文详情、参考文献
  • Recommendations API：相似论文
  • 返回标题、年份、摘要、引用量、paperId
  • 每次关键词/相似检索最多取 20 篇

1 · 初始检索

主题模式直接把主题变成一次 KeywordQuery；Idea 模式则先让 LLM 提炼关键词。

2 · 清洗与入库

去掉没有有效摘要的论文，并通过标题规则排除 survey、review、position paper。

3 · LLM 重排

LLM 按主题相关性、是否有实证方法、是否有启发性打 1–10 分，形成当前 Paper Bank。

4 · 选择下一跳

取当前 Top-K 论文作为上下文，让 LLM 避开历史查询，并选择关键词、相似论文或参考文献查询。

5 · 停止并输出

论文库达到 max_paper_bank_size，或循环达到 10 次后停止；最后按分数排序、去重并保存 JSON。

Agent 可以选择的三种检索动作

广度入口

KeywordQuery

按关键词搜索论文，适合从研究主题开始建立候选集合。

KeywordQuery("language model hallucination prompting")
相似扩展

PaperQuery

把一篇高分论文作为种子，通过推荐接口寻找语义或主题相近论文。

PaperQuery("paperId")
引用追踪

GetReferences

沿一篇论文的参考文献向前追踪，补充经典方法或直接相关工作。

GetReferences("paperId")

为什么要混合三种动作？关键词搜索容易受措辞限制；相似论文能在同一主题附近扩展；参考文献追踪能找到关键词未命中的前序工作。LLM 的作用就是根据当前论文库动态决定下一跳。

一次具体检索会怎样进行

假设输入主题是：“减少大语言模型幻觉的新型 prompting 方法”。以下是符合代码机制的简化示意，不代表仓库中保存的真实运行日志。

轮次 Agent 看到什么 选择的动作 结果如何使用
初始轮 只有研究主题 KeywordQuery("novel prompting methods ... hallucination") Semantic Scholar 返回第一批候选论文
扩展轮次 A Top-K 高分论文及摘要 PaperQuery("高分论文的 paperId") 扩展与关键论文相似的工作
扩展轮次 B 论文库 + 已执行查询 GetReferences("另一篇高分论文的 paperId") 追回该方法引用的前序论文
结束 达到数量上限或 10 轮 排序 + 去重 保存 all_queries、paper_bank、total_cost

扩展动作并非固定顺序：代码执行 1 次初始查询，随后最多进行 10 次动态扩展；达到论文数量上限时会提前停止。

Paper Bank 的角色：它既是检索过程的“短期记忆”，也是后续 RAG Idea Generation 的输入。每篇论文主要包含 paperId、标题、摘要、年份、引用量和 LLM 相关性分数。

它能做什么，不能做什么

它擅长

  • 围绕主题快速建立相关论文候选池
  • 根据当前结果迭代改变检索路径
  • 用 LLM 对摘要进行相关性重排
  • 为 Idea 生成和新颖性检查提供论文背景

它不负责

  • 下载、解析或理解论文全文
  • 生成系统性的 Literature Review 章节
  • 保证检索穷尽或学术数据库完整覆盖
  • 替代人工核实引用和新颖性判断

最容易误解的地方：这不是一个会自由调用任意工具的通用 Agent。它实际上是“LLM + 三个白名单函数 + Python 循环”。另外，LLM 看到的是标题和摘要，不是全文，因此相关性与新颖性判断都只是候选筛选。

最小代码地图

理解文献模块只需要顺着下面几处代码阅读。

src/lit_review.py

主循环：初始查询、生成下一查询、LLM 打分、停止、排序和缓存。

src/lit_review_tools.py

Semantic Scholar 接口与工具调用解析器，包括三种核心检索动作。

scripts/lit_review.sh

最简单的运行入口，设置主题、模型、论文库上限和输出文件。

src/grounded_idea_gen.py

读取 Paper Bank，并把抽样后的高分论文放进 Idea 生成提示词。

src/novelty_check.py

针对生成的 Proposal 再检索相关论文并进行逐篇新颖性比较。

scripts/end_to_end.sh

展示 Literature → Idea → 去重 → Proposal 的整体执行顺序。
