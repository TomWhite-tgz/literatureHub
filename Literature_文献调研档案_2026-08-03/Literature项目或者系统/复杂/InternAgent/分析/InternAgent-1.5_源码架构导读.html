§一句话心智模型

InternAgent = 一台"科研流水线机器人":它不是一个 agent,而是"两层编排"套两套循环——

① 外壳:Discovery 流水线(非 MAS)

launch_discovery.py → stage.py。负责把任务跑很多轮(loop_rounds):每轮 = 想法生成 → 跑实验 → 攒经验 → 演化提示词。它管文件夹、GPU、并行、记忆——但自己不思考,思考外包给内核。

② 内核:多 agent 系统(MAS)

internagent/mas/。一台状态机(OrchestrationAgent)把 11 个专职 agent串成"假设→反思→进化→排序→方法→精修"的认知流水线,产出 top ideas。每个 agent 本质是"一段 prompt + 一次 LLM 调用 + 结构化输出"。

所以读 InternAgent 有两个完全不同的"循环"别搞混:

  • 认知循环(内核):在 MAS 状态机里,反复生成/批判/进化想法,产出"该做什么实验"。语言模型 = OpenAI 兼容端点(默认 gpt-4o)。
  • 实证循环(外壳):拿到想法后,真的写代码、真的跑 bash launcher.sh、真的看报错再调试。这一步默认用 claudecode 后端——直接 shell 调本机 claude CLI(不是 SDK)。
★ 一句话抓住它InternAgent 把"科学家做研究"拆成 想点子(MAS 多 agent 辩论) 和 做实验(Claude Code 写码+自动调试) 两台机器,中间用 记忆系统把"哪些方向失败过、哪些成功了"沉淀下来,反过来改写下一轮的出题 prompt——这就是"自演化(self-evolving)"。

§在科研 agent 谱系里的位置

本系列已经讲过两种"科研 agent 怎么搭"的路线。InternAgent 是第三种:

项目底座选择解耦哲学"做实验"怎么落地
EvoScientist建在 deepagents / LangChain 上一切皆中间件 + YAML 子 agent子 agent 写代码,靠 langgraph 异步底座
AgentScope自造内核(强单体 ReAct)组件注入 + hook由用户在内核上自写
InternAgent 👈完全自造(MAS + 流水线,零 LangChain)状态机 + 工厂注册表:agent / model / tool / 后端各有注册点外包给独立后端:shell 调 claude CLI / iflow / openhands,带自动调试循环

关键区别:InternAgent 把"想点子"和"做实验"彻底物理分离——前者是纯 LLM 推理(OpenAI 兼容),后者是一个可替换的"实验后端"(默认让 Claude Code 这种成熟编码 agent 去干脏活)。这让它能同时是"多 agent 科研编排框架"和"benchmark 跑分平台"(MLE-Bench 第一名的 MLEvolve 就是它的实验优化子系统)。

⑤ 演化④ 编排②③① 单 agent④.5 实验(外包)
★ 错位一:②③ 这两层被"压扁"了实测 11 个 agent 里只有 generation 用 ReAct 工具循环(_call_model_with_tools),其余 10 个都是「一步 execute + 结构化 JSON 输出」(_call_model,在 execute() 里调 1–7 次)。也就是说:InternAgent 故意把"单个 agent"做成一次性专员,把多步思考上移到 ④ 编排层(串一堆浅 agent),而不是下沉到一个 agent 的深 loop。对照 AgentScope 正相反——它把重量全压在 ②③(单 agent 深 ReAct loop),④⑤ 几乎没有。同样 6 层,重量分布相反。
★ 错位二:最深的 agent_loop 不是它自己跑的真正最深、最像"自治 agent loop"的是 ④.5 实验/AutoDebug 那一圈——但它不是 InternAgent 的 agent 在跑,而是 subprocess shell 调本机 claude CLI,外包给 Claude Code 这个外部 agent(experiments_utils_claude.py:121)。一句话:它自己的 agent_loop(③)是浅的,它最深的 agent_loop(④.5)外包给了别人。
这 6 层只画了"纵向深度",还漏 3 个维度这个套娃模型刻画的是嵌套深度,但 InternAgent 还有几条它没覆盖的重要结构,用时心里要有数:
• 横向并行(fan-out):④ 编排用 asyncio.Semaphore+gather 并发处理多个 idea(reflection/evolution/scholar 各阶段);④.5 用 ThreadPoolExecutor+GPU 信号量并行跑多个实验。深度模型只有"竖切",没画这层"横切"。
• ④.5 的 MCTS 形态本身是一层"搜索":use_mcts=true 时实验循环从线性 AutoDebug 变成蒙特卡洛树搜索(mcts_experiments_utils_*.py),这正是综述说的 search-based。
• 嵌套子编排(② 里能套一个 ④):DRAgent(背景调研 / QA)一启动,就会再展开一整套 planner→并行执行→synthesizer 的图工作流(FlowSearch,dr_agents/workflow/main.py),即"一个 agent 的 execute 里嵌着另一套完整编排"。
• 记忆是横切侧信道:在 ④ 被读(过滤失败方向 / 注入指导语)、在 ⑤ 被写——它不是纵向的一层,而是让 ⑤ 成立的旁路。

2 ·Discovery 主循环(外壳怎么转)

launch_discovery.py:main()(~567 行起)的核心是一个 for round_num in range(start_round, loop_rounds+1) 大循环(launch_discovery.py:798)。每一轮三步:

步骤做什么源码
① 想法生成IdeaGenerator.generate_ideas() 跑 MAS 状态机,产出 top_ideas 与 ideas.json;并把想法灌进 IdeaGraph 长程记忆stage.py:283
② 跑实验 / 出报告--mode experiment:ExperimentRunner.run_experiments() 为每个 idea 建工作区、按后端 dispatch、并行(ThreadPoolExecutor)+ GPU 分配。--mode report:ReportWriter 出 markdownstage.py:1154
③ 攒经验每轮结束 _generate_experiences_for_round():把本轮 idea↔实验配对做对比学习,写进 experience_library.json,供下一轮 PromptEvolver 改写出题 promptlaunch_discovery.py:968

两种轮间模式(loop_mode)

fresh

每轮都从原始 baseline 代码出发。各轮独立,适合"广撒网"探索不同方向。

incremental(默认)

每轮从上一轮最好的结果继续(_find_best_experiment_result → best_code_path),逐轮"爬坡"优化。launch_discovery.py:800

★ "自演化"的闭环在这实验结果 → 经验库 → 演化提示词 → 下一轮出题。第 1 轮没有经验、不演化;从第 2 轮起,PromptEvolver 用累积经验原地重写 prompt.json 的 task_description,并用 IdeaGraph 把候选 prompt 往"还没探索过的方向"推(详见 §6)。这是 InternAgent 区别于"一次性跑完"的 agent 的核心。

3 ·MAS 状态机 ★(内核怎么想)

"想法生成"这一步,内部是 OrchestrationAgent(orchestration_agent.py,~1151 行)跑的一台状态机。WorkflowState 枚举 11 个状态(data_type.py:15),_execute_current_phase() 用 phase_handlers 字典把状态路由到 _run_*_phase(orchestration_agent.py:433)。

COMPLETED,产出"可实现的方法细节"。
Idea Innovation评估/检索/方法等待反馈判定

关键机制

  • 两阶段(method_phase 标志):进入 METHOD_DEVELOPMENT 时 method_phase=True(orchestration_agent.py:407),此后 EXTERNAL_DATA 走 scholar(给方法找证据)、终点改去 REFINING→COMPLETED。一套状态、两遍走法:先把"想法"磨好,再把"方法"磨好。
  • 人在环上(human-in-the-loop):每轮 RANKING 后会落到 AWAITING_FEEDBACK 并暂停(run_session 的 while 循环 break,orchestration_agent.py:195)。自治模式下,外壳的 IdeaGenerator 读 --offline_feedback JSON 文件自动喂反馈再 resume(stage.py:298-303),于是循环继续到 COMPLETED。
  • 并发处理想法:reflection / evolution / scholar / method_development 等阶段对多个 idea 用 asyncio + Semaphore 并发执行(如 _run_external_data_phase 的 execute_with_semaphore)。

4 ·11 个专职 agent(+2 个旁路)

注册表是 AgentFactory._agent_registry —— 一个静态 dict(agent_factory.py:41-53),不是装饰器。create_all_agents() 只实例化"既在注册表、又在 config.agents 里"的 agent。每个 agent 继承 BaseAgent、实现 async execute(context, params)。

5 ·BaseAgent & 模型层

BaseAgent(base_agent.py,~584 行)给所有 agent 提供两条"调模型"的标准通道:

_call_model() · base_agent.py:259

单轮调用。给 schema 就走 generate_json(强制结构化 JSON 输出),不给就走 generate(纯文本)。内置指数退避重试(max_retries 默认 10,失败抛 AgentExecutionError)。绝大多数 agent 用这条。

_call_model_with_tools() · base_agent.py:331

多轮 ReAct/工具循环:模型发 tool_calls → _execute_tool 执行 → 结果塞回 messages → 再问,直到不再调工具或触顶(max_iterations=10、max_tool_calls=20)。子类重写 _execute_tool 把调用转给 ToolRegistry。

模型层:全是"OpenAI 兼容"

ModelFactory.MODEL_PROVIDER_MAP 当前列出 4 个 provider；其中 OpenAI 与 OpenRouter 走 OpenAI 兼容接口，另有 InternS1 和 DeepSeek-R1 专用实现：

openai → OpenAIModel(AsyncOpenAI,默认 gpt-4o;generate/generate_json/generate_with_messages/embed) openrouter → OpenRouterModel(使用 OPENROUTER_API_KEY 与 OpenAI 兼容端点；配置见 config/openrouter_config.yaml) interns1 → S1Model(书生 InternS1) dsr1 → R1Model(DeepSeek-R1)

b8a9e81 更新OpenRouter 已成为主 discovery 流水线的一等 provider；但 launch_qa.py 的 Deep Research 客户端不会自动读取这个 provider，需要把 OpenAI 兼容环境变量指向 OpenRouter。详见 docs/openrouter.md。
两套"模型"别混!(a) MAS 推理用的 LLM = OpenAI 兼容 client(OPENAI_API_BASE_URL,默认 gpt-4o / QA 用 o4-mini)。(b) 实验后端 claudecode = 直接 shell 调本机 claude CLI(experiments_utils_claude.py,需装好 Claude Code 且 ANTHROPIC_API_KEY),不是用 Anthropic SDK。换端点时还要注意 sci_task.scorer_model(gpt-5.1)、QA(o4-mini)、实验(claude-sonnet-4-5-20250929)这些写死的型号名你的 base_url 是否支持。

6 ·记忆系统 ★★(自演化的发动机)

这是 InternAgent 1.5 的招牌,也是最容易讲错的地方。"记忆"不是一个统一的库,而是四套基本独立的子系统,各有自己的后端、配置开关、读写时机。并没有一个 god-object 总管它们——抽象的 MemoryManager 只负责其中一层(会话持久化);真正把四层串起来的是 stage.py / launch_discovery.py 的流水线。

D 层:prompt 到底"怎么演化"

这是"self-evolving"四个字的字面机制。PromptEvolver.evolve_prompt()(long_memory.py:560)做四件事:

  1. 读经验库 + 当前 prompt.json 的 task_description/background;
  2. 并行生成 N 个候选 prompt(num_candidates=3),每个由 prompt_evolver agent 用经验重写出 new_task;
  3. 对每个候选算探索分:去 IdeaGraph 查与它相关的已有想法数 + 最大簇大小,score = 0.6·(相关数/图规模) + 0.4·(最大簇/图规模)(long_memory.py:534)——分越低 = 越新颖;
  4. 选最低分(最探索)的候选,原地覆盖 prompt.json 的 task_description(先备份 prompt_backup_round{N}.json)。

B 层:怎么"避开失败方向"

任务记忆把每条实验记成 label ∈ {+1, 0, −1}。正记录→生成"靠拢这个方向"的指导语;负记录→在 generation/evolution 里主动过滤:任何与已知失败相似度 ≥ 0.7 的新想法被标记并重新生成(最多 max_regeneration_attempts=2 次,generation_agent.py:131,189)。判定 label 用主指标(ExpAnalyzeAgent),没 LLM 时退化为各指标平均。

两套嵌入、两套钥匙B/C/E 用本地 sentence-transformers(需下模型,model_name 空则静默跳过检索);而 D 层的 IdeaGraph 用 ChromaDB 写死 OpenAI text-embedding-3-small(读 OPENAI_API_KEY/OPENAI_API_BASE_URL)。两者相互独立。另:首轮无收益(库是空的)、离线导入是手动步骤、只有 run_0 baseline、没有改进 run 的实验会被丢弃不入库。

7 ·工具 & MCP(两个并存的"工具世界")

这里有个最容易踩的坑:代码里有两套并存、互不相通的工具机制。

世界① ToolRegistry(给 LLM 调的函数工具 + MCP)

tool_config.py 的全局单例。init_tools() 只注册了 5 个函数工具(__init__.py:26):calculate、query2smiles(PubChem)、patent_check(SureChEMBL)、modify_mol(RDKit)、academic_search。它们经 BaseAgent._call_model_with_tools 暴露给模型。

世界② agent 直接 import 的工具类(不走注册表)

LiteratureSearch、WebSearch、code_search、TaskMemoryRetriever 这些是 agent 内部当普通 Python 对象直接调的——例如 survey_agent 调 search_serper、scholar_agent 调 multi_source_search。它们不作为函数工具暴露给 LLM。

调用流(世界①)

LLM 发 tool_call → BaseAgent 解析参数 → agent 的 _execute_tool → registry.execute() → 路由到本地函数或 MCP(tool_config.py:114-136)→ 结果 JSON 化塞回对话。注册表是唯一路由点,agent 不需知道工具是本地的还是 MCP 的。

MCP 集成

  • FastMCP 2.0 是当前实现(mcp_manager_fastmcp.py);旧的 raw-SDK mcp_manager.py 被注释禁用(__init__.py:9-10)。
  • 远程 server 在 config.sci_tools.remote 配 {id, url, headers},协议看 URL 后缀(/sse→SSE,/mcp→Streamable HTTP);本地 server 走目录自动发现(tools/mcp/ 下匹配 *_server.py)。
  • 所有 MCP 工具名加 mcp_ 前缀入注册表,执行时再剥掉。
开箱即用其实"零工具"default_config.yaml 里 sci_tools.local: false 且 remote 全注释掉——所以默认既没有函数工具、也没有 MCP 工具,要自己开。注意 local 在代码里默认 True、在配置文件里却是 false,容易对不上。calculate 用的是 eval()(虽剥了 builtins),安全场景需留意。

8 ·实验后端:AutoDebug 循环 ★

想法变成"可实现的方法细节"后,真正的"做实验"在 ExperimentRunner 里按 --exp_backend 分派(stage.py:1068-1075):claudecodeiflowopenhands(各有 use_mcts=true 的 MCTS 变体)。默认 claudecode 的核心 = perform_experiments() 的迭代循环(experiments_utils_claude.py:307):

ClaudeCodeRunner.run() 就是一句 subprocess.run(['claude','--permission-mode','acceptEdits','--model',model, prompt], cwd=...)(experiments_utils_claude.py:121)。成功(return_code==0)→进入下一个"改进 run";失败→把 traceback 拼成下一个 prompt 喂回 claude 去 debug(NEXT_EXPERIMENT_PROMPT)。这正是官方图里 "AutoExecute → Error Traceback → AutoDebug" 那条回路。

论文复现(sci_task)模式同一套循环,初始 prompt 换成 CODER_PROMPT_SCI_TASK 并写 INSTRUCTIONS.md;跑完用 sci_task.scorer_model(gpt-5.1,LLM-as-judge)按 checklist.json 给报告打分。任务来自 ResearchClawBench；当前 sci_tasks/ 已按主仓库锁定的 9b5288e 检出。

9 ·Deep Research / FlowSearch(QA 模式)

mas/agents/dr_agents/ 是内嵌的一整套深度调研系统 = FlowSearch(Hu et al., arXiv:2510.08521,基于 CAMEL,405 个 .py)。两个用途:① discovery 里给想法做背景调研;② QA 模式一次性回答研究问题(launch_qa.py → DRAgent(model='o4-mini', mode='qa'))。DRAgent 懒加载 dr_agents/workflow/main.py 的 Workflow,按 mode 选 config_{qa,simple,complex}.yaml。

"动态结构化知识流"是什么

Workflow.execute()(workflow/main.py:131)的核心是把问题建成一张子任务图,而不是线性流水线:

  • GlobalPlanner 把问题拆成子任务图(节点类型 solve/answer,有且仅一个 answer 节点;max_nodes=7),逐层展开。
  • GlobalExecution 按拓扑序找 get_ready_nodes():同层节点并行检索(ThreadPoolExecutor(max_workers=10)),每个节点内部还各自跑一个子 workflow——两级并行。
  • 知识"流":已执行节点把答案写回图,下游节点经 _get_previous_results 把上游结论作为 knowledge_info 注入自己的输入——这就是"flow"。
  • Coordinator(可选,complex 模式)校验完整性、补子任务;Synthesizer 汇总:report 模式 5 段式(提纲→并行写各节→图→润色→去重引用),qa 模式单段直答。

检索工具(CAMEL FunctionTool):arxiv_searchopenalex_search(~2.5 亿条)crossref_searchvolc_search(火山引擎)url_processor。需 TAVILY_API_KEY/VOLC_SEARCH_API_KEY 等(与 §7 的 tools/ 注册表是两套独立的工具栈)。

两点澄清① DRAgent 只按调用方给的 mode 选配置(dr_agent.py:79),没有任务复杂度自动分类器;mode 来自 config.agents.dr.mode(默认 simple)。② 改 discovery 主流程通常不用碰这 405 个文件——它只服务背景调研与 QA。

§可复用范式(从 InternAgent 偷什么)

① 思考 / 动手两层物理分离

"想点子"用便宜可控的 LLM + 结构化输出;"做实验"外包给一个 可替换后端。两层只用一个 ideas.json 通信。换 LLM、换"谁写代码"互不影响。

② 一套状态、两遍走法

用一个 method_phase 布尔,让同一组状态先磨"想法"再磨"方法"。比写两套流水线省一半代码,且天然复用 reflection/scholar 等阶段。

③ 记忆反哺出题(self-evolving)

别只把记忆用于"检索注入"。InternAgent 让经验反过来改写下一轮的 prompt,并用图结构把候选推向"未探索区"——这是把"探索-利用"显式工程化。

④ 失败记忆做"负过滤"

给每条实验打 +1/0/−1;生成新想法时,凡与已知失败相似度 ≥ 阈值就重新生成。低成本避免反复踩同一个坑。

⑤ AutoDebug = 把报错当下一个 prompt

实验失败时,不抛异常,而是把 traceback 拼成下一句指令喂回编码 agent。配合"成功→进下一 run、失败→iter+1"的双计数器,得到稳健的自修复循环。

⑥ 注册表 + 工厂,处处可插拔

agent / model / tool / 实验后端各有一个注册点(dict 或 map)。加新东西 = 改一处注册 + 加一段 config,不动主流程。
