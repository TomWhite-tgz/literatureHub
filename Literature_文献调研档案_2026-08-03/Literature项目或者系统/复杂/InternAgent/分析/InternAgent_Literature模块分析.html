一、按源码执行顺序看完整流程

阶段 A · 初始 idea 生成：Survey 只在这里出现

① Research Task任务描述、领域、约束、baseline code
→
② 检查 do_survey由 GenerationAgent 的配置决定
↓ true 时调用；false 时整步跳过
③ SurveyAgent（可选）围绕整个任务建立共享 paper_lst
→
④ GenerationAgenttask + baseline + paper abstracts → 初始 ideas

Survey 不负责验证某个具体 idea；它只给首次 Generation 提供整个任务领域的背景论文。后续演化轮次不会重新回到 GENERATING，因此通常也不会再次运行 Survey。

阶段 B · Idea 演化循环：这里实际调用 Scholar

⑤ ReflectionAgent逐个批评当前 ideas
→
⑥ ScholarAgent逐个检索支持 / 反驳证据
→
⑦ EvolutionAgentidea + critique + evidence → 新 ideas
→
⑧ RankingAgent评分并选择 Top ideas
↺ 未达到最大轮数：等待 / 读取反馈 → 回到 Reflection（不是回到 Generation）

源码状态是 REFLECTING → EXTERNAL_DATA → EVOLVING → RANKING。其中 EXTERNAL_DATA 的日志写着 “Survey Agent”，但实际执行的是 self._get_agent("scholar")；这是最容易造成误读的地方。

阶段 C · Top ideas 方法化：Scholar 再以“方法证据”身份出现

⑨ 达到最大演化轮数保留 Top ideas
→
⑩ ScholarAgent（按需）idea 若没有 evidence，则先补证据
→
⑪ MethodDevelopmentAgentidea + 文献 → 具体方法
↓ 方法生成后，固定进入一次方法反思与文献检索
⑫ ReflectionAgent批评 method details
→
⑬ ScholarAgent（必经）围绕 method critiques 再检索，写入 refine_evidence
→
⑭ RefinementAgent方法 + 新证据 → 最终可执行方法

此时 session.method_phase = true。同一个 EXTERNAL_DATA 状态不再把结果写入 Idea.evidence，而是写入 Idea.refine_evidence，随后转到 REFINING，而不是 EVOLVING。

Agent是否一定调用调用次数输入粒度输出给谁
SurveyAgent否，受 do_survey 控制通常 0 或 1 次整个 research taskpaper_lst → GenerationAgent
ScholarAgent（idea 阶段）是，EXTERNAL_DATA 必经每轮一次；每个 idea 各执行一份检索单个 hypothesisevidence / references → EvolutionAgent
ScholarAgent（方法初始化前）按需，仅为没有 evidence 的 Top idea 补齐0 或若干个 ideaTop hypothesispaper_context → MethodDevelopmentAgent
ScholarAgent（方法修订）是，方法 Reflection 后的 EXTERNAL_DATA 必经每个 Top method 一次method details + critiquesrefine_evidence → RefinementAgent

把整条线压缩成一句话：Survey 负责“生成想法前先了解这个领域”；Scholar 负责“想法生成后，为每个想法和方法查找能支持、反驳或改进它的论文”。流程由 OrchestrationAgent 的固定状态机控制，不是两个 Literature Agent 自己决定何时运行。

二、论文的“两种模式”与代码如何对应

1.0 论文中的说法论文描述代码中的主要承载者准确理解
Literature Review mode 把任务拆成关键词组合，跨学术库广泛搜索，根据摘要与任务的相关性筛选论文。 SurveyAgent 任务级广搜、扩展 paper bank、摘要评分，为 Generation 提供领域背景。
Deep Research mode 精读相关论文全文，并围绕生成 idea 中的技术术语继续搜索与收窄研究方向。 SurveyAgent 的 Top-3 PDF 深读
＋ ScholarAgent 的 hypothesis / method 检索		 代码没有一个明确的 mode=deep_research 开关；论文所说的第二模式被分散在两个类和两个工作流阶段中。

所以答案不是“1.0 只有 SurveyAgent”：论文层面可以这样概括；实现层面则必须看到 Survey 与 Scholar 的双层结构。尤其是“围绕已生成 idea 查证据”这部分，真正执行的是 ScholarAgent，尽管日志和论文有时仍把整个阶段笼统称为 Survey。

三、SurveyAgent：先为整个任务准备一份论文清单

Survey 回答的问题是：“在生成任何 idea 之前，这个任务周围有哪些值得参考的方法论文？”它的输入是整个 research task，输出是一个 paper_lst 列表；它不针对某个具体 hypothesis，也不写综述报告。

Input

一个任务

description、domain、约束，以及任务的输入 / 输出形态。

Work

找一批候选论文

多轮生成查询、跨三个论文库检索、按标题去重、基于摘要给相关性分数。

Output

一份共享阅读列表

每篇包含标题、年份、摘要、来源、分数等字段，整体交给 GenerationAgent。

先理解任务边界。LLM 从任务描述中提炼研究领域，以及任务的 input / output。这样可以避免只搜到“方法名字相似、实际任务不同”的论文。
发起第一轮宽泛搜索。LLM 生成一个 KeywordQuery("...")；PaperSurvey 把它同时送到 PubMed、arXiv 和 Semantic Scholar，每个来源最多取一批结果。
扩展 paper bank。只要论文数量不足且没有达到 10 轮上限，LLM 就参考已找到的论文与历史 query，再选择关键词搜索、相似论文搜索或沿参考文献扩展。
合并与去重。三个来源的结果被拍平成一个列表；1.0 Survey 主要按完全相同的标题去重，然后继续加入 paper bank。
收集结束后统一评分。LLM 每次阅读 10 篇论文的标题与摘要，为每篇打 1–10 分。判断依据是任务相关性、input / output 是否匹配、是否有实证实验，以及是否可能启发新 idea。
尝试精读 Top 3。从高分论文中选择最多 3 篇具有可访问 PDF 的论文，下载全文并抽取 background / contributions / methods / challenges；没有可用 PDF 就无法深读。
返回整个 paper list。execute() 不返回摘要报告，而是直接返回论文对象列表；OrchestrationAgent 把它放进 paper_lst，再交给 GenerationAgent。

一个简化例子

假设任务是“提高医学图像分割模型在小目标上的性能”，Survey 最终交出的不是一段结论，而是类似下面的列表：

[
  {
    "title": "Small Lesion Segmentation with ...",
    "year": 2024,
    "abstract": "We propose ...",
    "source": "arXiv",
    "score": 9,
    "is_deep_read": true,
    "methods": "从 PDF 抽取的方法摘要"
  },
  ...
]

这些字段并没有被完整使用：GenerationAgent 最后只把每篇论文的 title + year + abstract 拼进生成 prompt。Survey 从 PDF 抽取出的 methods / contributions / challenges 虽然保存在对象中，却没有进入 1.0 的 Generation prompt。因此 Survey 的实际作用更接近“为生成 idea 提供一批摘要材料”。

四、ScholarAgent：针对一个 idea 判断哪些论文与它有关

Scholar 回答的问题是：“对于这个已经生成的 hypothesis，哪些论文可能支持、反驳或帮助改进它？”它每次只处理一个 idea。所谓“变成证据”，具体是让 LLM 根据论文摘要给出相关性分数和支持关系，并不是从全文中抽取经过验证的证据句。

Input

一个具体 hypothesis

Research goal + 当前 idea；方法阶段还会加入 method details 与 method critiques。

Work

围绕这个 idea 查证

生成多条针对性 query，检索论文，再让 LLM 比较每篇摘要与 hypothesis。

Output

带判断的论文记录

evidence、references 和 relevance_summary，供后续 idea / method 修改。

围绕 hypothesis 生成 query。普通阶段根据 goal + hypothesis 生成查询；方法阶段则重点读取 method details 和严重的 method critiques，查找能够解决具体技术问题的论文。
查询数量由 search depth 控制。shallow 最多 2 条，moderate 最多 4 条，deep 最多 6 条。LLM 可能返回更少；如果完全失败，就直接用 hypothesis 文本搜索。
逐条 query 检索三个来源。每条 query 都交给 LiteratureSearch；PubMed、arXiv、Semantic Scholar 三个来源在该 query 内并发搜索，不同 query 之间则按顺序处理。
先去重并截断，再判断相关性。结果按 DOI 或小写标题去重，然后直接保留前 max_papers 篇。也就是说，截断发生在 LLM 相关性排序之前。
LLM 阅读标题和摘要进行判断。对每篇论文输出 relevance_score ∈ [0,1]、简短理由，以及 supports / contradicts / neutral / unclear 四种关系之一。
超过阈值才成为 evidence。默认要求 relevance_score ≥ 0.6。合格论文被转换成结构化 evidence；所有完成评估的论文则生成 APA reference，所以 references 可能多于 evidence。
把结果交给后续 Agent。idea 阶段写入 Idea.evidence，EvolutionAgent 用它修改 idea；方法阶段写入 Idea.refine_evidence，RefinementAgent 用它修改方法。

“论文变成 evidence”实际发生了什么

假设当前 idea 是：“在分割模型中加入多尺度边界注意力，可以改善小病灶识别。”Scholar 找到一篇论文后，LLM 可能产生：

{
  "title": "Multi-scale Boundary Attention for Lesion Segmentation",
  "content": "论文摘要原文 ...",
  "relevance_score": 0.86,
  "relevance": "论文使用相似的边界注意力，并报告小病灶性能提升。[Supports]",
  "url": "...",
  "doi": "..."
}

这里的 content 通常就是摘要；[Supports] 是 LLM 的分类结果，而不是系统执行实验后得到的验证结论。

Scholar 返回什么OrchestrationAgent 怎么处理最终是否被使用
evidence：超过阈值的论文及相关性判断普通阶段保存为 Idea.evidence；方法阶段保存为 Idea.refine_evidence是，分别进入 EvolutionAgent 或 RefinementAgent
references：已评估论文的元数据与 APA citation普通阶段保存为 Idea.references保存出处，但没有绑定到 idea 中的某一句 claim
relevance_summary：证据整体支持、反驳或混合的简短总结Scholar 返回了该字段，但 OrchestrationAgent 没有写入 Idea主流程中基本丢失

最简单的区分：Survey 输出“关于整个任务，建议先看哪些论文”；Scholar 输出“关于这个具体 idea，这篇论文与它有多相关，以及看起来是支持还是反驳”。两者使用独立检索结果，没有共享 paper bank 或统一证据库。

五、配置、并发与实际运行语义

论文实验设置

论文称 Survey 搜索并审阅 50 篇论文，Generation 生成 15 个 ideas，每个 idea 演化出 3 个变体，最多演化 4 轮并保留 Top 5。仓库中的 config/config.yaml 与这些数字一致。

启动器默认设置

launch_discovery.py 默认加载 config/default_config.yaml，其中 do_survey: false；如果用户不换成完整配置，任务级 Survey 不会运行。不过 Scholar 所在的 EXTERNAL_DATA 阶段仍是状态机必经步骤。

并发层级

不同 ideas 的 Reflection 与 Scholar 可并行，Scholar 受全局 semaphore 限制；单个 Scholar 内部按 query 顺序执行，而同一 query 的 PubMed / arXiv / Semantic Scholar 请求并发。

数据没有统一证据库

Survey 的 paper bank 与 Scholar 的 evidence 分别创建、分别去重；没有共享缓存、统一 paper ID、跨阶段引用图或 claim-level provenance。

一句话评价：1.0 已经不是 Dolphin 那种“一次检索、整池塞进 prompt”的简单 RAG，而是一个嵌入科研状态机的双层 Literature 子系统；但它仍属于固定流程中的检索与证据增强，还不是 1.5 论文所描述的图式 Deep Research。

当前版本：三套 Literature 机制怎样进入主流程

这不是从左到右依次执行的“三步”，也不存在三路共同汇合的节点。 当前源码同时保留 FlowSearch、SurveyAgent 和 ScholarAgent： 前两者在 idea 生成前提供两种不同的背景材料；ScholarAgent 则在 ideas 已经产生并完成 Reflection 后，为每个 idea 检索证据。

二、一次调用按什么顺序运行

适配与配置。DRAgent 根据 mode 读取 config_qa.yaml、config_simple.yaml 或 config_complex.yaml，动态把 dr_agents/ 插入 sys.path，再创建独立 Workflow。
构造全局 DAG。从仅含 task answer node 的初始图开始，Global Planner 最多迭代 2 次，让 LLM 输出 nodes / edges。节点只有 task、type ∈ {search, solve, answer}；边有 relationship。代码拒绝有环图。
执行一个拓扑层。get_ready_nodes() 找到全部前驱已完成的节点；Global Execution 用最多 10 个线程并行执行这一层。层与层之间仍是串行的。
节点内再规划。每个节点有独立 TaskWorkflow。Planner 读取节点任务、前置节点摘要、原始 query 和工具说明，生成 XML 子任务；simple / QA 最多 2 个，complex 最多 3 个。
子任务内 tool-calling。子任务按顺序执行。每轮模型可一次发出多个 tool calls；结果作为 tool message 回填，再让模型决定是否继续。配置的 max_tool_calls: 5 实际限制的是“tool-calling 轮数”，不是精确的工具调用总数。
三次压缩信息。原始工具结果先被子任务 summarizer 压缩；多个子任务再被 node summarizer 压缩；最终 Synthesizer 又按大纲重写。报告可读性提高，但原始证据定位信息会逐级损失。
可选动态改图。complex 模式在每层执行后让 Coordinator 读整张图，通过 JSON 操作新增、删除或修改节点 / 边。它是 LLM 自评的缺口修补，不使用 gold paper set、recall 或 evidence coverage 阈值。
合成答案。当 answer 节点变为 ready 时，不再把它当普通检索节点执行，而是交给 Synthesizer。QA 单 prompt 输出；report 先生成 outline，再用 10 线程并行写 section，complex 还逐节顺序润色。

三、状态、并发与数据传播

Graph state

内存中的 DirectedGraph

节点保存 attributes、PENDING / EXECUTED、入边和出边；执行结果另存在 execution_results。不是持久化知识图谱。

Parallelism

节点并行，节点内串行

同一拓扑层最多 10 线程；一个节点的多个子任务依次运行；一轮内模型可并行“提出”多个工具调用，但代码逐个执行。

Context flow

只传前驱摘要

后继节点通过 knowledge_info 获得直接前驱的 task、final_answer、success、reasoning 和边关系，不直接获得完整原始 trace。

Persistence

日志 / 可选 synthesizer input

可保存 execution trace 和最终合成输入；核心图默认仍是一次调用内状态，不会自动进入 InternAgent long memory。

Async boundary

外异步，内同步

DRAgent.execute() 是 async，但直接调用同步 workflow.execute()，因此会阻塞所在 event loop，直到整次 DR 完成。

Failure policy

失败转成普通字符串

初始化或执行失败被包装成“Please provide background context manually”，不向上抛错。调用方可能把降级文本当成成功的背景。

文献如何变成“证据”与“引用”

FlowSearch 的 citation lifecycle

搜索结果返回。ExecutionAgent 只对指定搜索函数提取 URL；arXiv / OpenAlex / CrossRef 标为 paper，Web 标为 webpage。
立即分配数字 tag。ReferenceManager 按 URL 首次出现顺序生成 1, 2, 3…，并把 tag 写回工具结果。去重键只有 URL。
LLM 决定是否引用。summary prompts 要求把工具结果中的 tag 写成 [[n]]。代码没有自动把 claim 对齐到 source，是否保留 tag 取决于多轮 LLM 重写。
报告只保留被写出的 tag。Synthesizer 从最终正文提取 [[n]]，匹配 ReferenceManager，按正文首次出现顺序重新编号，再追加 References。

做到了

线程安全收集 URL；区分 paper / webpage；报告模式可生成可点击 References；引用编号可重新整理。

没有做到

没有 DOI / arXiv ID 归一；没有 claim–quote span；没有 entailment / citation correctness verifier；没有检索覆盖率。

信息损失点

工具结果 → subtask summary → node summary → section writing → polish，多次生成都会丢失出处细节。最终只剩 URL，不保留原文段落位置。

引用标签的含义只是“这个 URL 曾出现在搜索结果里”，不是“这个 URL 已被证明支持旁边的 claim”。此外 QA 模式绕过 _append_references_to_report()，即使检索过程中收集了 URL，最终直接答案也可能没有 References。

Survey / Scholar 的 evidence lifecycle

Survey 的论文信息主要用于生成 idea，不形成 claim-level citation；Scholar 会把通过阈值的论文转换为 evidence item，并把所有评估过的论文转换为 reference。这里的 evidence 比 FlowSearch 更结构化，但仍是“摘要 + LLM 相关性判断”，不是已核验的证据片段。

1.5 §2.2.1：跨学科知识图谱到底在做什么

核心含义：论文试图把来自不同领域的论文、综述、技术报告和领域笔记，加工成一个 “文献—概念—方法—数据集—科学问题—实验设置”异构图；查询时同时做图搜索与向量搜索， 再把命中的材料组织成带关系和出处的证据链。它不是 Figure 5 的 Flow Graph：KG 回答“有哪些知识可用”， Flow Graph 回答“这一次研究应该怎样执行”。

第一步：Schema-guided extraction 不是自由抽取

schema-guided 意味着先规定允许出现的科学对象和关系，再按照这套 schema 从文本中抽取，而不是让 LLM 临时创造任意节点类型。根据论文原文，至少可以还原出下表：

类别可能的图元素作用
文档节点论文、综述、技术报告、领域笔记保存标题、作者、时间、DOI / URL、正文或解析结果，是证据来源。
科学实体节点concept、method、dataset、empirical setting、problem statement把“论文相似”提升为“哪些方法解决哪些问题、在哪些数据和条件下验证”。
文本关系proposes、uses、evaluates-on、supports、contradicts、related-to 等由正文陈述抽取；论文只举出 cites 和 by product，完整关系 schema 未公开。
文献计量关系citation、co-citation、co-usage用共同引用或共同使用的方法、数据集、概念，为尚不明确的实体建立初始联系。
证据锚点原文片段、来源论文、引用记录把图中的边对齐到文本证据和引用证据，使关系理论上可以回溯。

第二步：从“脏候选”整理成紧凑图谱

解析跨领域文本。输入可能来自论文、综述和报告；格式、命名习惯及学科术语并不统一，因此原文称其为 noisy, cross-domain text。
发现候选实体。先用领域无关 NER 和 noun-phrase mining 找人名、方法名、数据集、科学概念及问题短语；这一步只产生候选项，不代表已经完成正确分类。
建立初始链接。正文中的共同出现提供文本线索；document-level co-citation 表示两项工作经常被一起引用；co-usage 很可能指共同使用方法、数据集、指标或概念，但论文没有给出严格定义。
实体归并与消歧。例如 AMOC、Atlantic Meridional Overturning Circulation 应合成一个概念节点；同名但不同义的实体则应拆开。
规范节点和边。把模糊的“相关”细化为有方向、有类型的关系，并统一 concept / method / dataset 等节点类型，压缩重复和噪声。
对齐证据。将抽取自正文的关系与引用网络提供的关系一起保存，理想输出不只是一个 edge，还应包含支持它的原文和文献出处。

“跨学科”的关键不是把多个学科的论文堆在一起，而是让一个领域的问题能够沿图路径连到另一个领域的方法。例如“AMOC 临界点预测”可经由“critical slowing down”连接到生态系统或复杂系统中的早期预警方法。

第三步：Graph search 与 dense retrieval 为什么要同时使用

Explicit structure

Graph search

沿已有边查找节点和路径，适合回答“它们通过什么科学关系连接”。结果可呈现为 问题 → 方法 → 数据集 → 论文证据，结构清晰且原则上可解释；但图中没有建边的相关内容可能被漏掉。

Semantic neighborhood

Dense vector retrieval

把 query 和文档或图节点编码成向量，找语义相近内容。它能召回尚未被图谱显式连接的工作，例如把 AMOC tipping point 与其他领域的 early-warning signal 方法联系起来；但相似不等于存在可靠科学关系。

最后的 ranking step 将两路候选合并，输出 path-structured evidence chains。论文没有说明排序特征、权重或训练方法，因此不能确定它究竟使用向量分数、图距离、引用信息、文献质量还是 LLM reranking。

当前实现中最影响理解与复现的技术边界

FlowSearch

--file 默认路径未接通

Planner 直接调用工具名 extract_document_content；但配置启用的是类别名，三个默认配置都未包含 file_processor。异常被捕获后退回默认子任务，容易形成“看似运行、实际没读文件”的静默降级。

FlowSearch

OpenRouter 只接入了主框架

DR 有独立 models/get_model()，不识别 OpenRouter provider；工具模块导入时还会创建 GPT-4o / GPT-4o-mini / o3-mini / o4-mini 对象。修改主 default_provider 不会统一替换 DR 模型。

FlowSearch

引用管理有残留标签 bug

真实 tag 是纯数字；update_reference() 却按带前缀标签切 tag[1:]，ExecutionAgent 中一个未使用的辅助函数也按 [R1] 解析。主报告路径走另一套 [[1]] 逻辑，因此不是所有运行都会触发，但显示实现曾迁移过标签协议。

FlowSearch

“有 PDF URL”不等于“做了全文检索”

默认学术工具返回摘要和链接；只有模型继续选择 url_processor 才会读页面，而且读后只保存一次针对问题的答案。没有论文级 chunk、embedding index、passage rerank 或页码定位。

Survey

Web source 会被永久移出实例配置

execute() 首次调用 Web 后直接修改 self.sources 删除 web_search。AgentFactory 会缓存实例，因此后续 discovery round 复用同一个 SurveyAgent 时，不再做 Web 搜索。

Survey

查询语法与后端不一致

prompt 要求输出 KeywordQuery(...) / PaperQuery(...) / GetReferences(...)，但新版代码不再通过旧 PaperSurvey.query_route() 解析，而把整段字符串直接交给 arXiv / CrossRef 搜索。

Survey

第二批之后的评分 ID 写回可能失效

prompt 给论文的 ID 是全局编号；写回代码却把 LLM key 当作批内 0…9。若第二批返回 10…19，这些分数会被忽略，论文保留默认分 1。

Scholar

先截断，再做相关性评估

多 query / 多 source 结果按收集顺序合并，DOI / 标题去重后先取前 max_papers，然后才让 LLM 评估相关性。它不是对完整候选集做全局 reranking。

最终判断

InternAgent 的文献能力确实经历了实质升级：从扁平 paper bank，发展为任务级调研、假设级证据和图式 Deep Research 三层能力。当前最成熟的工程部分是“DAG 拆解 + 工具调用 + 分层并行 + 报告合成”；最薄弱的部分是“三条检索路径没有统一、论文级归一不足、全文与 passage 证据不稳定、引用没有支持性验证”。

因此，它更适合被理解为科研 Agent 的知识获取与上下文生成层，而不是已经完成的系统综述引擎或审计级 Literature evidence system。
