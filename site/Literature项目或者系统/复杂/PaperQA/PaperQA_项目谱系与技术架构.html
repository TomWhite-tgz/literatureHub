01

先建立全貌：PaperQA 到底位于哪里

机构目标

自动化科学发现

FutureHouse 的目标不是只做搜索产品，而是让 AI 能读文献、形成假设、分析数据、设计与解释实验。

PaperQA 的位置

文献研究 Agent

它负责把海量论文变成带出处的证据和答案，是 AI Science Assistant，而不是完整 AI Scientist。

向上生长

WikiCrow / ContraCrow

同一套检索与证据机制，通过不同任务提示和配置，变成综述生成器与矛盾发现器。

进入系统

Edison Literature / Kosmos

PaperQA3 支撑面向用户的 Edison Literature，同时是 Kosmos 科研过程中的文献检索层。

最重要的理解

PaperQA 解决的是“从科学文献得到可信、可追溯的证据”这一子问题。 当它被 WikiCrow 调用时，输出长篇主题综述；被 ContraCrow 调用时，寻找反例；被 Kosmos 调用时， 它提供构建与更新 world model 所需的外部知识。上层任务不同，底层文献能力相通。

他们怎样理解“AI Scientist”

1AI Tools预测模型、数据库、实验设备、解析器与 API，例如结构预测或 PDF parser。
2AI Science Assistant完成一个多步骤科研工作流。PaperQA / Edison Literature 属于这一层。
3AI Scientist围绕 world model 循环提出假设、分析数据、规划验证并更新认识。Kosmos 位于这里。
4Human给出 broad quest、价值判断与现实验证，不必规定每一步工具调用。

因而 PaperQA 很重要，但它不是终点：它是“读懂已有知识”的能力模块；完整 AI Scientist 还要处理数据、假设、实验和持续更新。 参见 FutureHouse 的四层定义。

仓库与研究路线如何演化

下面把论文、代码版本、评测集、派生应用和组织变化放到一条时间线上。

2023-02代码起点

PaperQA 仓库初始提交

从“给一批 PDF 做带引用问答”起步。核心对象是 Docs：解析文档、检索片段、汇总证据、生成答案。

2023-11～12机构 + v1

FutureHouse、PaperQA 论文与首版 WikiCrow

FutureHouse 宣布构建 AI Scientist；PaperQA v1 将 RAG 拆成 Search、Gather Evidence、Answer 三类动作，并以 LitQA v0 的 50 道全文检索题评测。

2024-07评测扩展

LAB-Bench 与 LitQA2

不再只问“会不会答题”，而是评估文献检索、图表理解、数据库访问、克隆与序列任务。公开 LitQA2 本地归档含 199 条记录。

2024-09PaperQA2

论文系统与代码 v5.0.0

Agent 式查询扩展、LLM 重排与 contextual summarization（RCS）成为核心；研究系统还利用引用图补充论文。WikiCrow2 和 ContraCrow 展示同一文献底座的不同任务形态。

2024-12训练框架

Aviary

把 LitQA2 等科学任务封装成 Agent environment，使 tool-use trajectory 可评测、训练和优化。当前 PaperQA 运行时也直接使用 Aviary 的 Environment / Tool 抽象。

2025-01～08能力扩展

临床试验、控制工具与多模态起步

仓库加入 clinical trials 搜索、更多元数据和 Agent 控制；2025-08 开始加入多模态 PDF 支持，使图表进入开源解析与证据流程。

2025-11～12组织与版本

Edison 成立；PaperQA 改用 CalVer

商业平台从 FutureHouse spin out；代码从 v5.x 改成 v2025.12.17 等日期版本，并加入 Docling、Nemotron Parse、Office、图表与公式处理。

2026-02PaperQA3

Edison Literature 的多模态深度研究

产品侧可在超过 1.5 亿论文与专利中按需读取图表，并让 reasoning LLM 自主检查文档、复查片段和决定结束时机；同时服务 Kosmos 的文献环节。

2026-02～05LABBench2

用更贴近现实的任务继续驱动迭代

LitQA3、FigQA2、PatentQA、TrialQA 等任务把文本检索、图表、专利和临床试验放进同一评测体系，成为 PaperQA3 的公开证据之一。

命名提醒：论文代际与 Python 包版本不是同一种编号。官方规定 paper-qa >= 5 叫 PaperQA2； 2025-12 后包版本改成日期。PaperQA3 目前主要是产品/研究发布名称，仍链接同一个开源仓库，没有单独的 PQA3 arXiv 论文或独立 repo。

05

三代整体架构：每一代真正改了什么

PAPERQA v1 · 2023

把 RAG 变成会循环的文献 Agent

  • Search：LLM 生成关键词，在大语料中找论文。
  • Gather：在全文片段中做语义检索并产生证据摘要。
  • Answer：对证据再排序，生成带引用回答。
  • 可根据新术语再次搜索，而非一次检索后直接回答。
核心突破：RAG 步骤成为可反复调用的动作。
PAPERQA2 · 2024

更强的检索决策与证据质量控制

  • Agentic query expansion：逐轮改写、补充搜索。
  • RCS：LLM 先按问题给片段打分并写 contextual summary。
  • Citation traversal：研究/内部系统沿引用图补充候选。
  • 用元数据、来源质量与跨文献证据改善事实性。
核心突破：不只“搜得像”，还要让证据真正支持问题。
PAPERQA3 · 2026

多模态、广语料与更自主的 reasoning Agent

  • 读取论文/专利的图、表、公式与页面图像。
  • LLM 决定何时查看图片，避免把所有图塞进上下文。
  • 覆盖论文、专利、临床试验与来源可信度元数据。
  • 弱化固定 harness，让模型自主复查并决定完成。
核心突破：从“文本证据 RAG”变成文档级多模态深度研究。

一次查询的共同骨架

1. 问题科学问题或 claim
2. 候选文献关键词、索引、元数据
3. 证据片段/页面/图表打分与摘要
4. 决策继续搜、换问法、重置或回答
5. 输出结论、引文、页码与不确定性

代际变化主要发生在第 2～4 步：候选文献覆盖更广、证据表示从文本扩展到图表、Agent 的动作选择与停止判断更自由。

06

当前开源仓库：真正的代码架构

当前 HEAD 为 d7675d7（2026-06-05）。仓库不是“一个 prompt 加向量库”，而是由文档摄取、 索引/元数据、Agent environment、工具和状态五部分组成。

A. 文档摄取与检索层

输入
PDF、纯文本、HTML、Office、图片；产品侧还接入论文、专利与临床试验语料。
Reader / Parser
pypdf、PyMuPDF、Docling、Nemotron Parse 等，把页面转换为文本、表格和 ParsedMedia。
元数据
Semantic Scholar、Crossref、OpenAlex、Unpaywall、撤稿与期刊质量；多源查询减少单点错误。
索引与 Docs
Tantivy 本地全文索引定位文档；文档进入 Docs 后切块、嵌入，供问题相关的片段检索与摘要。

B. Agent 状态层

每轮 LLM 不是盲看全部论文，而是看到任务 prompt、工具描述、工具历史、最佳证据和一个紧凑状态摘要。

EnvironmentState
docs当前已加入的文档、文本块与元数据
sessionquestion、contexts、answer、tool_history、token/cost
statusPaper Count / Relevant Papers / Current Evidence
tools按 Settings 构造的本轮可调用动作
它确实是 Agent。默认 ToolSelector LLM 根据状态动态选工具；只有 fast 配置使用 fake 路径，固定执行 search → gather → answer。

运行时循环：LLM 选择动作，Python 保存状态并执行

◎
ToolSelector LLM 读取问题、状态计数、工具结果和少量高分证据；输出一个或多个 tool call。
paper_search用 LLM 给出的查询和年份过滤搜索本地文献索引，把新论文与文本加入 Docs。可并发
gather_evidence针对一个更具体的问题检索片段；summary LLM 生成上下文化摘要与相关度分数。更新 contexts
gen_answer使用当前高分证据和来源上限生成带引用答案；失败时 Agent 可以继续检索。写入 answer
reset清空不合适的证据上下文，但保留原始任务，允许换方向重新搜集。纠偏
complete明确报告最后答案是否成功，并终止 environment rollout。正常结束
clinical_trials_search可选工具：按临床试验语法搜索并把结果接入同一证据流程。非默认
循环不是固定四轮。每次 Environment.step() 记录工具调用、并发执行允许的工具、把结果交回 LLM； Agent 可以反复 search / gather，也可以 answer 后发现不足再继续。仓库默认 max_timesteps = None，但仍受超时、 runner 的步数限制、最大回答失败次数和 complete 控制。
正常完成LLM 调用 complete，标记 certain 或 unsure。
时间耗尽默认 agent timeout 为 500 秒；超时后 Python 强制再执行一次 gen_answer。
步数截断runner 可设置 max_timesteps；截断同样走兜底回答。
失败保护达到最大 answer 尝试或 trajectory 异常，状态转为 unsure / fail，而不是无限循环。

证据检索内部到底做什么

阶段代码行为LLM 的职责Python / 数据结构的职责
文档级搜索SearchIndex.query() 找 top-N 文档，默认一次 8 篇；重复同一查询会用 offset 取下一页。提出搜索表达式、年份范围并决定是否继续。索引查询、去重、加载文本和文档元数据。
片段级检索Docs.aget_evidence() 按具体子问题检索文本块。可把总问题改写成更适合证据收集的子问题。嵌入相似度、chunk 管理、并发和缓存。
RCSsummary LLM 对每个候选片段输出摘要、相关度分数；多模态时可附页面图片。判断“这个片段对当前问题具体支持什么”。保存 Context、排序并只展示少量最佳证据给 Agent。
回答Docs.aquery() 选择高分来源并生成有 citation key 的回答。跨来源综合、处理冲突、保持答案紧扣证据。来源上限、引用格式、answer/session 持久化。

多模态怎样进入开源实现

Parse

页面 → 文本 + Media

Reader 保存页面文本，并把图、表、公式作为 ParsedMedia，保留 page_num、类型、图片字节或表格文本。

Enrich

图片描述改善检索

enrichment LLM 描述图表中的标签、图例、趋势和科学含义，使纯文本 embedding 也能把相关图所在页面检索出来。

Reason

按需交给多模态 LLM

生成 contextual summary 时可把候选页面图片一并发送，并记录 used_images；产品侧再由 Agent 决定何时深入查看。

每个派生项目的整体架构

生成式应用

WikiCrow

给定基因或主题，按预设章节拆成多个研究问题；每节调用 PaperQA 搜集证据并写 Wikipedia 风格段落，最后合并、去重引用。

主题 → 章节问题 → 多轮检索/RCS → 分节回答 → 文章与参考文献
本地已归档 19,249 篇 WikiCrow2 文本。
矛盾发现

ContraCrow

从目标论文抽取 claim，把 claim 当成检索问题寻找支持或反对证据，再用 11 档标签从 explicit contradiction 到 explicit agreement 分级。

Seed paper → Claims → 针对 claim 检索 → 证据综合 → 矛盾强度与出处
训练与环境

Aviary

不是新的文献搜索算法，而是 Environment + Tool + Reward/Task 的训练框架。它把 LitQA2 变成 trajectory，可训练 Agent 如何选择工具。

Task → Environment observation → Agent action → Tool response/reward → 下一步
评测体系

LitQA / LAB-Bench

LitQA 专测“答案藏在全文、摘要不够”的文献题；LAB-Bench 再加入图表、数据库、序列与实验设计，让优化不局限于问答分数。

真实研究任务 → 人类/模型基线 → 消融定位瓶颈 → 反向推动 Agent 改进
产品化文献 Agent

Edison Literature

PaperQA3 的用户界面与 API。生产端自带大规模全文/专利索引、来源可信度服务和多模态解析，而不是要求用户先准备一小批 PDF。

问题 → 全局语料检索 → 文档/图表核验 → 简洁带出处回答 → 页面级证据展示
AI Scientist

Kosmos

将 PaperQA3 文献能力与代码执行、数据分析和持续 world model 结合。文献证据只是它更新研究状态、提出与检验假设的一种输入。

Quest → 文献 + 数据 → World model → 假设/分析 → 新证据 → 持续更新
PaperQA 有“主题模式”和“Idea 模式”吗？
当前官方 PaperQA 仓库没有 AI Researcher 那种明确的 Topic / Idea 二分。它的变化主要通过 问题、工具集合、prompt 和 Settings preset完成： high_quality 做高质量问答，fast 走固定低成本路径， wikicrow 写综述，contracrow 判矛盾，clinical trials 配置搜索试验。 “生成 Idea”属于上层科研任务，可以调用 PaperQA 提供证据，但不是仓库内置的独立模式。
Semantic Scholar 在这里扮演什么角色？
它是元数据与引用关系来源之一，不是整个 Agent。PaperQA 还会用 Crossref、OpenAlex、Unpaywall、撤稿与期刊质量数据； PDF 解析、切块、embedding、RCS、工具循环和最终回答都在 PaperQA 自己的流程中完成。 更重要的是：当前开源默认 paper_search 搜索用户构建的本地索引，不等于生产版直接拥有全量 Semantic Scholar 全文。

必须分清的三层边界

论文系统

研究结论与消融

PaperQA2 论文描述了内部完整系统，包括全语料检索和 citation traversal，并在 LitQA2、WikiCrow、ContraCrow 上评测。

开源仓库

可运行的算法框架

公开 reader、索引、RCS、Agent environment 与默认工具；通常需要用户提供可访问的论文全文，默认工具中目前没有 citation traversal。

生产平台

语料、授权与基础设施

Edison 拥有大规模论文/专利索引、授权全文、内部元数据服务、多模态计算和产品层 orchestration，不能由 GitHub 包自动得到。

因此不能直接说“clone 仓库就复现 PaperQA3”。 更准确的说法是：开源仓库提供核心算法与可配置 Agent；论文和生产指标还依赖内部工具、访问许可、索引质量、模型与计算预算。 官方 README 也明确说明内部工具和论文访问授权存在差异。 查看本地 README 原文
