01

先建立正确的系统心智模型

PaperQA 同时是一条文档处理管线、一个高精度 RAG 内核，以及一个让 LLM 决定检索步骤的 Agent harness。

A

它处理什么

PDF、文本、HTML、Office 文档、源码，以及新版本中的图、表、公式和页面图像。

B

它检索什么

默认搜索用户预先准备的本地语料库。先选论文，再从入选论文中选片段。

C

Agent 决定什么

选择搜索词、何时重新搜索、用什么问题取证、何时生成答案、是否重置或结束。

D

Harness 决定什么

可用工具、状态更新、执行并发、超时、步数、失败回退、引用格式和答案持久化。

✓
一句话定义

当前开源 PaperQA 是“在本地科学文献库上运行的、证据摘要驱动的 Agentic RAG”。它不是单次 LLM 调用，也不是默认拥有开放互联网浏览器的通用研究 Agent。

控制面：谁决定下一步

run_agent、PaperQAEnvironment 和 Aviary/LDP Agent 组成循环。LLM 只能通过工具改变研究状态，不能直接绕过 Environment 完成任务。

数据面：证据怎样流动

Docs、DocDetails、Text、Context 与 PQASession 承载论文、切块、证据摘要、引用和最终答案。

03A

PaperQA v1：LangChain Agent 包裹的非线性 RAG

以下只还原 2023 年论文实验中的架构，不混入当前版本的 Environment、Tantivy、Aviary/LDP、多模态 reader 或临床试验工具。

v1
一句话定义

一个 GPT-4 Agent 控制 search、gather evidence、answer question 三种 RAG 工具，在共享论文库和证据库上反复执行，直到它认为答案足够完整。

用户科学问题 · 系统先用完整问题自动执行一次论文搜索
↓
Agent LLM · GPT-4-0613 LangChain OpenAIFunctionsAgent · 改写问题、选择工具、判断证据是否足够、接受或拒绝候选答案
Tool 01

Search · 论文级检索

  1. Agent 给出关键词与可选年份
  2. Google Scholar 检索可访问论文
  3. 经 arXiv、PMC、PubMed 等取得全文
  4. PDF 解析并切成重叠的 4,000 字符 chunk
  5. text-embedding-ada-002 向量化入库
Tool 02

Gather Evidence · 片段取证

  1. Agent 提交一个具体问题或子问题
  2. 向量搜索召回候选 chunk
  3. MMR 增加来源与内容多样性
  4. GPT-3.5 针对问题摘要每段
  5. 输出 1–10 relevance score，高分证据入库
Tool 03

Answer Question · 引用回答

  1. Ask LLM 先给约 50 字参数知识
  2. 从证据库选最高分的 8 条 Context
  3. GPT-4 Answer LLM 综合回答
  4. 每项主张附论文 citation marker
  5. 证据不足时应输出 “I cannot answer”
共享论文库 / Bibliography已经找到的论文、元数据、全文 chunk 与 embedding
⇄
共享证据库 / Context Library面向问题生成的摘要、出处与相关性分数
关键控制回路：候选答案会先返回 Agent，而不是直接交付用户。Agent 可以接受并结束，也可以认为答案不完整，再次搜索、换一种问法收集证据，然后重新生成答案。这是 v1 所说的 a posteriori 判断。

三层检索，而不只是“embedding 找相似文本”

01论文搜索Google Scholar + 全文获取 API，先决定读哪些论文
02向量召回问题 embedding + MMR，从论文全文中找候选 chunk
03LLM 重排Summary LLM 将 chunk 改写成问题相关证据并给 1–10 分
04证据归约最高分的 8 条 Context 进入最终回答 prompt

一次回答中的四个 LLM 角色

Agent LLMGPT-4-0613规划、选工具、改写检索、判断是否继续；temperature 0.5。
Summary LLMGPT-3.5-turbo-0613并行摘要候选 chunk 并评分；temperature 0.2，是调用量最大的模型。
Ask LLMGPT-4-0613提供预训练参数知识，作为最终回答的额外背景；temperature 0.5。
Answer LLMGPT-4-0613根据证据和背景生成带引用的候选答案；temperature 0.5。
!
RCS 分数的正确理解

1–10 分是 Summary LLM 为候选证据生成的工程排序信号，与 embedding 距离共同完成第二次筛选；它不是经过专家标定的科学相关性尺度，也没有在论文中证明跨问题可比较。

v1 已经是什么

它已经是会多步执行的 Agent：可以重复搜索、分解问题、换关键词取证、生成候选答案，再决定是否继续。它不是“一次检索 + 一次 LLM”的固定 RAG。

v1 还不是什么

它不是新的通用 Agent 算法，也没有当前版本正式的 Environment、ToolRequest、PQASession、Tantivy 本地索引、明确终止工具与失败状态；更接近 LangChain Agent 加共享可变状态的科学 RAG 系统。

架构依据：PaperQA v1 论文 §3.1–3.2、§5.1 与附录 A.2–A.4。论文实验每轮 Gather Evidence 考虑 20 个候选来源，最终回答使用 8 条证据 Context。

03B

从 ICLR 2024 同行评审反看 PaperQA v1

这组评审最有价值的地方，不是“论文被拒”本身，而是它清楚暴露了 PaperQA v1 的贡献边界、评测薄弱处，以及后来 PaperQA2 为什么必须把系统和 benchmark 都做得更完整。

展开 ICLR Submission 8010 评审档案 横向滑动阅读：Area Chair → 4 位审稿人 → 作者总体立场 → 综合分析

投稿时间为 2023-09-24，最终决定为拒稿。四位审稿人的分数并不一致：两位明确拒绝，一位略低于接收线，一位略高于接收线；Area Chair 最终认为“创新性有限 + LitQA 规模过小”没有在 rebuttal 中得到实质解决。

Area Chair · CTzJMeta-review

决定者：问题不在结果，而在贡献是否足够

核心判断

  • 方法仍像常见 RAG 框架，论文没有证明足够强的方法创新。
  • LitQA 只有 50 题，难以承担“新 benchmark”的主贡献。
  • 剩余贡献主要是实验评估，但评测细节本身也存在争议。

为何 rebuttal 没扭转决定

作者解释了标注昂贵，却没有在投稿后扩大数据集；AC 因而看不到 camera-ready 阶段能出现实质改善的证据。

理解要点：高性能不自动等于论文贡献强。AC 把“系统效果”与“方法/benchmark 贡献”分开评价。

Reviewer · 1BNP3 / Reject

可复现性审查者：概念有前景，技术说明不够

认可

认可“找论文—抽取证据—综合回答”的完整科学检索流程，也认可 LitQA 尝试逼近真实文献研究。

主要质疑

  • pipeline 与已有 retrieval–reading–answering 工作差异不足。
  • 50 题无法充分检验泛化。
  • 1–10 relevance score 缺乏标定；模型版本、竞品配置与实验细节缺失。

作者回应

强调 Agent 可任意次、任意顺序调用 RAG 工具；补充模型为 gpt-3.5-turbo-0613 和 gpt-4-0613，并说明分数只用于把 20 个候选压到 8 个。

理解要点：RCS 的数字是工程排序信号，不是经专家标定、可解释的“科学相关性测量”。

Reviewer · afKA3 / Reject

研究问题审查者：更像产品，论证有过度延伸

主要质疑

  • 论文没有一开始明确提出要回答的研究问题。
  • 参数知识与检索证据冲突时怎么办，没有系统研究。
  • “错误率低”不能推出“模型更确定”；API 用时与人类判断时间也不可直接类比。
  • 要求 summary LLM 给分却“不解释分数”，所谓 reasoning 缺少可检查依据。

作者回应

后补三个问题：非线性 Agent RAG 是否优于线性 RAG、RAG 工具是否改善科学 QA、全文分层 RAG 是否减少虚假引用；并把“更确定”改成“更愿意在不确定时表达不确定”。

理解要点：这是对 claim discipline 的批评——实验支持“答对得更多”，却未必支持校准、推理或类人研究效率。

Reviewer · CSpW5 / Borderline reject

Agent 视角审查者：看到了模块化价值，但不认为框架新

认可

准确抓住 PaperQA 的技术特点：把 search、gather evidence、answer 拆成工具，允许系统改写检索词、重复取证，并判断答案是否完整。

主要质疑

  • 动态工具调用与 ReAct 很接近，缺少 ReAct、Reflexion 等 Agent 框架对照。
  • 50 道选择题与真实科学研究、长答案生成仍有明显距离。
  • “零引用幻觉”的长文本实验细节交代不足。

作者回应

明确 PaperQA 不是新 Agent 框架，而是搭在任意 Agent 框架之上的科学 QA 系统；当时实际使用 LangChain OpenAIFunctionsAgent，ReAct 测试差异不大。

理解要点：PaperQA 的原创单元更适合说成“科学 RAG 工具与 workflow 设计”，而不是新的通用 Agent 算法。

Reviewer · vdwn6 / Weak accept

评测设计审查者：效果认可，但担心过拟合与选择题捷径

认可

认为写作清晰、消融充分、LitQA 上表现很好；阅读 rebuttal 后还将分数上调 1 分。

主要质疑

  • 50 题是否事实上成了开发集？缺少 dev/test 划分。
  • 选择项给了额外线索；真正重要的应是去掉选项后的开放回答结果。
  • 长文本零幻觉很难置信，需要解释评估方法与搜索工具条件。
  • Perplexity、Scite、Elicit 并非为选择题设计，比较是否公平？

作者回应

称 LitQA 在系统完成后才引入、未用于调参；无选项答案由 GPT-4 判定并人工抽查一轮；引用幻觉实验本来就是无选项长答案。

理解要点：这是最支持论文的审稿人，但他依然认为开放式评测才更接近 PaperQA 的真实用途。

Authors · Rebuttal总体立场

作者怎样定义自己的贡献

他们坚持的三点

  • 把 RAG 步骤暴露为工具，让 Agent 非线性地重复、改写和组合步骤。
  • 检索范围覆盖广泛科学文献，并深入全文，而非只看摘要或单一数据库。
  • 证明通用 LLM 配合合适工具，可以优于单纯调用 LLM，未必需要任务微调。

他们承认的边界

LitQA 规模小；开放式 QA 尚需更好的评估；相关性分数未经标定；工业竞品内部配置不可知；早期文字中关于“确定性”和 GPT-4 summary 的部分表述不严谨。

理解要点：作者最强的答辩是系统工程与实证效果；最弱的答辩是用“数据昂贵”回应 benchmark 规模与统计可靠性。

Synthesis · 我们的判断如何利用评审

拒稿没有否定系统价值，但限定了应如何描述它

真正站得住的贡献全文科学文献检索、证据压缩与引用回答被组织成可迭代工具链；系统效果具有吸引力。
不能夸大的贡献它不是新的通用 Agent 框架；1–10 RCS 也不是经过校准的相关性理论。
最大评测弱点LitQA v1 仅 50 道选择题，缺少独立划分，开放式现实任务的证据不足。
最关键的方法风险参数知识、选择项和检索证据可能共同提供捷径；引用正确也不等于结论完整或科学上可靠。

把它放回项目演进中

这批意见解释了后续工作的方向：PaperQA2 更强调可复现的 Agent harness、完整轨迹和更严格的 LitQA2；当前代码则进一步把 Environment、Tools、索引、模型角色和失败状态工程化。换言之，v1 的拒稿问题并未让 PaperQA 消失，而是推动它从“效果很好的 RAG 应用论文”转向更可测、更可审计的研究系统。

最终定位：把 PaperQA v1 看作一个有价值的科学文献 Agent 原型与系统实证，而不是已被充分验证的新 Agent 方法或成熟 benchmark。

范围提醒：上述批评针对 2023 年投稿的 PaperQA v1 与 LitQA v1，不能原样套用到 PaperQA2、LitQA2 或 2026 年的当前代码；后续章节描述的是显著扩展后的系统。

03C

PaperQA2：围绕召回、证据质量与可归因性重构

PaperQA2 没有推翻 v1 的 Agentic RAG，而是把“Agent 为什么有用、检索在哪一层失败、怎样更可靠地筛证据”变成可消融、可度量的工程问题。

一句话定义

一个读取显式状态的 GPT-4-Turbo Agent，动态控制论文搜索、全文取证、引用图遍历和引用回答；它用 hybrid retrieval 扩大召回，用深层 RCS 压缩并重排证据，再让生成模型只基于最高质量 Context 作答。

为什么从纯 dense 变成 hybrid

语义 embedding 擅长找概念相似内容，稀疏关键词向量擅长保留基因名、化合物、变异编号和缩写等精确符号。科学检索同时需要两种能力。

结构化 RCS

为什么摘要不只是文本

真正驱动变化的六个 insight

01
首要瓶颈常在召回，而不是写答案

目标论文没进入状态，Answer LLM 再强也无从回答。因此 v2 测量 Search → Top-k → RCS → Attribution 每一阶段是否仍保留正确 DOI。

02
Agent 的价值是“修复检索失败”

No Agent 固定管线显著更差。动态系统的优势来自看到低召回后改关键词、再次搜索或沿引用图扩展，而不是抽象的“思维链更长”。

03
引用网络本身就是科学检索索引

高相关论文的 references 与 citers 往往比表面关键词更接近目标证据。Citation Traversal 模拟研究者顺藤摸瓜，并提高 DOI recall。

04
RCS 存在模型能力门槛

GPT-3.5 和 Llama 3 70B 做 RCS 有时比不做更差；错误摘要或评分会提前丢掉正确证据。GPT-4-Turbo RCS 显著更强。

05
检索要看得宽，生成要喂得精

RCS 深度从 1 增至 10 明显提高准确率，10–30 仍有递减收益；先并行审查更多 chunk，再只把最高质量摘要交给 Answer LLM。

06
Context 不是越多越好

更多证据提高覆盖率，也带来干扰与冲突。5 条 Context 偏向 accuracy，15 条偏向 precision，因此 cutoff 是任务相关参数。

PaperQA2 核心之外的两个外层系统

PaperQA2 Core一次任务中的搜索、取证、引用遍历与回答 Agent；它才是本节的核心架构。
WikiCrow围绕基因的结构、功能、互作和临床意义，编排多个 PaperQA2 调用后合成长篇 Wikipedia 风格文章。
ContraCrow先从论文抽取 claim，再让 PaperQA2 跨文献寻找支持、反驳或无证据，完成矛盾检测。
!
论文系统不等于当时开源仓库的开箱能力

论文实验运行在作者机构更完整的 HTTP 与数据基础设施上，包含非本地全文访问、缓存、数据库、任务编排和云存储。论文明确说明：当时开源包不包含完整的非本地全文检索、GROBID 服务代码和 Citation Traversal 工具。算法与配置公开，不代表外部用户无需补基础设施就能逐项复现。

架构依据：PaperQA2 论文 §2–3、§8.1–8.1.1。LitQA2 运行平均每题使用 14.5 篇论文、调用 1.26 次搜索和 0.46 次引用遍历，说明工具轨迹确实随问题动态变化。

Agent 不负责解析 PDF 或实现检索；它只选择工具。Environment 把工具调用作用到状态，底层 RAG 内核完成真正的数据处理。

离线阶段：论文怎样进入系统

第一次 pqa ask 默认会同步语料目录并建立索引。这可能是整个流程中最耗时、最依赖外部服务的一步。

01扫描目录递归发现 PDF/TXT/HTML/Office
02读取文档按扩展名选择 reader
03推断引用首 1–3 页交给 LLM
04补全元数据DOI、标题、作者、期刊质量
05解析与切块文本、页码、图表和重叠
06向量化可立即或延迟 embedding
07保存双索引Tantivy + 压缩 Docs 对象

Tantivy 中保存什么

file_location、完整正文 body、标题和年份。它用于快速选出“哪几篇论文可能相关”，是关键词/BM25 风格的文档级全文检索。

docs/ 目录保存什么

每篇论文对应一个压缩 pickled Docs 对象，其中包含 DocDetails、所有 Text chunks、媒体对象以及可能已经计算好的 embedding。

Reader 如何选择？
  • PDF：默认 reader 或可选 PyPDF、PyMuPDF、Docling、Nemotron Parse。
  • TXT/HTML/源码：文本 reader，支持按字符数与行切块。
  • DOCX/XLSX/PPTX：Office reader；图表可进入多模态流程。
  • 图像：解析为带媒体内容的 ParsedText。
Manifest 为什么重要？
Manifest CSV 可直接提供 file_location、DOI、标题、引用等元数据，避免逐篇调用 LLM 推断引用并查询在线元数据服务。做 benchmark 时，它还能固定 corpus identity，减少网络波动和错误元数据造成的变量。
索引何时重建？
AgentSettings.rebuild_index 默认是 true。构建时使用文件清单和正文 hash 跳过未变化文件；如果 sync_with_paper_directory 开启，语料目录里消失的文件也会从索引移除。实验时应固定独立的 paper_directory 和 index_directory。
!
常见误区：paper_search 不是联网搜论文

当前默认工具只是搜索已建立的本地 Tantivy 索引。Crossref、Semantic Scholar 等默认用于元数据补全，而不是让 Agent 任意搜索和下载论文。早期 v1 的 paperscraper 在线搜索并没有原样保留到当前默认工具。

在线阶段：一次问题如何跑完

先区分“是否经过 Agent Environment”，再区分 Environment 内使用哪种 runner。Manual Docs API 不属于 run_agent 的一种 Agent。

经过 Agent harness

run_agent() 创建同一个 PaperQAEnvironment，再选择三种 runner 之一。

Aviary ToolSelector默认动态 Agent，根据观察逐步选择工具。
LDP Agent可学习或自定义 policy，复用同一 Environment。
fake确定性工具链，用于基线和组件消融。
绕过 Agent harness

用户直接调用 Docs 的取证与回答方法。

Manual Docs API没有 Agent policy，也没有 Environment 的 complete/timeout 语义。

Aviary ToolSelector：真正的动态多步执行

obs, tools = await env.reset()
while not done:
    action = await agent(messages + obs, tools)
    obs, reward, done, truncated = await env.step(action)
  1. run_agent() 先确保本地语料索引存在。
  2. Environment 清空本轮工作集，创建新的 PQASession 和工具。
  3. Agent LLM 接收问题、当前论文数、证据数、成本以及工具 schema。
  4. LLM 可多次换关键词调用 paper_search，也可一次并行发出多个安全工具调用。
  5. 有论文后调用 gather_evidence；可用原问题，也可用更窄的子问题。
  6. 调用 gen_answer 后，Agent 可以继续搜索和迭代答案，而非强制结束。
  7. 只有调用 complete 才正常结束；它同时声明 Agent 对答案是否确信。

LDP：更换 policy，不更换 PaperQA 数据面

env = PaperQAEnvironment(query, settings, docs)
manager = RolloutManager(agent, callbacks=[...])
trajectories = await manager.sample_trajectories(
    environments=[env],
    max_steps=settings.agent.max_timesteps,
)

LDP runner 使用同一组 Environment、Tools、Docs、RCS 和 PQASession。它改变的是怎样根据历史与观察产生下一步 action，可接入不同 memory 或经过优化的 policy。

因此比较 ToolSelector 与 LDP 时，主要测 Agent policy；只有同时修改 Settings、工具或模型，才把 RAG 变量也带入比较。

fake：没有选择策略的确定性 harness

3 × LLM-proposed search query
→ gather_evidence(original_question)
→ gen_answer()
→ LLM fills complete(has_successful_answer)

“fake”并不意味着不用 LLM：搜索词、证据摘要、最终回答和 complete 参数仍可能由 LLM 产生。它只是没有逐步观察状态并自由选择工具的 Agent policy。

内置 fast.json 使用该模式。因此比较模型时，如果一个实验使用 ToolSelector、另一个使用 fast/fake，比较结果同时包含 harness 差异。

Manual：直接调用 RAG 内核，不使用 Agent

docs = Docs()
await docs.aadd(path, settings=settings)
session = await docs.aget_evidence(question, settings=settings)
session = await docs.aquery(session, settings=settings)

这条路径适合组件消融、固定 corpus QA、调试 reader/embedding/prompt，以及构建自己的 Agent harness。它不会自动改写查询或决定何时再次检索。

i
PaperQA 可以评测“模型”，也可以评测“Agent 系统”

固定 fake/manual 流程、更换 LLM，接近模型能力对比；固定模型、更换 ToolSelector/ReAct/Memory Agent，则是在评测 policy；同时更换模型、prompt、工具和语料，测到的是整个系统。

08

核心算法：两层检索 + RCS

PaperQA 的高成本和高精度都主要来自第三层——它不是只依赖 embedding 分数，而让 LLM 针对问题重新表述并评分每段证据。

LEVEL 0
Agent 查询规划

根据问题与已有状态产生关键词或更窄的取证问题。

LLM policy
LEVEL 1
Tantivy 论文级全文检索

在标题、正文、路径等文本字段上召回整篇论文，默认每次 8 篇。

lexical retrieval
LEVEL 2
Embedding / MMR 片段级检索

在已载入论文的 Text chunks 中选出 top-k；MMR 可抑制重复证据。

dense / hybrid
LEVEL 3
Contextual summarization + relevance scoring

summary LLM 将每个 chunk 压缩成针对问题的 Context，并输出 0–10 相关性分数。

LLM re-rank
LEVEL 4
Context serialization

按分数排序、截断到 answer_max_sources、移除低于阈值的 Context，生成带合法 key 的上下文。

deterministic
LEVEL 5
Grounded answer generation

answer LLM 只能引用本次 context 提供的 pqac-* keys；之后系统清理幻觉 key 并生成 bibliography。

LLM synthesis

为什么先选论文？

避免把整个大型语料库的所有 chunk 都放入内存和向量搜索；Tantivy 便于增量索引、缓存和全文关键词召回。

为什么还要 RCS？

原始 chunk 可能长且夹杂无关信息。RCS 将其转换为“回答当前问题所需的证据”，同时保留数字、公式和直接引语。

为什么成本高？

一次 gather_evidence 会对 top-k chunks 并发发起多个 summary LLM 请求；Agent 又可能多轮搜索和取证。

多模态如何进入这条链？
Reader 将图片、表格或页面截图挂在 Text.media。可选 enrichment LLM 先描述媒体，使描述参与 embedding；RCS 阶段再把原始图像 URL、文本和 Markdown 表格一起发送给 summary LLM。也就是说，视觉内容主要在“检索增强”和“证据形成”阶段进入，而不是把整篇 PDF 无差别塞给最终回答模型。
引用 grounding 能保证什么，不能保证什么？
系统能够限制并清理 citation ID：不存在于 Context 的 ID 会被移除，合法 ID 会映射回文献名和 citation。但它不能程序化证明“每个主张确实被对应 Context 支持”；证据摘要错误、相关性误判和最终模型的语义外推仍可能发生。

三个模型角色与外部服务

默认三种 LLM 角色可以指向同一模型，但实验上最好把它们当成独立变量。

agent_llm

工具选择模型

阅读观察和工具 schema，生成 ToolRequestMessage。决定搜索深度、查询改写、何时回答和结束。

调用次数 ≈ Agent steps
summary_llm

证据形成模型

对每个召回 chunk 生成 Context 和相关性分数；启用多模态时也查看相关图表。

调用次数 ≈ 每轮 evidence_k
llm

回答与辅助模型

生成最终答案；添加无 manifest 文献时也可能推断 citation、标题和 DOI；fake 模式还用它提出搜索词。

调用次数 = 回答 + 元数据辅助

Embedding model

当前默认 text-embedding-3-small；可使用 Sentence Transformers、本地模型、稀疏或 hybrid embedding。它影响片段召回，不直接选择论文级 Tantivy 结果。

Metadata clients

默认顺序为 Crossref、Semantic Scholar、Journal Quality 后处理。OpenAlex、Unpaywall 和 RetractionData 属于可选的 ALL_CLIENTS，并非默认全部调用。

外部能力默认用途它不等于什么

Semantic Scholar元数据、引用数、论文匹配；代码支持更多搜索类型默认 Agent 的网络搜索工具

配置决定“同一个 PaperQA”实际是什么

模型、检索深度、工具、prompt、reader 和 agent_type 都由 Settings 控制。报告结果时仅写“用了 PaperQA”是不充分的。

high_quality

默认高质量

20 个候选证据、最多 5 个回答来源、10 路证据摘要并发、7,000 字符 chunk、启用详细文献元数据。

fast

低成本固定链

5 个证据、3 个来源、短摘要和短答案、不查详细元数据，并把 agent_type 设为 fake。

debug

快速调试

小模型、2 个证据、延迟 embedding、短答案；适合检查链路，不代表论文级性能。

wikicrow

长证据综述

hybrid embedding、25 个证据、最多 12 个来源、约 300 字证据摘要，并使用 Wikipedia 风格回答 prompt。

contracrow

矛盾检测

30 个证据、最多 15 个来源；最终输出从 explicit contradiction 到 explicit agreement 的等级。

clinical_trials

论文 + 试验

显式加入临床试验搜索工具；也有只搜临床试验、不提供 paper_search 的变体。

≡
最小可复现实验配置

至少固定：Git commit、完整 Settings JSON、三个 LLM 角色、embedding、语料 manifest、索引 hash、reader 及版本、agent_type、max_timesteps、timeout、随机种子与并发限制。

失败路径、保护机制与产品边界

PaperQA 有工程化保护，但这些保护可能掩盖 Agent policy 的失败；评测时需要单独统计。

超时或步数耗尽

runner 标为 TRUNCATED。如果尚未调用 gen_answer，harness 会强制生成一次答案。因此“有 final answer”不代表 Agent 正常完成。

Agent 调错工具或输出普通文字

Environment 返回错误观察但不立即终止；ToolSelector malformed message 最多重试 5 次，工具异常可转换成响应交还 Agent。

没有论文或没有证据

gather_evidence 对空 Docs 抛出明确错误；gen_answer 可以懒加载 evidence，仍无 Context 时输出固定的 “I cannot answer...” 句式。

多模态请求失败

可配置只用文本重试 Context 创建；系统会记录 used_images=false，但视觉任务上这可能形成隐性能力降级。

索引构建中断

按文件 hash 和批次提交，可从已有 files.zip 继续；失败文件会标记为 ERROR，避免每次全量重做。

引用幻觉

后处理移除不存在的 context ID；但语义上错误归因仍需 citation correctness evaluator 或人工复核。

≠
开源 PaperQA 包 ≠ Edison Literature / PaperQA3 完整生产系统

开源包提供算法框架、reader、元数据接口、本地索引和 Agent environment；生产产品还可能依赖大规模论文/专利/临床试验索引、授权全文、内部检索服务和不同的现代 reasoning harness。不能用本地包的语料覆盖率推断产品能力，也不能把产品成绩直接当成开源仓库可复现成绩。

建议的源码阅读与实测路线

不要从 1,000 多行的 Settings 或 Types 开始硬读。沿一次真实状态变化阅读最容易建立整体理解。

先看入口和分流agents/__init__.py: ask() → agents/main.py: run_agent()，弄清 fake/Aviary/LDP 三条路径。

追最终引用后处理Docs.aquery() → context_serializer() → PQASession.populate_formatted_answers_and_bib...。

最小实测

用 3–5 篇本地论文建立独立 corpus；开启 verbosity 和 callbacks；保存每一步 observation、tool request、Context、answer 与费用。
