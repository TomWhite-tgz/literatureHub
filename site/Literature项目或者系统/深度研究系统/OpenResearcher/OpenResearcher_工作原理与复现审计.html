01 / POSITION

先建立正确定位：它研究的是“如何训练研究智能体”

OpenResearcher 的核心问题不是怎样写一份漂亮报告，而是：怎样低成本、可复现地获得大量包含搜索、证据检查和多步推理的完整示范。

最准确的一句话：OpenResearcher 是一个“离线深度研究轨迹合成管线”，以及由这些轨迹监督微调得到的开放权重浏览智能体。

研究轨迹

16 个随机种子覆盖约 6.1K 个困难问题，保存模型与浏览器的完整多轮交互。

论文与配置
30B-A3B

智能体模型

总参数约 30B，每个 token 激活约 3B；继承 Nemotron 的长上下文混合架构。

代码确认
3 tools

浏览抽象

search、open、find 对应从全局检索到页面内证据定位。

论文声称
4 suites

评测框架

覆盖 BrowseComp-Plus、BrowseComp、GAIA 和中文 xbench-DeepSearch。

它不是什么

不是文献管理器

没有 Zotero 式条目库、PDF 标注、引用格式化或知识图谱界面。

不是完整科研自动化系统

目标集中在开放网络问答与证据检索，不包含选题、实验、代码执行和论文写作闭环。

不是即装即用的消费产品

仓库主要是研究代码，需要多 GPU、搜索索引和 API 配置；本地没有前端应用。

02 / CONTEXT

Introduction 与相关工作：它争夺的不是“文献问答”，而是长程研究轨迹的生产方法

论文没有把 OpenResearcher 写成一种全新的 Agent 架构，而是先接受“用强模型轨迹监督较小模型”的技术路线，再指出：到了 Deep Research 场景，真正稀缺的是便宜、稳定、足够长、能够分析的浏览轨迹。

Introduction 的论证链条

① 已验证的训练范式DeepSeek-R1-Distill、OpenThoughts、OpenMathReasoning、OpenCodeReasoning 表明：强教师生成长推理轨迹，再用 SFT 训练学生模型是有效路线。
② 新场景更困难Deep Research 不只是 2–5 轮 multi-hop QA；它要持续搜索、检查异构来源、聚合证据，并判断何时可以停止。
③ 瓶颈转向数据模型能力固然重要，但缺少反映真实浏览行为的高质量长轨迹，成为训练研究智能体的核心障碍。
④ 现有生成方式有缺口Search-R1 轨迹偏短；WebExplorer、MiroThinker 等长程方案依赖变化中的在线搜索 API，成本、复现与可控分析都受限。
⑤ OpenResearcher 的回答先一次性在线补齐支持答案的文档，再固定 15M 文档语料和搜索引擎，把反复执行的多轮轨迹合成完全搬到离线环境。

论文真正提出的中心问题：如何以可扩展、低成本、可复现并且适合机制分析的方式，合成高质量、长程的 Deep Research 轨迹？因此它首先是数据生成管线与实验环境，其次才是由这些数据训练出来的 30B-A3B Agent。

相关工作被组织成三条谱系

研究谱系论文提到的代表工作OpenResearcher 如何承接或区分
长推理轨迹与蒸馏 DeepSeek-R1-Distill、OpenThoughts、OpenMathReasoning、OpenCodeReasoning 继承“教师轨迹 + SFT 学生”的基本范式，但把轨迹从数学、代码推理扩展为包含大量浏览器交互的开放网络研究。
Deep Research Agents OpenAI Deep Research、Claude Research、Kimi-Researcher、Grok DeepSearch；Tongyi DeepResearch、MiroThinker、Verl-Tool、AgentFlow、Cognitive Kernel-Pro、DeepMiner 承认这些系统推动了长程工具使用、训练算法、交互扩展和动态记忆；它选择补足多数系统仍依赖实时、专有搜索 API 的数据基础设施问题。
离线环境与合成轨迹 WebArena、Mind2Web、OSWorld；AgentTuning、APIGen-MT 继承固定环境带来的低成本和可复现性，但认为这些环境主要面向短程工具使用、UI 导航或简化 API，缺少大规模非结构化知识语料与几十轮检索条件。

它具体怎样评价相邻工作

轨迹长度

Search-R1

能够训练搜索型推理，但论文认为其典型的 2–5 轮交互距离真实 Deep Research 的几十至上百次工具调用仍然很远。

在线依赖

WebExplorer / MiroThinker

可以产生更长交互，却通常依赖 Google 等实时搜索服务；错误探索也要付费，网页变化还使数据难以复现和逐事件分析。

训练重点

Tongyi / Verl-Tool / AgentFlow 等

这些工作更强调端到端训练、强化学习、交互扩展或记忆机制；OpenResearcher 把创新轴移到轨迹生产环境、语料覆盖和浏览监督。

环境形态

WebArena / Mind2Web / OSWorld

静态环境适合复现实验，但主要模拟网页或操作系统中的动作任务，不等于在 15M 篇非结构化文档上持续寻找事实证据。

数据合成

AgentTuning / APIGen-MT

同样用模拟交互监督开放模型，但论文认为它们更偏短程工具/API 使用，不能直接覆盖长程研究所需的反复检索和证据收敛。

竞争坐标

OpenResearcher

不主张发明 Deep Research，也不主张发明 ReAct；它主张首次把“大语料、长轨迹、低成本、固定环境、全链路开放”组合成一套合成管线。

与 PaperQA / 科研文献检索的边界

PaperQA 的问题空间

面向论文、PDF、文献元数据和可引用证据，目标是基于学术文献回答研究问题或辅助综述，核心对象是科研文献本身。

OpenResearcher 的问题空间

面向一般 Web 文档和搜索行为，目标是制造训练 Deep Research Agent 的完整示范，核心对象是搜索—打开—定位—推理轨迹。

从论文文本得到的直接判断：Introduction 和 Related Work 没有讨论 PaperQA，也没有围绕 scholarly literature、scientific literature、PDF 解析或引用管理建立对比。这不是说二者“毫无关系”——它们都涉及检索、证据和回答——而是二者不处于同一个直接竞争层级：PaperQA 更像领域应用系统，OpenResearcher 更像训练通用浏览 Agent 的数据工厂。

如何看待作者的创新声明

离线、可复现的合成

一次在线建库后，昂贵的搜索与浏览循环在固定环境中运行，能够反复生成和比较轨迹。

显式浏览结构

search、open、find 把候选发现、全文检查和页面内定位拆开，使浏览行为可训练也可诊断。

数据与 Agent 机制分析

固定语料让作者能够研究轨迹过滤、证据覆盖、轮数预算、工具组合，以及“已经找到证据却仍答错”的失败。

阅读时保留一个限定：“第一个完全开源、且可与专有系统竞争的长程 Deep Research 轨迹合成管线”是论文作者的优先权声明。更稳妥的理解是：这项工作的独特组合在于离线大语料 + 100+ 工具调用轨迹 + 完整开放 + 可控诊断，而不是其中任何单个组件此前从未出现。

03 / SYNTHESIS

核心贡献：把昂贵的在线研究循环搬进离线环境

持续调用商业搜索 API 会带来成本、速率限制、网页变化和不可复现性。作者把在线网络只用于一次性补齐证据，之后的大规模轨迹生成全部面对固定语料和固定索引。

① 困难问题从 MiroVerse 随机抽取约 10%，得到约 6,102 个长程、多跳问题。
② 答案清洗把原始答案规范成简洁、可验证的目标答案；不沿用原数据中的轨迹。
③ 一次在线引导用“问题 + 答案”向 Serper 检索，收集约 10K 个支持答案的 gold 文档。
④ 离线语料将 gold 文档与 15M FineWeb 文档合并；前者保证证据存在，后者制造真实干扰。
⑤ 建立索引Qwen3-Embedding-8B 编码文档，FAISS 提供固定、可重复的稠密检索。
⑥ 教师研究GPT-OSS-120B 不看参考答案，只通过三个浏览工具自己找回答案。
⑦ 过滤与 SFT剔除超长、坏工具调用和未收敛轨迹；约 55K 条正确轨迹进入学生模型训练。
论文设计

“离线”不等于从未接触网络

作者先用答案引导的在线检索把相关证据放入语料库。真正离线的是之后 9.7 万次长轨迹生成过程。

论文设计

教师生成时不能看到答案

答案只用于建库和事后判分，不进入教师的研究上下文。否则生成的只是答案条件化的伪搜索轨迹。

方法解释

固定环境分离“搜索失败”与“语料缺失”

先保证证据可检索，再观察模型能否找到它，才能把检索器、搜索策略和推理错误分开分析。

方法解释

不是只保存最终答案

训练信号来自每次查询改写、页面选择、证据定位和停止决策，最终答案只是轨迹的最后一个节点。

材料中的数量口径有冲突：代码 README 把专用语料写为约 11B tokens，论文正文却写成约 10 trillion tokens。15M 文档若有 10T token，平均每篇约 66.7 万 token，明显可疑。页面将“15M 文档”视为稳定口径，不把 token 总量当作已核实事实。

为什么一题要生成 16 次？深度研究的成功取决于早期搜到什么、选择打开什么、何时改写查询。论文报告 Pass@1 为 0.567，Pass@16 为 0.792；同一道题存在大量失败路径，也可能有少数关键成功路径。多采样既增加成功数据，也暴露策略差异。

05 / MODEL

学生模型：用监督学习吸收“如何研究”，不是现场调用教师

最终模型从 NVIDIA Nemotron-3-Nano-30B-A3B-Base-BF16 初始化，在完整、未经截断的工具轨迹上做一次长上下文 SFT。

Architecture

混合 Mamba–Attention–MoE

52 层、隐藏维度 2,688、128 个路由专家，每个 token 选择 6 个专家；模型类型为 nemotron_h。

Context

262,144 token 配置

训练以 256K 最大长度预打包完整轨迹，避免把研究过程截成不连贯的局部片段。

Efficiency

30B 总量，约 3B 激活

MoE 让模型保留较大知识容量，同时每步只激活部分参数；A3B 是激活参数规模，不是总参数。

论文报告的训练配置

项目配置含义
训练数据约 55K 条答案正确轨迹由 97K+ 合成轨迹经过 rejection sampling 得到。
训练框架Megatron-LM训练实现放在外部 openresearcher 分支，不在当前 code 仓库内。
硬件 / 时间8 × H100，约 8 小时这是论文训练配置；代码 README 的运行环境另写为 8 × A100 80GB。
优化347 steps，global batch 64学习率 5e-5，不做学习率衰减。
精度BF16模型配置和权重均采用大模型常用的半精度表示。

训练真正学到的对象：在当前证据不足时继续搜；怎样把模糊问题改写成检索词；从摘要判断哪个链接值得打开；在长页面里定位实体；证据冲突时继续验证；达到足够信心后停止。

06 / RUNTIME

运行时架构：一个最多 200 轮的“模型—浏览器”闭环

推理代码的核心不复杂：每轮把历史消息和工具定义套入 chat template，调用 vLLM 生成；若生成工具调用就执行并回填结果，否则检查是否出现最终答案标记。

OpenResearcher 模型

读取问题、历史思考与证据，决定查询、页面操作或最终回答。

deploy_agent.py

最多
200 轮

BrowserPool

每个 qid 独立保存浏览状态，将模型函数调用映射到 search/open/find。

搜索后端

本地 BM25 / Dense 服务，或 Serper 的 Google 搜索与网页抓取。

⌕

search · 从语料到候选页

返回标题、URL 和摘要。负责扩大覆盖、检验假设、发现可追踪的实体与关系。

失败风险：搜索漂移、重复改写、只看 snippet。
↗

open · 从候选页到全文

打开 URL，提取页面正文并以带行号的浏览视图返回。它把“可能相关”变成“可读证据”。

实验中加入 open 带来最大的性能跃升。
⌁

find · 从全文到证据点

在当前页面中定位精确字符串，适合人名、年份、机构、数字和术语的快速验证。

减少盲目滚动，也降低上下文和工具调用成本。

两种搜索后端的边界

Fixed corpus

本地 BM25 / Dense

BrowseComp-Plus 使用固定语料。BM25 可在 CPU 上运行；Dense 使用 Qwen3-Embedding-8B，文档称额外需要约 15GB GPU 显存。

Live web

Serper 搜索与抓取

BrowseComp、GAIA、xbench 等使用真实网络，需要 SERPER_API_KEY。结果会随时间变化，因此不具备严格的固定环境可复现性。

08 / INSIGHTS

比排行榜更值得保留的五个机制性洞见

Insight 1 · Search efficiency

失败轨迹搜得更多，而不是更少

正确轨迹平均 38.4 次工具调用，错误轨迹达到 71.7 次；差异主要来自 search（22.1 vs. 48.8）。瓶颈是查询质量和搜索漂移，不是简单增加预算。

Insight 2 · Evidence access

搜到 gold 文档不等于真正使用证据

已在结果里命中 gold 时，答对概率为 61.84%；明确打开 gold 文档后升至 86.72%。检索 recall 与证据消费必须分开测量。

Insight 3 · Tool structure

open 是最大跃升，find 继续提高效率

search-only 准确率 43.86%；加入 open 后 56.39%；三工具齐全达到 62.17%，同时平均调用和 token 使用都下降。

Insight 4 · Trajectory value

错误轨迹也携带强监督信号

正确轨迹、错误轨迹、全部轨迹分别训练得到 54.81%、55.06%、54.46%，差距不到 0.6 点。工具顺序和证据交互本身可能比最终标签更重要。

Insight 5 · Corpus coverage

没有证据覆盖，再强的教师也教不出搜索能力

移除一次性 gold 文档引导后，gold hit 从 29.54% 降到 1.73%，下游 BrowseComp-Plus 从 54.81% 崩到 6.35%。环境质量是训练数据质量的前置条件。

Insight 6 · Horizon

长程有用，但约 100 轮后收益递减

准确率和 gold hit 随最大轮次持续提升，但超过约 100 轮后趋于平台。系统需要足够探索空间，也需要更好的停止与重规划机制。

对其他科研智能体最直接的启示：不要只记录“最终答对没有”。至少应同时记录候选证据是否被召回、是否被打开、首次命中时间、查询重写次数、页面内定位、证据冲突和停止原因。否则无法知道系统究竟坏在检索、浏览还是推理。

把整项工作压缩成四句话

  • 深度研究模型需要学习完整的搜索过程，而不只是问题和答案。
  • 用一次在线引导保证证据覆盖，再在固定离线语料中反复采样，可以低成本生成可复现长轨迹。
  • search → open → find 的显式浏览层级，以及真正打开 gold 证据，是性能提升的关键。
  • 这批轨迹让 30B-A3B 基础模型在 BrowseComp-Plus 从 20.8% 提升到 54.8%，但完整复现仍需要较重硬件与未包含在本地的资产。

建议怎样利用这份归档

第一优先：把数据作为研究对象

统计成功/失败路径、查询改写、证据打开顺序、首次命中时间与停止行为。这 7GB 数据比单纯运行模型更适合当前 Literature 系统横向研究。

第二优先：抽取通用 Agent 设计

复用三层浏览工具、独立会话、固定 corpus 评测和 evidence exposure 指标，把它们迁移到你的 Literature Agent 基准框架。

第三优先：再决定是否补齐模型

如果只是理解方法或做数据分析，没有必要立刻承担数十 GB 下载和多 GPU 部署成本；需要端到端对比时再续传。

不要直接当作完整科研 Agent

它擅长开放网络事实查找，不等同于领域文献综述、PDF 图表解析、实验设计或可引用的学术写作系统。
