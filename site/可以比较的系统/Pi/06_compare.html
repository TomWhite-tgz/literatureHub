⑥ Pi 的优点与 AutoResearch 借鉴

先明确 Pi 用小内核取得的独特优势，再比较其他 coding agent，并把成熟机制与尚在施工的设计分开映射到 AutoResearch。

一句话定位

Pi：最小、可嵌入、可扩展的 TypeScript coding-agent 栈，经典运行时成熟，新 durable runtime 尚在施工。
Codex：事件协议和执行治理最硬，app-server 与 OS sandbox 边界最完整。
Claude Code：单个长会话内部的流式工具、权限竞态、多级上下文和后台 agent 最丰富。
AutoResearch：应以证据可恢复为中心，吸收三者机制而不复制三套产品复杂度。

Pi 最突出的五个优点

  1. 内核小且可嵌入。Agent + agentLoop 只负责 turn、tool 与队列，SDK、TUI 和宿主应用复用同一主链，便于把研究领域语义放在内核之外。
  2. 物理并行与上下文确定性分离。工具可并行完成并及时发出事件，但 tool result 仍按模型调用顺序进入上下文，兼顾延迟和可复现推理输入。
  3. provider 消息与业务消息分层。内部消息先保留业务语义，再投影到不同模型 API，适合 AutoResearch 长期更换模型而不重写 durable history。
  4. 会话树天然表达分支。append-only JSONL、parent pointer、branch summary 与 retained tail 让探索分叉和压缩成为一等数据，而不是覆盖旧对话。
  5. 扩展面自由且前端复用度高。工具、hook、命令、UI、provider 均可扩展；SDK、TUI、JSON/RPC 可围绕小内核组合。代价是任意进程内扩展扩大信任面，需要另补治理。

Pi 修正了前两轮比较中的一个盲点

Codex 与 Claude Code 都容易让人以为“成熟 agent 必须先有重型 server 或复杂 swarm”。Pi 证明另一条路径可行：先把 provider/message/tool loop 做成小而稳定的库，让 SDK、TUI 与扩展直接复用；等真正需要跨进程 ownership 和 crash recovery 时，再引入 durable session/server。

但 Pi 同时给出反例：如果下一代协议面一次性设计 lanes、hooks、watch、manual drive、deferred provider、compaction/navigation 和三种 backend，而执行主链尚未落地，就会产生“类型看起来完成、能力其实 unavailable”的落差。

建议的最小数据模型

ResearchRun(run_id, parent_run_id, status, seq)
RunEvent(event_id, run_id, parent_id, kind, actor, timestamp)
ActionAttempt(action_id, ordinal, tool, input_hash, replay_policy,
              started_event, result_event, artifact_refs, error_class)
ContextCheckpoint(summary, retained_event_ids, artifact_refs,
                  open_hypotheses, task_refs, token_stats)
PolicyDecision(action_id, source, rule_id, decision, sandbox_profile)
ResearchTask(task_id, parent_run, lane, owner, state, transcript_ref)
EvidenceArtifact(hash, media_type, provenance, environment_digest)

实现顺序

  1. 先稳定单 run 的 append-only event、tool pairing 和 content-addressed artifact。
  2. 加入 context projector，让 event truth 与模型可见 context 分离。
  3. 在每个外部 effect 前持久化 intent；用 manual gate 做 crash-prefix 测试。
  4. 加入 checkpoint/branch，但原始 evidence 永不被摘要覆盖。
  5. 只实现一个 background task/lane 和一个 container backend，验证恢复后再扩展。
  6. 最后才引入远程 protocol、多 lease 与更多 UI adapter。

不该照搬

  • 不把 Pi Harness 规范中的未实现 API 当作现成依赖。
  • 不采用 Pi 默认的“进程权限即工具权限”作为科研执行边界。
  • 不一开始复制 Claude Code 的完整 swarm/backend 矩阵。
  • 不因 Codex app-server 很完整，就在只有单 UI 时预付全部版本兼容成本。
  • 不把 compaction summary 当证据；结论必须回指代码、数据、参数、环境和原始输出。
最终判断：三者的最佳交集不是“更多 agent”，而是：Pi 的小 loop 与显式投影、Codex 的硬事件/执行边界、Claude Code 的长程 context/task 恢复，再加科研系统独有的 evidence 与 environment provenance。
