① 经典 Agent loop：小，但不含糊

Agent 管状态与生命周期，agentLoop 管一次 run；两者故意保持可替换。

调用链

AgentSession.prompt→Agent.prompt→agentLoop→streamAssistantResponse→executeToolCalls↺

agentLoop() 从新 prompt 开始，agentLoopContinue() 从已有 context 继续。两者汇入 runAgentLoop()，依次发出 agent/turn/message 事件，再进入 runLoop()。外层循环消费 follow-up，内层循环处理 tool calls 和 steering。

证据：packages/agent/src/agent-loop.ts:31-279；packages/agent/src/agent.ts:173-430。

一个 turn 的真实顺序

user/pending messages
  → turn_start
  → assistant message stream（完整收束）
  → message_end
  → 若 stopReason=error/aborted：结束
  → 若 length 且含 tool call：生成失败结果，不执行截断参数
  → tool batch prepare / execute / finalize
  → toolResult messages 按模型调用顺序写回
  → turn_end
  → steering? 下一次模型调用
  → 无工具、无 steering 时再取 follow-up

Pi 与 Claude Code 的重要差异在这里：经典 Pi 会先把整个 assistant response 流完，再启动工具；它没有在 tool input streaming 尚未结束时抢跑工具。好处是状态机简单、参数边界清楚，代价是不能隐藏安全工具的模型流延迟。

steer 与 follow-up 不是同一队列

队列可见时机作用
steer当前 assistant turn 及其整个 tool batch 完成后在下一次 LLM 调用前改变方向；不会中途取消正在执行的 sibling tools
followUp没有 tool continuation，也没有 steering 后把新任务作为下一段对话处理

prompt() 在 active run 中会拒绝，并明确要求调用方选择 steer() 或 followUp()。这避免了“新 prompt 到底插在 transcript 哪一层”的隐式竞态。

证据：packages/agent/src/agent-loop.ts:155-269；packages/agent/src/agent.ts:283-320,348-353。

EventStream 与 Agent 的语义不同

低层 loop 返回 EventStream，适合边读边消费；高层 Agent 则把 listener 逐个 await。于是 agent_end 是最后一个 loop event，但只有它的 listeners 全部 settle 后，Agent 才真正 idle。这是一个容易忽视但很实用的 barrier：会话持久化 listener 可以在下一次 prompt 前完成。

设计价值：事件不是只给 UI 看。高层 Agent 把它用作状态更新与持久化的同步边界；低层 loop 则保持可组合和观察式消费。两个 API 没有假装具有同样的 settlement 语义。
证据：packages/agent/src/agent.ts:247-252,326-331,540-592。

失败也必须闭合协议

  • provider error/abort 生成终态 assistant message 并结束 turn。
  • length 截断且出现 tool call 时，所有 call 都得到错误 tool result，绝不执行可能残缺的参数。
  • 工具 schema、hook 或执行异常被捕获并转成 isError result，保证每个 tool use 有配对结果。
  • terminate: true 可以阻止自动 tool continuation；并行 batch 只有所有 finalized results 都 terminate 才停止。
判断：Pi loop 的核心质量来自少量明确不变量，而不是庞大调度器：一次只跑一个 Agent run；assistant 先收束；每个 tool call 必须闭合；队列只在规定 checkpoint 可见；事件处理完成才算 idle。
