先说结论

Gemini CLI 的架构重心不是一个孤立的 while-loop，而是三层协作：GeminiClient/Turn 把模型流翻译成稳定事件，Core Scheduler 把工具调用推进为可确认、可并行、可取消的状态机，CLI 或 LegacyAgentProtocol 再把完成的 function responses 回注模型。它正在迁往统一的 AgentProtocol/AgentSession 消费面，但默认路径仍保留既有 loop，因此当前源码应按“成熟内核 + 迁移适配层”来读。

一句话架构：gemini.tsx 完成配置、认证与可选 sandbox 再执行；交互 TUI、非交互 CLI、ACP、SDK 和 A2A 各自适配 Core；Core 内部以 GeminiChat → Turn → GeminiClient → Scheduler 形成 reasoning/action 主链，MessageBus、PolicyEngine、HookSystem、ChatRecordingService 与 ContextManager 横切其上。

包切分与真实重心

包/区域职责架构判断
packages/cli启动、设置、认证、Ink UI、noninteractive、ACP、slash command不只是薄 UI：默认交互 loop 的回注编排仍在 React hook 内
packages/core模型 client、Turn、Scheduler、tools、policy、sandbox、context、sessions、agents、MCP、hooks主要可嵌入运行时；Config 同时是依赖容器和 feature/capability 汇合点
packages/sdk程序化 session API、Zod tools、dynamic instructions基于 Core client/Scheduler 自建薄 loop；不经 AgentSession，安全默认也不同于 CLI
packages/a2a-serverHTTP/A2A 服务、任务与持久化服务化适配器，不是所有 CLI 前端都必须经过的中心 server
packages/vscode-ide-companionIDE 上下文与 diff/command 互操作编辑器状态通过专用连接进入 CLI，GeminiClient 发送 full/delta context
packages/devtools开发期活动流与调试可视化观测通道，与生产 agent loop 解耦

          │
          ▼
GeminiClient.sendMessageStream
  → processTurn → model routing / context management / loop detection
  → Turn.run → GeminiChat.sendMessageStream
  → Content | Thought | ToolCallRequest | Finished | Error ...
          │
          ▼
Core Scheduler
  validating → policy/hook → awaiting_approval → scheduled
  → executing → success/error/cancelled
          │
          ▼
functionResponse parts → same prompt_id continuation → next model turn
  → no pending tool call / stop / abort / max turn / invalid stream → end
