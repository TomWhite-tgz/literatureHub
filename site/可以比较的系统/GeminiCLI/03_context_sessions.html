③ 上下文与会话：三份历史，而不是一份 messages

持久 transcript 是事实来源，工作图负责变换，API history 是一次请求的投影；另有 checkpoint 负责文件世界。理解这些边界，才能解释压缩、恢复和 rewind。

Legacy 压缩：先截工具输出，再做两次模型调用

默认触发阈值是模型 context limit 的 50%，目标是保留最新约 30%。切分点只选在不含 functionResponse 的 user turn，避免把 function call 与 response 拆开；若最后一条是无 function call 的 model turn，才允许把全部历史压缩。

PreCompress hook→检查阈值→反向分配 50k tool-response 预算→选择合法 split→摘要 LLM→验证/补漏 LLM→token 复核

工具响应从新到旧分预算；超限结果截断，并把原文保存到 project temp。摘要 prompt 会带上既有 <state_snapshot>，再由第二次模型调用审阅第一版、补回遗漏。空摘要直接失败；新 history 若反而比旧 history token 更多，也拒绝替换。一次自动摘要膨胀失败后，后续只做 truncation，避免每轮重复烧两次请求。

成功后 client 以 summary user turn + model acknowledgement + 未压缩尾部重启 chat，同时强制下一轮刷新 IDE context；仅发生工具截断时则原地 setHistory。

新 ContextManager：working buffer 是可追踪的变换图

具体 node 与一个 Gemini Part 一一对应，类型包括 USER_PROMPT、SYSTEM_EVENT、AGENT_THOUGHT、TOOL_EXECUTION、MASKED_TOOL、AGENT_YIELD、SNAPSHOT、ROLLING_SUMMARY。每个 node 有稳定 id/turnId；派生节点用 replacesId 或 abstractsIds 指回来源。这比“直接改 messages 数组”多出一层 provenance。

一次 renderHistory() 的顺序很严格：

  1. 从 durable AgentChatHistory 同步 pristine/active graph。
  2. 把本轮 pending request 映射为 ephemeral nodes，先跑 new_message 同步 pipeline。
  3. 首次请求用 countTokens 校准估算；压力过线时等待正在运行的 async pipeline。
  4. 评估 retained/max budget、节点年龄与 coalescing/hysteresis，触发对应 pipeline。
  5. 渲染 header、受保护节点和 late-bound 内容。
  6. 只把 master graph 的 durable 变换同步回 chat；ephemeral request 不落入历史。
  7. 执行 role/tool pairing hardening，再拆成历史与本轮 request。
packages/core/src/context/contextManager.ts:78-275, 307-492；packages/core/src/context/graph/types.ts:14-122

Pipeline：同步先决定本轮，异步只准备未来

Orchestrator 对 sync processors 顺序执行，processor 异常只记录，不让整个请求崩溃；随后按 pipeline key 调度异步工作。相同 async pipeline 有 mutex/coalescing，运行时重新读取最新 nodes。若 token pressure 逼近上限，下一次 render 会通过 barrier 等所有 pending pipeline settled，确保后台整理不会与紧急请求竞态。

generalist profile 的默认数字很有信息量：retained budget 65k、max 150k、coalescing 5k；新消息到达时可对超过 8k 的 tool output 做 masking、超过 15k 的 node 做 distillation；retained 超限时对 3k 以上节点再 distill，并把单节点限制到 4k；aged-out/GC snapshot 最多约 4k、5 turns。这里的预算是 profile 策略，不等于模型固定 context window。

packages/core/src/context/pipeline/orchestrator.ts:18-227；packages/core/src/context/config/profiles.ts:66-169

保护与 hardening：压缩不能破坏协议

环境首轮、最近窗口与 active task 相关节点会被标记 protected。变换结束后，hardenHistory() 再做协议修复：保证合法起止 role、user/model 交替、function call/response 成对；缺失 response 或 call 会注入 sentinel，响应按模型 call 顺序重排，必要时补 continuation turn。最后 scrub ContextManager 的自定义字段，避免内部 metadata 泄漏到 API。

这不是为了伪造成功结果，而是保证被压缩、恢复或旧版本生成的 history 仍满足 Gemini API 的结构约束。sentinel 内容明确表示缺失/跳过，模型仍能看到异常语义。

会话格式：JSONL 追加日志，加载时归并成当前视图

主会话文件名含 timestamp 与 session id；subagent 会话放在父 session 专属目录。第一条是 metadata，后续是 message 或控制记录。写入使用同步 append，崩溃最多留下坏尾行；loader 逐行解析并跳过单行错误，也支持旧版 whole-JSON fallback。

{ "sessionId": "…", "projectHash": "…", "startTime": "…" }
{ "id": "m1", "type": "user", "content": […] }
{ "id": "m2", "type": "gemini", "content": […], "toolCalls": […] }
{ "$set": { "summary": "…" } }
{ "$rewindTo": "m2" }

loader 用 message id 的 Map 归并：同 id 的后写记录替换先前内容但保持原位置。$set.messages 是全量 checkpoint，清空后重建 messages；普通 $set 合并 metadata；$rewindTo 删除目标消息及之后的逻辑视图。rewind 只追加控制事件，不物理截断原文件。

ContextManager mask/summary 后，updateMessagesFromHistory() 会同步 message content 与 tool result；若有变化，通过 $set 写入新的 messages checkpoint。因此恢复看到的是最新逻辑历史，而 JSONL 仍保留此前事件。

Resume 是投影重建，不是反序列化一个 chat 对象

恢复时，转换器忽略 info/error/warning 与内部 slash、session-context、hook-context 消息。现代 gemini record 的 content 是事实来源；旧 record 缺内容时才从 thoughts/toolCalls 重构，并把 tool results 生成为相邻 user function-response turn。ensureStableToolIds() 给旧调用确定性补 ID，并在相邻轮次配对。

GeminiChat 优先接受显式 history，否则从 recording resume；每次 send 由 promise 链串行化。普通用户内容和 function responses 都进入 durable recording。getHistoryTurns() 可返回 curated 或 comprehensive 视图；setHistory() 同时回写 recording，使内存变换和下次恢复保持一致。

Rewind 与 checkpoint 是两件事

Session rewindTool checkpoint restore
恢复对象对话 messages 的逻辑前缀client/UI history + Git 工作区快照
持久方式追加 $rewindTocheckpoint JSON 指向 shadow Git commit
文件回滚本身不保证调用 Git service restore snapshot
覆盖范围任意已记录消息开启 checkpointing 且工具 invocation 可恢复时

创建 checkpoint 时保存 restorable tool 的 name/args、messageId、client/UI history 与 Git snapshot；若 snapshot 创建失败可记录当前 commit。restore 会分别恢复 histories 和 Git snapshot，commit 不存在则明确报错。因此“倒回聊天”不应被描述成通用事务回滚，checkpoint 也不是所有副作用的 durable transaction log。

本章结论

  • 默认上下文治理仍是线性 summary + tool truncation；图式 ContextManager 的设计更先进，但必须标注 experimental/default-off。
  • 新路径把 durable history、变换图和 API projection 分离，并用 lineage、保护集、压力 barrier 与 hardening 控制一致性。
  • JSONL 是可恢复的追加日志：重复 ID、$set、$rewindTo 在加载时折叠为当前会话。
  • session resume 恢复模型语义；checkpoint restore 才尝试恢复文件世界。两者都不是跨任意外部工具的事务。
