⑥ Gemini CLI 的优点与 AutoResearch 借鉴

Gemini CLI 最值得学的不是某个 prompt，而是 policy/Scheduler 的结构化治理、协议适配广度和正在形成的统一事件/上下文中间层。

先给结论：它在哪些轴上最强

架构轴Gemini CLI相对位置
工具治理分层 first-match policy + safety checker + confirmation + native sandbox expansion四者中最显式、最可归因
协议/产品面TUI、headless、ACP、SDK、A2A server、IDE MCP最广，但编排尚未完全统一
并行工具连续 wave、全组 ready barrier、确定性 response order一致性设计优秀；没有 Claude 的流式 latency hiding
上下文成熟 legacy summary + default-off 图式 pipeline新设计有潜力，当前成熟度落后于接口野心
会话线性 JSONL 追加日志 + current-view controls恢复实用；分支/operation durability 弱于 Pi/Claude
子 Agent声明式 local/A2A、一层并行 fan-out隔离清楚；缺 durable background/fork/worktree/team
扩展声明式能力包，分接 MCP/hooks/skills/policy/agents/themes安全可治理；不如 Pi runtime extension 灵活

Loop：Gemini 更确定，Claude 更会隐藏延迟

采样与工具重叠并发判定结果顺序

Gemini 的全组 ready barrier 是独到优点：A 已获准也不会在 B 仍弹确认时提前执行。代价是即使模型早已完整吐出第一个昂贵工具，也不能和后续 token 生成重叠。AutoResearch 的训练/下载/评测常耗时很长，可以组合两者：tool call block 完整后预验证，整组 admission 决定后按资源 wave 启动；模型上下文仍按稳定 action sequence 回收结果。

Gemini：packages/core/src/scheduler/scheduler.ts:303-353, 429-578；对照：Claude Code ①、Codex ①、Pi ①

Policy：Gemini 把“为什么允许”提升成数据

Codex 很清楚地区分 execpolicy 与 permission profile，Claude Code 区分 permission rules 与 sandbox enforcement；Gemini 再前进一步，把 default/extension/workspace/user/admin 映射到数值 tier，rule decision 带 source，之后还串 shell structural analysis 与 prioritized safety checkers。拒绝不是模糊的“不安全”，而是可定位到某条规则/来源。

尤其值得借鉴的三个点：

  • 最高优先级第一条命中，不用多规则投票制造难以解释的组合结果。
  • checker 只能收紧，扩展检查器不能把 admin deny 翻成 allow。
  • 权限失败可扩权重试，先以最小 sandbox 运行，根据真实 denial 精确请求 path/network capability。

AutoResearch 应把同一模型扩展到 GPU、数据许可证、外网域名、API 预算和实验队列：admission decision 说明实验应不应该做，capability lease 才决定 worker 实际能使用什么；二者都要有 source/provenance。

Gemini：packages/core/src/policy/policy-engine.ts:198-260, 555-759；packages/core/src/scheduler/scheduler.ts:836-938；对照：Codex ②、Claude Code ②

Gemini 新 ContextManager 最重要的思想是把“持久事实、变换图、API projection”拆开；Claude 的优势是减重层级已进入主路径；Pi 的优势是 branch/compaction 从 session schema 就可表达；Codex 的优势是压缩后再注入关键环境。最合适的研究系统应四者合并：

durable research journal
  → current branch / experiment lane projection
  → lineage-preserving reducers (mask/distill/snapshot)
  → re-inject active objective, dataset/model contracts, budget
  → provider-specific API history hardening
不要复制 Gemini 的迁移状态：同一系统长期保留 legacy compression 与 default-off pipeline，会让测试矩阵、恢复语义和前端行为翻倍。AutoResearch 应先定义 canonical context IR，再让旧入口成为短期 adapter，并设删除条件。
Gemini：packages/core/src/context/contextManager.ts:78-492；对照：Claude Code ③、Pi ③、Codex ①

Session durability：Gemini 可恢复聊天，不等于可恢复 operation

Gemini JSONL 对坏行容忍、重复 ID 覆盖、$set.messages checkpoint 和 $rewindTo 都很实用；但它的主结构仍是线性 messages current view，没有 parent/leaf 分支，也没有“tool intent 已 durable、effect 尚未发生”的 operation record。remote A2A context/task ID 甚至只在 static Map 中。

Pi 当前 v3 的 append-only tree 比 Gemini 更适合分叉探索；Pi Harness v2 设计又明确 lane、operation、intent-before-effect 和 replay declaration，不过 operation engine 仍未落地。Claude Code 的 UUID parent graph、sidechain/background metadata 和 worktree resume 更接近可恢复多 Agent；Codex rollout journal 则适合审计单线执行。

AutoResearch 的事实底座不能只是聊天记录。一次训练或评测在进程死掉后，必须能区分 never started、running/unknown、committed result、safe-to-replay；会话文本只负责给模型解释，operation journal 才负责恢复。
Gemini：packages/core/src/services/chatRecordingService.ts:133-400, 927-1019；对照：Pi ⑤、Claude Code ⑤、Codex ⑥

Frontends：Gemini 证明了 adapter strategy，也暴露了 drift 风险

ACP、SDK、A2A、IDE MCP 的覆盖非常有价值：同一套能力能进入终端、编辑器、程序和远程 task protocol。AgentSession 的 AgentEvent 正在成为统一事件面，这个方向应当借鉴。

但源码同时给出反例：TUI hook、headless、ACP、SDK、A2A 各自有 loop；ACP 甚至不走中央 Scheduler。共享 Tool 类型并不足以保证共享语义。每新增入口都可能在“并行、policy、hook、取消、token usage、session commit”中漏掉一项。

建议：AutoResearch 只保留一个 headless runtime：accept operation → emit canonical events → wait effects/approval → commit。TUI、Web、CLI JSONL、Python SDK、A2A 都只做 protocol adapter，不各写 while loop。可用 Gemini AgentSession 的迁移方向作正例，用 ACP drift 作测试反例。

Extensions：声明式 bundle 比任意代码注入更可治理

Gemini extension 把 MCP、policy、hooks、skills、agents、context 和 themes 分别交给专门 loader，每种能力仍经过 trust/consent/admin control。Pi runtime extension 能拦截和注册更多内核行为，开发体验更自由，但同样扩大 in-process trust surface。对研究平台，默认应选 Gemini 式声明能力：

  • 数据源/评测器/外部服务：MCP 或 typed service connector；
  • 研究策略：lazy skill + version/hash；
  • 实验准入：分层 policy；
  • 生命周期集成：typed hook，默认外进程、timeout、结构化 stdin/stdout；
  • 专门角色：declarative agent definition；
  • 只有核心算法插件经过签名/管理员安装后才允许进程内代码。
Gemini：packages/cli/src/config/extension-manager.ts:678-987；对照：Pi ④

哪些东西不应照搬

  • 不要复制多套 loop。入口短期并存可以，不能让 TUI/ACP/SDK 各自永久定义执行语义。
  • 不要把 default-off 新架构写成能力完成。ContextManager/AgentSession 的接口很漂亮，生产证据仍是默认开关和实际调用链。
  • 不要用 chat rewind 代替实验回滚。训练、下载、外部 API 与发布需要各自补偿/幂等协议。
  • 不要用进程内 Map 保存远程 task continuity。contextId/taskId 必须进入 operation state，并关联 endpoint/auth identity。
  • 不要默认所有 SDK tool 都可信。Gemini SDK 的 default ALLOW 适用于受信任宿主库，不适合加载第三方研究插件。
  • 不要混淆 policy 与 sandbox。“系统认为可做”和“操作系统实际限制”必须分别验证。

最终判断

Gemini CLI 是一个能力面极宽、治理层很成熟、运行时统一化正在进行的系统。Scheduler/PolicyEngine/SandboxManager 的分工、局部 agent registries、A2A task approval、IDE MCP 和声明式 extension bundle 都值得直接研究；ContextManager 与 AgentSession 更适合作为方向性参考，而不是已验证完成品。

对 AutoResearch，最有价值的组合不是“做一个 Gemini CLI for research”，而是：Gemini 的可归因治理 + Claude 的流式/后台生命周期 + Pi 的分支与 durable operation 设计 + Codex 的执行隔离与副作用证据。先把 operation journal 和 capability enforcement 建牢，再谈更聪明的多 Agent。
