③ 接入层：app-server · mcp-server · tui

TUI、IDE、非交互 exec 的主路径由 app-server JSON-RPC 统一；MCP server 则是另一条把 Codex 能力向外适配的边界。本篇同时解释两者，避免把它们混成同一种 client。

本篇主线

对 TUI、exec、IDE/daemon 这条主产品路径，Codex 的"多前端"不是 if-else 分支，而是一个 server + 多种 transport + 多种 client。但 MCP server 等独立适配器仍可直接依赖 core，所以 app-server 是主要公共接入边界，不是全仓库唯一能持有 CodexThread 的模块。

一、app-server：JSON-RPC 会话托管

app-server 是整个接入层的枢纽。它把 CodexThread（agent 内核）包装成可远程调用的服务。

1.1 它是什么

app-server 是一个 JSON-RPC server，接受 codex_app_server_protocol::ClientRequest，委托给一族 request processor，processor 再驱动 codex_core::CodexThread。三种 transport：

transport用途入口
stdioIDE 扩展（VS Code）通过子进程 stdio 通信AppServerTransport::Stdio
websocket远程 daemon / cloud 连接acceptor in transport.rs
in-processTUI / exec 在同一进程内跑 server（mpsc channel）in_process.rs:355 start()

默认 AppServerTransport::Stdio，真正启动在 run_main_with_transport_options（lib.rs:456）：构建 Config，启动 transport acceptor，spawn outbound router，构造 MessageProcessor。

2in_process::start（in_process.rs:355）

1.3 消息分发

3MessageProcessor（message_processor.rs:101）

struct MessageProcessor { thread_manager: Arc<ThreadManager>, thread_request_processor, turn_request_processor, ... }

app-server/src/message_processor.rs:101

MessageProcessor 持有约 20 个 processor。核心：ThreadManager（Arc::new_cyclic，message_processor.rs:271）—— 所有 CodexThread 的生命周期管理者。请求流：

process_client_request(req)
  → match req {
      ClientRequest::ThreadStart(params) → thread_request_processor.thread_start(params)
      ClientRequest::TurnStart(params)   → turn_request_processor.turn_start(params)
      ClientRequest::ReviewStart(params) → turn_request_processor.review_start(params)
      ClientRequest::ThreadInterrupt(...) → ...
      ...
    }
  → ThreadManager 启动 / 驱动 CodexThread
  → outbound router 把 Event 流推回 client

1.4 三类核心请求

4thread_start（thread_processor.rs）

app-server/src/request_processors/thread_processor.rs

ClientRequest::ThreadStart(ThreadStartParams) 创建一个新的会话线程。processor 调 thread_manager.start_thread(...)，后者构造 Session + CodexThread，返回 ThreadStartResponse（含 thread_id）。

5turn_start（turn_processor.rs）

app-server/src/request_processors/turn_processor.rs

ClientRequest::TurnStart(TurnStartParams) 在已有线程上发起一轮对话。这会触发 core 里的 run_turn（见 ①）。响应 TurnStartResponse 里含 turn_id，客户端用它过滤后续 notification。

6review_start（turn_processor.rs）

app-server/src/request_processors/turn_processor.rs

ClientRequest::ReviewStart(ReviewStartParams) 是 codex exec --review 的后端。它不走正常 turn 流程，而是做 PR 评审：拉取 diff、让模型按 review 专用 prompt 分析、输出结构化评审意见。

1.5 通知回流

agent 内核发出的 Event 不会自动到达 client。app-server 有一个 thread lifecycle listener task，把 core 的 Event 转成 ServerNotification，经 outbound router 推给所有订阅该 thread 的 connection。

三种出站消息 ServerNotification（单向通知，如 token delta、tool call 开始）
ServerRequest（需要 client 回应，如 AskForApproval、Elicitation）
RPC response（对应某个 ClientRequest 的结果）

二、exec：非交互前端的薄壳

codex-exec（5.5 千行）是最薄的前端：它不做 UI，只把 prompt 喂进 app-server，把 Event 流转成人类可读或 JSONL 输出。

2.1 入口与启动

7run_main（exec/src/lib.rs:239）

exec/src/lib.rs:239

main.rs:31 用 arg0_dispatch_or_else 处理 argv[0] 分发（同一二进制可充当 codex-linux-sandbox）。run_main 做的事：

  • 设 originator、解析颜色、装 tracing subscriber + OTEL layer。
  • 找 CODEX_HOME，加载 bootstrap config，解析 OSS provider/model。
  • 构建 Config，headless 默认 approval_policy: Never（非交互模式不等待审批）。
  • 初始化 state DB、OTEL、EnvironmentManager，构造 InProcessClientStartArgs，调 run_exec_session。

8run_exec_session（exec/src/lib.rs:646）

// 主循环：tokio::select! { Ctrl-C / client.next_event() }

exec/src/lib.rs:646

核心循环在 lib.rs:932-1024，是一个 tokio::select!：

  • Ctrl-C → 发 TurnInterrupt，优雅停止。
  • client.next_event() → 拿到 InProcessServerEvent，分三类：
    ServerRequest → handle_server_request（lib.rs:1646）：headless 模式下自动拒绝所有审批/elicitation 请求；
    ServerNotification → 过滤 thread/turn（should_process_notification，lib.rs:1259），交给 EventProcessor；
    Lagged → 告警。

结束时：thread/unsubscribe、break、client.shutdown()、print_final_output()；如果见过 fatal error 就 exit(1)。

2.2 两种输出处理器

9EventProcessor trait + 两个实现

trait EventProcessor { print_config_summary(); process_server_notification(); process_warning(); print_final_output(); }

exec/src/event_processor.rs:13；event_processor_with_human_output.rs；event_processor_with_jsonl_output.rs

--json 模式用 EventProcessorWithJsonOutput，把每个 ServerNotification 序列化成 JSONL 一行；否则用 EventProcessorWithHumanOutput，用 owo-colors 着色，把 agent 的文本输出直接打到 stdout。这是 codex-exec 能被脚本 | jq 消费的原因。

三、mcp-server：把 Codex 暴露成 MCP 工具

这一层方向反过来：前面是 Codex 作为 MCP 客户端消费外部 server；这里是 Codex 作为 MCP 服务端，让自己被别的 MCP 客户端（比如 Claude Desktop、Cursor）调用。

10mcp-server（3.0 千行）

mcp-server/src/lib.rs、main.rs

mcp-server crate 暴露的是一个 MCP server，它把 Codex 的会话能力封装成 MCP tools/resources 暴露给外部 MCP 客户端。入口是 fn main()（启动 stdio MCP server）。它内部驱动 CodexThread，把 agent 的输出转成 MCP 响应格式。

★ 对称的双向 MCP Codex 对 MCP 是双向的：
方向 A：agent loop 里的 McpManager（core）作为 MCP client，连接外部 MCP server，把它们的工具暴露给模型。
方向 B：mcp-server crate 作为 MCP server，让 Codex 自己变成一个可被外部调用的工具源。
这种对称性让 Codex 既能"用别人的工具"，也能"被别人当工具用"。

四、tui：24 万行的终端前端

TUI 是 repo 里最大的 crate（411 文件，24.2 万行）。它不直接碰 CodexThread，而是通过 app-server-client 走 JSON-RPC 协议接入 app-server——和 IDE 扩展走的是同一条路。

4.2 事件循环

11App::run（app.rs:774）—— 四路 select

tui/src/app.rs:774；事件循环 app.rs:1197

App::run 内部是一个 tokio::select!（app.rs:1197），监听四路事件源：

  • app_event_rx —— 内部 AppEvent 总线（app_event.rs:189），由 widget 通过 AppEventSender 投递。
  • active_thread_rx —— 当前活跃线程的 buffered turn events。
  • tui_events —— Tui::event_stream()（tui.rs:760），crossterm 的 key / paste / resize / draw 事件。
  • app_server.next_event() —— app-server 推来的 ServerNotification。

分发：handle_event（内部）/ handle_tui_event（app.rs:1294，经 RuntimeKeymap 路由按键，调 render_chat_widget_frame）/ handle_app_server_event。

4.3 与内核的连接

12AppServerSession + AppServerClient

tui/src/app_server_session.rs:261；app-server-client/src/lib.rs:451

TUI 通过 AppServerSession（app_server_session.rs:261）与 app-server 通信。它包装了 AppServerClient，后者是一个 enum：

  • InProcess —— InProcessAppServerClient::start（app-server-client/src/lib.rs:462），调 codex_app_server::in_process::start(...)，即 codex-core 的 app server 在同一进程跑，后面是 mpsc channel。
  • Remote —— websocket / JSON-RPC client（用于 daemon / cloud 连接）。

关键方法：bootstrap（:381）、next_event（:579）、request_handle（:1457，发送 typed ClientRequest）、resume_thread / fork_thread、shutdown。

4.4 渲染管线

13ChatWidget + Renderable + Tui::draw

tui/src/chatwidget.rs:543；render/renderable.rs:16；tui.rs:925

渲染核心是 ChatWidget（chatwidget.rs:543）。它实现 Renderable trait（render/renderable.rs:16），由 App::render_chat_widget_frame（app.rs:1392）触发，最终走 Tui::draw（tui.rs:925）→ ratatui 的 terminal.draw_with_size。

ChatWidget 的结构是一个 FlexRenderable：上面是 TranscriptAreaRenderable（对话流，由一堆 history_cell / exec_cell 组成），下面是 bottom pane（输入框 + 状态栏）。流式 markdown 渲染在 markdown_render/；diff 渲染在 diff_render.rs / diff_model.rs。

五、与 AgentScope 接入层的对照

维度CodexAgentScope 2.0
