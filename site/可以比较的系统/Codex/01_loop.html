① 核心：run_turn 的 agent 循环

逐函数精读 core/src/session/turn.rs（2750 行）。循环骨架在 L273 的 loop {}，采样在 L1317 的 run_sampling_request。

阅读路线

Codex 的"agent"不是单个对象，而是一条事件流。最小执行单元是 turn（一轮对话），turn 内部是 step（一次采样 + 工具批）。本篇按"入口 → 循环 → 采样 → 工具"四层讲，每个关键函数附源码块。

第一层：会话的入口——CodexThread

外部世界（TUI / exec / app-server client）接触到的只是 CodexThread。它是一个双向消息流的句柄：你往里塞 Op::UserInput，它往外吐 Event。

1CodexThread（L193-234）

pub struct CodexThread { session: Arc<Session>, io: SessionIo, session_source: SessionSource, ... }

core/src/codex_thread.rs:193

CodexThread 持有 Session（真正的状态机）和 SessionIo（事件管道）。对外只暴露 submit(op)、wait_until_terminated() 等少数方法——turn 的生命周期对调用方不可见，client 只看事件。

设计要点这是 Codex 区别于 AgentScope 的关键：AgentScope 的 Agent.reply() 是一个会 await 到结束的 async fn；Codex 把 turn 做成后台 task，turn 内部用 tokio::select! 监听取消、新输入、采样事件。所以 Codex 天然支持"用户在模型跑的时候打断/追加输入"。

Session 是一个 turn 的所有可变状态容器。它同时持有同步原语（watch 推状态变更、Mutex 保护 SessionState）和异步通道（tx_event 向外发事件）。一个 session 同时只有 1 个 running task。

★ 关键洞察：三层状态 Codex 的状态分三层：
Session（thread-scoped，持久：history、provider、policy）
→ TurnContext（turn-scoped，这一次对话的输入、metadata、model_info）
→ StepContext（step-scoped，一次采样的 snapshot：tool_router、window、prompt 视图）
每次循环开头都会 capture_step_context() 重新抓一份 step 视图，保证同一 turn 内多步采样看到一致的上下文。

第二层：循环骨架——run_turn

这是整个 crate 最重要的一段代码。函数本体在 L151，真正的循环在 L273。它把"采样 → 处理输出 → 跑工具 → 回到采样"串成一个 loop {}。

3run_turn（L151-273）—— 入口准备

pub(crate) async fn run_turn(sess: Arc<Session>, turn_context: Arc<TurnContext>, input: Vec<TurnInput>, prewarmed_client_session: Option<ModelClientSession>, cancellation_token: CancellationToken) -> CodexResult<Option<String>>

core/src/session/turn.rs:151

进入循环前，run_turn 要做 6 件事：

  • pre-sampling compact（L164）：采样前先压缩历史，避免一上来就超窗口。
  • 解析 MCP 需求（L187 required_mcp_servers_for_input）：看用户输入里 mention 了哪些 MCP server/plugin，决定这一轮要启哪些。
  • 抓 first step context（L200 capture_step_context_with_required_mcp_servers）：冻结一份 tool_router / window / prompt 视图。
  • build skills & plugins（L222 build_skills_and_plugins）：把 skill prompt 注入进上下文。
  • 跑 hooks（L234 run_pending_session_start_hooks、L238 run_hooks_and_record_inputs）：用户自定义的 pre-turn hook。
  • 建 TurnDiffTracker（L261）：跟踪这一轮对工作区产生的 diff，供后续展示和回滚。
设计要点ModelClientSession 是 turn-scoped 的，缓存 WebSocket + sticky routing 状态。Codex 在同一个 turn 的多次重试里复用这一个 session，而不是每次重连。

4主循环 loop {}（L273-560）

loop { pending_input = drain; run_hooks; capture_step_context; run_sampling_request → Ok/Err 分支; needs_follow_up → 继续; 否则 break }

core/src/session/turn.rs:273

循环体每轮做四件事，下面是关键源码节选：

let mut next_step_context = Some(first_step_context);
loop {
    // 1) 拿 pending 用户输入（UI 在模型跑时追加的消息）
    let pending_input = if can_drain_pending_input {
        sess.input_queue.get_pending_input(&sess.active_turn).await.0
    } else { Vec::new() };

    if run_hooks_and_record_inputs(&sess, &turn_context, &pending_input).await {
        break;
    }

    // 2) 抓 step 视图：有就用，没有就 capture 一份
    let step_context = match next_step_context.take() {
        Some(step_context) => step_context,
        None if pending_input.is_empty() => {
            sess.capture_step_context(Arc::clone(&turn_context), &cancellation_token).await?
        }
        None => { /* 带 pending input 的 capture */ }
    };

    // 3) 跑采样：这一步会把模型流式回包驱动到底
    let sampling_request_result: CodexResult<_> = async {
        // record world state、clone history、build responses_metadata
        run_sampling_request(
            Arc::clone(&sess),
            Arc::clone(&step_context),
            Arc::clone(&turn_context.extension_data),
            Arc::clone(&turn_diff_tracker),
            &mut client_session,
            &responses_metadata,
            sampling_request_input,
            cancellation_token.child_token(),
        ).await
    }.await;

    // 4) Ok → 看 needs_follow_up；Err → retryable 才重试
    match sampling_request_result {
        Ok((sampling_request_output, sampling_request_input)) => {
            let SamplingRequestResult {
                needs_follow_up: model_needs_follow_up,
                last_agent_message: sampling_request_last_agent_message,
            } = sampling_request_output;
            if model_needs_follow_up {
                sess.input_queue.accept_mailbox_delivery_for_current_turn(...).await;
                // ← 回到 loop 顶，再做一次采样
            } else {
                break; // 模型说完了，turn 结束
            }
        }
        Err(err) => { /* 重试逻辑 */ }
    }
}
★ 关键洞察：loop 的退出条件 退出 loop 只有两个路径：
(a) needs_follow_up == false —— 模型这一轮没有再要求工具调用，turn 自然结束；
(b) run_hooks_and_record_inputs 返回 true —— pre-turn hook 主动拒绝。
这意味着多轮工具调用是循环的同一 turn 内完成的，而不是 AgentScope 那种"每一轮 reply 都是一次完整调用"。

第三层：采样——run_sampling_request

这一层负责"把 prompt 送进模型、把流式回包分发到事件流"。它自己也有一个 loop（L1347），但那个 loop 是重试 loop，不是 ReAct loop。

5run_sampling_request（L1317-1406）

async fn run_sampling_request(sess, step_context, turn_store, turn_diff_tracker, client_session, responses_metadata, input, cancellation_token) -> CodexResult<(SamplingRequestResult, Vec<ResponseItem>)>

core/src/session/turn.rs:1317

这个函数做三件事：

  • 构造 ToolCallRuntime（L1332）—— 工具执行的 runtime，持 sess + step_context + diff_tracker。
  • 调 try_run_sampling_request（L1368）—— 真正发请求、收流、分派事件。
  • 失败时按 err.is_retryable() 决定是否重试（L1404），最多 stream_max_retries 次（L1342）。

源码（节选）：

async fn run_sampling_request(
    sess: Arc<Session>,
    step_context: Arc<StepContext>,
    turn_store: Arc<codex_extension_api::ExtensionData>,
    turn_diff_tracker: SharedTurnDiffTracker,
    client_session: &mut ModelClientSession,
    responses_metadata: &CodexResponsesMetadata,
    input: Vec<ResponseItem>,
    cancellation_token: CancellationToken,
) -> CodexResult<(SamplingRequestResult, Vec<ResponseItem>)> {
    let turn_context = Arc::clone(&step_context.turn);
    let router = Arc::clone(&step_context.tool_router);

    let base_instructions = sess.get_base_instructions().await;
    let tool_runtime = ToolCallRuntime::new(
        Arc::clone(&sess),
        Arc::clone(&step_context),
        Arc::clone(&turn_diff_tracker),
    );
    let max_retries = turn_context.provider.info().stream_max_retries();
    let mut retries = 0;
    let mut initial_input = Some(input);
    loop {
        let prompt_input = if let Some(input) = initial_input.take() {
            input
        } else {
            sess.clone_history().await.for_prompt(&turn_context.model_info.input_modalities)
        };
        let prompt = build_prompt(prompt_input, router.as_ref(), turn_context.as_ref(), base_instructions.clone());
        match try_run_sampling_request(
            tool_runtime.clone(),
            Arc::clone(&sess),
            Arc::clone(&turn_context),
            Arc::clone(&turn_store),
            client_session,
            responses_metadata,
            Arc::clone(&turn_diff_tracker),
            &prompt,
            cancellation_token.child_token(),
        ).await {
            Ok(output) => return Ok((output, original_input.unwrap_or(prompt.input))),
            Err(err) => match err.details() {
                CodexErrorDetails::ContextWindowExceeded => { sess.set_total_tokens_full(&turn_context).await; return Err(err); }
                CodexErrorDetails::UsageLimitReached(e) => { ... return Err(err); }
                _ => err,
            },
        }
        if !err.is_retryable() { return Err(err); }
        // ... retry
    }
}

7try_run_sampling_request（L2146-2211）

async fn try_run_sampling_request(...) -> CodexResult<SamplingRequestResult>

core/src/session/turn.rs:2146

真正驱动模型流式回包的函数。内部用 client_session.stream(prompt) 拿到一个流，然后逐 chunk 处理：

  • assistant 文本 delta → emit_streamed_assistant_text_delta（L1885）推到事件流。
  • 工具调用 delta → 累积成完整工具调用，等 done 时 dispatch。
  • reasoning/thinking delta → 视 reasoning_summary 配置决定是否对外暴露。

整个采样用一个 while let Some(res) = in_flight.next().await（L2102）消费流，并在 L2211 用 loop {} 处理可重试错误。

第四层：工具分发——ToolRouter

模型在流里吐出 tool call 后，Codex 不是立刻执行，而是累积到 done 再分发。ToolRouter（core/src/tools/）是所有工具的注册表与分派器。

8ToolRouter::dispatch

// core/src/tools/ 下 ToolRouter + ToolCallRuntime

core/src/tools/（31 文件，6.9 千行）

工具调用的 runtime 由 ToolCallRuntime::new(sess, step_context, turn_diff_tracker)（L1332）创建，持 ToolCallRuntime 把模型生成的 tool call 分派到具体工具实现。内置工具包括：

  • shell —— 执行 shell 命令（受 execpolicy 准入控制）。
  • apply_patch —— 多文件编辑（详见 ②）。
  • update_plan —— 维护待办计划。
  • view_image —— 查看图片。
  • MCP 工具 —— 通过 McpManager 转发到外部 MCP server。
★ 与 AgentScope 的关键差异 AgentScope 在 _batch_tool_calls 里把工具分成 sequential / concurrent 两批并发执行；Codex 的工具调度也是同一 step 内并发，但跨 step 严格串行——每个 step 的工具批必须全部 done，才能进入下一个采样 step。这保证了"模型看到工具结果后再决定下一步"的 ReAct 语义。

9handle_output_item_done

// core/src/stream_events_utils.rs

core/src/stream_events_utils.rs

当模型流里某个 output item（assistant message / function_call / reasoning）done 时，这个回调被触发。它做三件事：

  • 把 item 落进 conversation history（record_conversation_items）。
  • 如果是 function_call，触发 ToolRouter::dispatch。
  • 向 tx_event 发一个 Event，让 app-server client 能看到。

所有"流式 token → UI 显示"的魔法都起源于这里——TUI 不是直接读模型 socket，而是消费 CodexThread 发出的 Event 流。

第五层：上下文压缩——run_auto_compact

长对话会爆窗口。Codex 在 turn 内有多个压缩触发点。

10run_auto_compact / run_pre_sampling_compact（L1155 / L989）

// core/src/session/turn.rs:1155 (run_auto_compact) + L989 (run_pre_sampling_compact)

core/src/session/turn.rs:1155

Codex 有两条压缩路径：

  • inline auto-compact（run_auto_compact，L1155）—— 采样返回 ContextWindowExceeded 时触发，把历史压缩后重试。
  • pre-sampling compact（run_pre_sampling_compact，L989）—— 在采样前主动判断，避免等到失败。分本地（compact.rs）和远端（compact_remote.rs / compact_remote_v2.rs）两种实现。
设计要点压缩不只是"summarize history"。Codex 维护 InitialContextInjection，压缩时会重新注入被裁掉的关键上下文（AGENTS.md、用户 instructions、MCP server 列表），保证压缩后模型不会"失忆"。
