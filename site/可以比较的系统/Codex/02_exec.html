② 执行层：apply-patch / linux-sandbox / execpolicy

模型说"改这个文件 / 跑这条命令"，谁来落地？本篇解剖 Codex 的三个执行子模块。

本篇主线

agent loop 里模型发出两种动作：工具调用（shell / apply_patch / MCP）和文本。工具调用要走一条"准入 → 沙箱 → 文件落地 → diff 追踪"的流水线。这条流水线由三个 crate 支撑：

  • apply-patch（4.6 千行）—— OpenAI 自定义的 *** Begin Patch 格式的解析与应用。
  • linux-sandbox（7.0 千行）—— 默认 bubblewrap + seccomp；保留 legacy Landlock 兼容路径。
  • execpolicy（2.0 千行）—— 命令行准入策略（allow / deny / ask）。

一、apply-patch：模型编辑文件的"格式合同"

Codex 为模型提供一种首选的结构化补丁格式，但 shell 工具仍可能运行 sed / python；因此它是可审计的编辑合同，不是唯一写文件通道。apply-patch 负责解析、校验、计算并逐项应用，失败时显式返回已提交的部分，而不是承诺全量原子性。

1.1 补丁格式（L4-22 Lark 文法）

补丁的开头必须是 *** Begin Patch，结尾是 *** End Patch。中间是若干 hunk（补丁块）。三种 hunk：

*** Begin Patch
*** Add File: src/new.rs
+pub fn hello() {}

*** Delete File: src/old.rs

*** Update File: src/main.rs
@@ fn main() @@
-    println!("old");
+    println!("new");
*** End of File
*** End Patch

关键标记常量在 parser.rs:37-46：BEGIN_PATCH_MARKER / END_PATCH_MARKER / ADD_FILE_MARKER / DELETE_FILE_MARKER / UPDATE_FILE_MARKER / MOVE_TO_MARKER / EOF_MARKER。

1Hunk 枚举（parser.rs:66-82）

pub enum Hunk { AddFile { path, contents }, DeleteFile { path }, UpdateFile { path, move_path, chunks } }

apply-patch/src/parser.rs:66

三种 hunk 用一个 enum 表示。UpdateFile 持有 Vec<UpdateFileChunk>——一个文件里可以有多个独立的"上下文块 + 改动行"。

#[derive(Debug, PartialEq, Clone)]
pub enum Hunk {
    AddFile {
        path: PathBuf,
        contents: String,
    },
    DeleteFile {
        path: PathBuf,
    },
    UpdateFile {
        path: PathBuf,
        move_path: Option<PathBuf>,
        chunks: Vec<UpdateFileChunk>,
    },
}

2UpdateFileChunk（parser.rs:115）

pub struct UpdateFileChunk { change_context: String, change_lines: Vec<ChangeLine>, eof: bool }

apply-patch/src/parser.rs:115

每个 chunk 由"上下文锚点"（@@ ... @@，即 change_context）+ 改动行列表组成。eof 标记这块改动是否延伸到文件末尾。锚点不是行号，而是文件里的一段文本——apply 时用 similar 库（文本 diff）定位。这比行号鲁棒得多：模型哪怕记错了行号，只要上下文文本还在，就能对上。

1.2 流式解析：让 TUI 边收边显示

3StreamingPatchParser（streaming_parser.rs:22-154）

pub struct StreamingPatchParser { ... }; fn push_delta(&mut self, delta: &str) -> Result<Vec<Hunk>, ParseError>; fn finish(&mut self) -> Result<Vec<Hunk>, ParseError>

apply-patch/src/streaming_parser.rs:22

模型流式吐 token，补丁是一点一点攒出来的。StreamingPatchParser 接收每个 delta，内部维护一个行缓冲；每凑成一个完整 hunk 就返回。finish() 在流结束时调用，收尾。

★ 为什么要流式？ apply_patch 在 TUI 里是逐文件 diff 展示的——用户能在模型还没说完时就看到"这个文件会变成这样"。非流式解析只能等模型吐完整个 *** End Patch 再处理，延迟太高。

1.3 应用：把 hunk 落到文件系统

4apply 主流程（lib.rs:833+ AppliedPatchDelta / ApplyPatchFailure）

apply-patch/src/lib.rs:833（ApplyPatchFileUpdate）、lib.rs:184（AppliedPatchDelta）、lib.rs:251（ApplyPatchFailure）

应用逻辑在 lib.rs 中段。整体流程：

  • 校验路径：所有 hunk 的 path 必须落在沙箱允许的工作区内（resolve_path + 上层 permission）。
  • 逐 hunk 应用：
    • AddFile —— 创建新文件，写入 contents。
    • DeleteFile —— 删除文件。
    • UpdateFile —— 读现有内容，对每个 chunk 用文本匹配定位 change_context，替换 change_lines。
  • 收集 delta：AppliedPatchDelta（lib.rs:184）累积每个文件的实际变化（AppliedPatchChange），供 diff 追踪器 TurnDiffTracker 使用。
  • 失败证据：任意一个 hunk 失败，返回 ApplyPatchFailure（lib.rs:251），包含 ApplyPatchError 和 AppliedPatchDelta（已成功应用的部分）。没有事务性的全量回滚；若写操作可能先改文件再报错，delta 还会把 exact 置为 false。源码能证明的是“如实暴露部分副作用”，不能进一步推断这是为了让用户保留进度。
⚠ 部分应用的风险 apply_patch 失败不会自动撤销已成功的 hunk。git 工作区通常可以人工恢复，但 apply-patch crate 本身没有“失败时自动 git rollback”的保证；非 git 工作区或未提交改动更需要预先 snapshot/staging。

1.4 鲁棒性：为什么要"宽容解析"？

parser.rs:53 有一行注释：gpt-4.1 会产出不完全合规的补丁。所以解析器默认 PARSE_IN_STRICT_MODE = false，对空白、换行符、标记大小写做宽容处理。这是一个很现实的工程妥协——模型不是规则引擎，输出总会有瑕疵。

二、linux-sandbox：可切换后端的命令隔离

模型调 shell 工具时，Codex 不会无条件直接执行。在 Linux 上，受限命令先经过 codex-linux-sandbox；当前默认文件系统后端是 bubblewrap，进程内再安装 seccomp 网络过滤。Landlock + mount protection 是显式开启的 legacy 路径，并非三者始终叠加。

两条文件系统路径 + 共同的运行时硬化
  • bubblewrap（默认）—— 用 mount/user/PID（按网络策略也可含 network）namespace 构造只读基线，再叠加可写根和受保护子路径。
  • legacy Landlock—— 在显式 feature 下提供兼容文件系统约束与 mount protections；不是默认路径上再叠的一层。
  • 共同硬化—— no_new_privs 与 seccomp 网络过滤；managed network 模式再通过隔离 network namespace 和代理桥控制出口。

2.1 入口：codex-linux-sandbox 二进制

5run_main（lib.rs:39）

pub fn run_main() -> !

linux-sandbox/src/lib.rs:39

入口很简单：在 Linux 上调 linux_run_main::run_main()，否则 panic。真正的逻辑在 linux_run_main.rs。这个二进制被设计成自包含：它自己就是受限执行的根。

2.2 bubblewrap 默认路径与 legacy Landlock

源码包含系统/随包分发等 bubblewrap 获取与启动逻辑，以适配不同部署环境：

模块场景关键点
bundled_bwrap.rs自带 bubblewrap 二进制不依赖系统 bwrap，保证始终可用
bazel_bwrap.rsBazel 构建处理 Bazel 的 sandboxfs / 输出树布局
bwrap.rs标准系统 bwrap直接调 /usr/bin/bwrap
设计要点当前实现优先使用工作目录之外 PATH 中的 bwrap，缺失时回退到随 Codex 分发的 bundled binary；bubblewrap 路径以只读根挂载为基线，再叠加 writable roots 和受保护的只读子路径，并安装 no_new_privs 与 seccomp 网络过滤。features.use_legacy_landlock 才切到兼容的 Landlock 路径。这里的亮点不是“固定三重沙箱”，而是同一 permission profile 可编译到不同平台/后端。

2.3 代理生命周期：网络出口控制

6proxy_lifecycle / proxy_routing（lib.rs:26-27）

linux-sandbox/src/proxy_lifecycle.rs、proxy_routing.rs

沙箱不只是限制文件读写。网络可以整体隔离；在managed proxy 模式下，bubblewrap 隔离网络 namespace，再经内部 TCP→UDS→TCP bridge 把工具流量送到配置的代理端点。此时才可以实施比“能否联网”更细的出口规则；不能概括为所有 Codex 命令始终经过域名代理。

2.4 启动器：把命令送进沙箱

7launcher（lib.rs:24）

linux-sandbox/src/launcher.rs

launcher 负责组装完整的沙箱启动命令：先 spawn codex-linux-sandbox 自己（作为 sandbox 入口），再在内部用 bwrap + landlock + seccomp 包裹真正的用户命令。输出通过管道回传给 agent loop。

三、execpolicy：命令行准入策略

沙箱管"执行时的隔离"，execpolicy 管"这条命令到底该不该跑"。它是 agent loop 在 dispatch shell 工具前的第一道闸。

3.1 三种裁决

每条命令会被归入三类：

裁决含义后续动作
Allow命令在白名单 / 无危险特征直接进沙箱执行
Deny命令命中黑名单（如 rm -rf /）拒绝执行，把拒绝原因回传模型
Ask命令需要用户确认走 app-server 审批流程（见 ③）
★ 拒绝也是一种反馈 和很多 agent 框架"拒绝就报错退出"不同，Codex 把 Deny 的原因当成 tool result 回传给模型。模型看到"这条命令被拒绝因为 X"，可以自己换个写法再试。这是一种用环境约束教模型的设计。

3.2 准入规则的来源

execpolicy 的规则不是从 AGENTS.md 文本中解析；AGENTS.md 是模型可见的项目指令。可执行策略来自配置 layer stack 中用户/项目的 rules/*.rules、托管 requirements policy，以及会话中获批后形成的 amendment。规则偏向命令前缀/模式匹配，并与 permission profile（文件系统、网络等运行时权限）分工：前者决定 allow / prompt / forbidden，后者决定即使获准后进程还能访问什么。

四、一条命令的完整生命周期

把上面三个模块串起来，模型调 shell 工具时发生的事：

① 模型流式吐 function_call: shell("cargo test")
   ↓
② agent loop 的 handle_output_item_done 收到完整 tool call
   ↓
③ ToolRouter::dispatch → shell 工具实现
   ↓
④ execpolicy 评估 "cargo test"
   ├─ Allow → 继续
   ├─ Ask   → 发 ServerRequest::AskForApproval，等用户
   └─ Deny  → 返回拒绝原因给模型，本轮结束
   ↓
⑤ 平台 sandbox transform 启动
   ├─ Linux 默认 bwrap 构造受限文件系统视图
   ├─ 安装 no_new_privs / seccomp 网络过滤
   ├─ 显式配置时改走 legacy Landlock
   └─ managed network 时走代理桥与出口规则
   ↓
⑥ 命令在沙箱内执行，stdout/stderr 通过管道回传
   ↓
⑦ tool result 塞回 conversation history
   ↓
⑧ agent loop 回到 loop 顶，做下一次采样
   (模型现在能看到 "cargo test" 的输出了)
与 apply_patch 的对比 apply_patch 不走 execpolicy 的命令行评估——它是结构化编辑工具，不是 shell 命令。但 apply_patch 同样受 permission profile 的路径级准入控制：模型只能在配置允许的工作区里改文件。两条准入路径：命令行走 execpolicy，文件路径走 permission profile。

本篇小结：执行层的三个正交维度

维度负责 crate解决的问题
格式apply-patch模型怎么表达"改这个文件"？用结构化补丁，不用 sed/awk。
隔离sandboxing + 各平台 sandbox把 permission profile 翻译为 Linux bwrap/seccomp（或 legacy Landlock）、macOS Seatbelt、Windows restricted token，并按配置限制网络。
准入execpolicy + permission profile这条命令该不该跑？这个路径该不该写？三级裁决 + 路径白名单。

三个维度互相独立：你可以换掉沙箱后端而不动 apply_patch；也可以加新的准入规则而不碰隔离实现。这是 Codex 把它们切成独立 crate 的根本原因。
