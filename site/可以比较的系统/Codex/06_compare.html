⑥ 源码审计、横向对比与 AutoResearch 借鉴

先区分“源码能证明什么”和“产品宣传说了什么”，再讨论 Codex 相比其他 coding agent 真正值得借鉴的工程亮点。

审计快照：codex @ 0a0ebb8535（2026-08-06）；复核日期：2026-08-08。

结论先行：原解读的主线——“事件流内核 + 受控执行 + app-server 协议边界”是成立的，但若干比较结论不成立或证据不足。Codex 的独特价值不是笼统的“最强沙箱”或“唯一后台 agent”，而是把协议、准入、运行时权限、持久化、诊断证据做成可组合且可测试的边界。对 AutoResearch 最有价值的，也是这套“把一次自主运行变成可治理、可恢复、可审计对象”的方法。

二、Codex 源码中真正突出的七个亮点

1. 会话不是一次函数调用，而是可寻址、可插入、可中断的运行对象

源码证据：core/src/codex_thread.rs 的 CodexThread 同时暴露 submit* 与事件消费，并进一步区分普通提交、等待 admission、等待 persisted admission。protocol/src/protocol.rs 把输入建模为 Op，输出建模为 EventMsg。

亮点：“消息已收到”“已获准进入 turn”“已持久化”是不同完成语义。很多 agent API 只有一个 await run()，调用方无法严谨回答请求究竟卡在哪个阶段。

2. in-process 也走同一 JSON-RPC envelope，而不是另开一套捷径

源码证据：app-server-client/src/lib.rs 明确说明，即使 in-process 成功响应也经由与 socket/stdio 相同的 JSON-RPC result envelope；TUI 与 exec 都使用 app-server client，远程路径再切 websocket/UDS。

亮点：这不是“为了 RPC 而 RPC”。它让本地 UI、headless runner、远端 daemon 对 thread/turn/item 的状态语义保持一致，也使 app-server 公共 API 的集成测试成为真正的兼容性门禁。

3. 安全不是一个布尔开关，而是一条分层决策链

源码证据：execpolicy 先做命令模式裁决；approval 决定是否请求额外权限；permission profile 描述文件系统/网络能力；sandboxing 再翻译到 Linux bubblewrap+seccomp、macOS Seatbelt、Windows restricted token。managed proxy 继续收窄网络出口。

亮点：“允不允许尝试”和“获准后操作系统实际允许什么”被分开。拒绝原因还能成为结构化 tool result，让模型调整方案，而不是把策略失败误当成程序失败。

4. 产品历史与诊断证据分层：observe first, interpret later

源码证据：thread-store/README.md 规定 canonical history 写 rollout JSONL、queryable metadata 写 SQLite；rollout-trace/README.md 则定义 opt-in raw events/payloads，离线 reducer 生成 state.json 语义图。

亮点：恢复会话所需的稳定历史，不必承担所有调试细节；诊断层保存原始证据而不在热路径过早解释。相比“把日志、状态和实验结果塞进一个 JSON”，这套边界更利于 schema 演进与追责。

5. 上下文管理被当成缓存与安全不变量，而不只是 prompt 拼接

源码证据：仓库 AGENTS.md 对 model-visible context 明确要求：history 增量构建、不频繁重写以避免 cache miss、所有注入项有硬上限、跨阈值内容需额外审查；core/context 用类型约束可注入 fragment。

亮点：它把“上下文污染/膨胀/缓存抖动”提升为代码评审规则。对长周期 agent，这比单纯做一次 summary 更关键。

6. apply_patch 不假装原子：失败结果携带已提交前缀

源码证据：apply-patch/src/lib.rs 的 ApplyPatchFailure 携带 AppliedPatchDelta；delta 记录按顺序已落盘的 change，并用 exact 标记写失败后证据是否完整。

亮点：真实文件系统写入可能“先截断、后报 ENOSPC”，所以纯 Result<(), Error> 会丢掉关键事实。Codex 把部分副作用建模进错误类型。它不是事务性保证，但比假装失败即无副作用诚实得多。

7. 多 agent 不只是 spawn：路由身份与因果边被纳入 trace

源码证据：rollout-trace 为 thread 保存类似 /root/search_docs 的稳定 routing path，并记录 spawn、task、result、close interaction edges；feature/config 还把 multi-agent mode 明确注入模型可见上下文。

亮点：并行本身不难，难的是事后回答“哪个子任务产生了哪个工具调用和结果”。Codex 把多 agent 当作可还原的因果图，而不是一堆无法关联的并发日志。

三、仍然存在的代价与边界

问题源码层面的判断对使用者的含义
体量和认知成本130 个 workspace member，src/**/*.rs 约 106 万行；core、TUI、app-server 都很大边界丰富不等于容易复用；小项目照搬会先得到维护负担
协议重复成本app-server protocol 与 core protocol 之间需要映射、版本兼容和大量 integration tests多前端收益真实，但单前端项目不值得预付这笔成本
沙箱不是绝对安全行为取决于平台、permission profile、approval、feature 与 managed environment；还有显式 full-access 路径不能用“行业最强”替代 threat model；应逐项声明可读、可写、网络与 secret 边界
补丁非事务失败可留下部分修改，delta 只是把事实暴露出来关键数据仍需 snapshot、staging area 或事务式 artifact store
trace 含敏感信息源码 README 明示可能包含 prompt、response、tool I/O、terminal output 与路径科研系统必须把 trace 当敏感研究数据，设置保留期、脱敏和访问控制
解释性分层不是稳定 APIcrate 很多，但并非每个 crate 都是可插拔接口复用前先找 trait/protocol/test gate，不要按目录复制

四、对 AutoResearch 的直接借鉴：从 coding turn 到 experiment run

AutoResearch 不应照搬 Codex 的 UI 或 crate 数量；应复制它对“自主运行”的治理语义。下面给出可以落到数据模型和模块边界的映射。

Codex 机制AutoResearch 对应设计需要科研化改造的地方
CodexThread / Op / EventMsgResearchRun / RunCommand / RunEvent；proposal、search、experiment、evaluation 都只追加事件事件必须带 dataset、code、environment、seed、budget 的版本引用
admission / persisted admission区分“任务已提交、资源已获批、run manifest 已持久化、worker 已启动”加 GPU quota、伦理审查、数据许可、最大成本和 wall-time admission
execpolicy + approval + sandbox实验意图策略 → 人/guardian 审批 → 实际容器/调度器权限限制的不只是命令，还包括数据集、算力、外网、模型 API 和危险实验
rollout JSONL + SQLite metadataappend-only run journal + 可查询 run indexjournal 只存控制面事实；大 checkpoint、图表、数据放 content-addressed artifact store
raw rollout trace + reducer先保存原始 observation，再离线生成 hypothesis/experiment/evidence graphreducer 必须版本化；论文结论要能追到原始表格、日志和代码 commit
AppliedPatchDelta.exact每个工具错误都返回 side_effects 与 evidence_complete对数据和 checkpoint 默认 staging + atomic publish，不能只靠 git
multi-agent routing path / interaction edges为 literature、method、runner、reviewer 分配稳定路径并记录任务/结果边合并结果时保留 provenance，禁止 reviewer 与被评估产物共享未声明状态
bounded contextual fragments每类研究上下文有 token/size cap、版本和来源文献摘要不得替代原文证据；关键 claim 应保留 citation pointer

推荐的最小数据骨架

ResearchRun
  id, parent_id, routing_path
  manifest_ref          # code commit, dataset snapshot, env image, seed, budget
  status                # queued/admitted/running/completed/failed/interrupted

RunEvent (append-only)
  seq, run_id, turn_id, timestamp
  kind                   # command/tool/result/artifact/decision/approval/evaluation
  payload_ref            # 大对象放 artifact store
  producer, causal_parent
  side_effects[]
  evidence_complete

RunIndex (derived)
  queryable metadata, cost, metrics, latest status

EvidenceGraph (offline reducer)
  hypothesis → experiment → observation → analysis → claim

实施优先级

  1. P0：先定义 RunEvent 与 manifest。没有稳定身份、环境快照和 append-only 事件，其余“自动研究”都无法可靠复现。
  2. P0：建立 artifact staging/commit。代码 patch 可借鉴 Codex delta；数据、checkpoint、指标文件必须比 Codex apply_patch 更事务化。
  3. P1：把 admission 与执行权限分开。policy engine 判断实验是否该做，sandbox/scheduler 保证即使模型失控也越不了界。
  4. P1：建立 raw trace → versioned reducer。先做到可回答“这条结论来自哪次 run、哪份日志”，再做漂亮 dashboard。
  5. P2：需要第二种前端或远程 worker 时再引入 RPC 硬边界。不要一开始复制 7 万行协议层。
  6. P2：多 agent 最后加。先确保单 run 的状态、证据、恢复正确，再用 routing path 和 causal edges 扩展为树。
最终判断 Codex 相比许多 coding agent 最有辨识度的地方，是它没有把“模型会写代码”当作系统完成，而是继续追问：请求何时真正被接纳？命令为什么获准？权限最终由谁强制？失败留下了哪些副作用？历史如何恢复？原始证据如何还原成因果图？这套问题意识，正是 AutoResearch 从 demo 走向可复现研究基础设施时最值得借鉴的部分。
