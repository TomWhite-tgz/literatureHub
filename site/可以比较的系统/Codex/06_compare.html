⑥ 源码审计、横向对比与 AutoResearch 借鉴

先区分“源码能证明什么”和“产品宣传说了什么”，再讨论 Codex 相比其他 coding agent 真正值得借鉴的工程亮点。

审计快照：codex @ 0a0ebb8535（2026-08-06）；复核日期：2026-08-08。

结论先行：三套源码把复杂度放在不同位置。Codex 更突出事件协议、app-server 硬边界、执行准入与平台沙箱；Claude Code 更突出流式工具并发、权限竞态、多级上下文减重、可恢复子 agent 与 JSONL 会话图；Pi 则以极小 Agent loop、provider/message 分层和任意代码扩展换取可嵌入性，同时正在建设尚未完成的 durable Harness。AutoResearch 应让 Pi 式小 loop、Codex 式治理骨架和 Claude Code 式长程状态各司其职。

一、审计口径：避免苹果和橘子比较

现在可以对 Codex 与 Claude Code 做函数级比较，但证据强度仍不完全相同。Codex 是带 Git 提交号、Cargo workspace 与低层 sandbox crate 的仓库快照；Claude Code 材料是一个只有 src/、无 .git/package.json 的 source-map backed TypeScript 展开树。后者的大部分 query、tool、session、agent 和 SDK 实现可读，但若干内部 feature 模块缺失，sandbox 底层也来自外部 runtime。

原文需要撤回的说法
  • “Claude Code 没有本地沙箱”不成立。本树有完整 sandbox adapter，但底层 runtime 外置、且默认由 sandbox.enabled ?? false 控制；正确说法是“存在可配置沙箱路径，低层实现未在本树审计”。
  • “Claude Code 只有前台同步 subagent”不成立。AgentTool 明确支持 background、resume、fork、worktree 和 swarm mailbox；但这些路径不是一个完全统一的 worker backend。

  • “Claude Code / Aider 没有权限控制、Aider 不跑 shell”不成立；Claude 权限链已能从源码追到 rule/hook/classifier/交互 handler，Aider 也明确有 /run 和 /test。
  • “异步 PR 交付只有 Codex”不成立；Cursor Background Agents 也是远程隔离 VM + 分支交付。
  • “Linux 始终 Landlock + seccomp + bwrap 三层叠加”不成立；当前默认是 bubblewrap + seccomp，Landlock 是 legacy 路径。
  • “rollout 可换模型精确重放做 A/B”没有现成源码语义保证；恢复历史不等于重现实验环境。

三、在看过 Claude Code 源码后，Codex 仍突出的七个亮点

1. 会话不是一次函数调用，而是可寻址、可插入、可中断的运行对象

源码证据：core/src/codex_thread.rs 的 CodexThread 同时暴露 submit* 与事件消费，并进一步区分普通提交、等待 admission、等待 persisted admission。protocol/src/protocol.rs 把输入建模为 Op，输出建模为 EventMsg。

亮点：“消息已收到”“已获准进入 turn”“已持久化”是不同完成语义。很多 agent API 只有一个 await run()，调用方无法严谨回答请求究竟卡在哪个阶段。

2. in-process 也走同一 JSON-RPC envelope，而不是另开一套捷径

源码证据：app-server-client/src/lib.rs 明确说明，即使 in-process 成功响应也经由与 socket/stdio 相同的 JSON-RPC result envelope；TUI 与 exec 都使用 app-server client，远程路径再切 websocket/UDS。

亮点：这不是“为了 RPC 而 RPC”。它让本地 UI、headless runner、远端 daemon 对 thread/turn/item 的状态语义保持一致，也使 app-server 公共 API 的集成测试成为真正的兼容性门禁。

3. 安全不是一个布尔开关，而是一条分层决策链

源码证据：execpolicy 先做命令模式裁决；approval 决定是否请求额外权限；permission profile 描述文件系统/网络能力；sandboxing 再翻译到 Linux bubblewrap+seccomp、macOS Seatbelt、Windows restricted token。managed proxy 继续收窄网络出口。

亮点：“允不允许尝试”和“获准后操作系统实际允许什么”被分开。拒绝原因还能成为结构化 tool result，让模型调整方案，而不是把策略失败误当成程序失败。

4. 产品历史与诊断证据分层：observe first, interpret later

源码证据：thread-store/README.md 规定 canonical history 写 rollout JSONL、queryable metadata 写 SQLite；rollout-trace/README.md 则定义 opt-in raw events/payloads，离线 reducer 生成 state.json 语义图。

亮点：恢复会话所需的稳定历史，不必承担所有调试细节；诊断层保存原始证据而不在热路径过早解释。相比“把日志、状态和实验结果塞进一个 JSON”，这套边界更利于 schema 演进与追责。

5. 上下文管理被当成缓存与安全不变量，而不只是 prompt 拼接

源码证据：仓库 AGENTS.md 对 model-visible context 明确要求：history 增量构建、不频繁重写以避免 cache miss、所有注入项有硬上限、跨阈值内容需额外审查；core/context 用类型约束可注入 fragment。

亮点：它把“上下文污染/膨胀/缓存抖动”提升为代码评审规则。对长周期 agent，这比单纯做一次 summary 更关键。

6. apply_patch 不假装原子：失败结果携带已提交前缀

源码证据：apply-patch/src/lib.rs 的 ApplyPatchFailure 携带 AppliedPatchDelta；delta 记录按顺序已落盘的 change，并用 exact 标记写失败后证据是否完整。

亮点：真实文件系统写入可能“先截断、后报 ENOSPC”，所以纯 Result<(), Error> 会丢掉关键事实。Codex 把部分副作用建模进错误类型。它不是事务性保证，但比假装失败即无副作用诚实得多。

7. 多 agent 不只是 spawn：路由身份与因果边被纳入 trace

源码证据：rollout-trace 为 thread 保存类似 /root/search_docs 的稳定 routing path，并记录 spawn、task、result、close interaction edges；feature/config 还把 multi-agent mode 明确注入模型可见上下文。

亮点：并行本身不难，难的是事后回答“哪个子任务产生了哪个工具调用和结果”。Codex 把多 agent 当作可还原的因果图，而不是一堆无法关联的并发日志。

五、对 AutoResearch 的直接借鉴：Codex 作骨架，Claude 补长程状态

AutoResearch 不应照搬 Codex 的 crate 数量，也不应照搬 Claude Code 的所有 task/backend 分支。更稳妥的组合是：以 Codex 的 run/event/admission 形成控制面，以 Claude Code 的 context checkpoint、permission provenance、sidechain task 和恢复包承载长周期自治。

实施优先级

  1. P0：先定义 RunEvent、ActionAttempt 与 manifest。请求接受后先持久化稳定身份；每个工具调用都必须闭合到成功、错误、中断或 synthetic terminal result。
  2. P0：建立 artifact staging/commit。代码 patch 可借鉴 Codex delta；数据、checkpoint、指标文件必须比 Codex apply_patch 更事务化，大内容只在 context 中保留可追溯 preview。
  3. P1：把 admission 与执行权限分开。policy engine 判断实验是否该做，sandbox/scheduler 保证即使模型失控也越不了界。
  4. P1：实现可恢复的单 worker 与 ContextCheckpoint。恢复测试必须覆盖消息、预算、workspace、artifact projection 和未完成 action，而不只是重新加载 summary。
  5. P1：建立 raw trace → versioned reducer。先做到可回答“这条结论来自哪次 run、哪份日志”，再做漂亮 dashboard。
  6. P2：需要第二种前端或远程 worker 时再引入 RPC 硬边界。不要一开始复制 7 万行协议层。
  7. P2：多 agent 最后加，而且先只做一种 backend。先确保单 task 的状态、证据、权限与恢复正确，再用 routing path、sidechain transcript 和 causal edges 扩展为树。
最终判断 Codex 迫使我们追问：请求何时真正被接纳和持久化？权限最终由哪层强制？原始事件如何还原成因果图？Claude Code 又追问：模型流尚未结束时工具如何安全并行？压缩损失了什么、后台任务如何续接？Pi 则提醒我们：核心 loop 和 context projection 可以很小，但扩展自由度不能替代安全边界，精致的 durable 规范也不能替代已运行的实现。三组问题合在一起，才是 AutoResearch 从 demo 走向可恢复、可治理、可复现研究基础设施所需的完整工程视角。
