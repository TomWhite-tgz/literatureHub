⑤ 总架构 & 全 crate 依赖图

审计快照的 workspace 明列 130 个 member，仓库内共有 137 个 Cargo.toml，src/**/*.rs 共 1,058,898 行。本篇把核心部分按 5 层做解释性切分。

数字一览
  • 130 个 workspace member；仓库内共 137 个 Cargo.toml（含根清单及不在 member 列表中的包）
  • 1,058,898 行 Rust 源码（统计所有 src/**/*.rs）
  • codex-protocol 是被依赖最多的 crate（69 个直接 dependents；含 normal/dev/build/target dependency）
  • 29 个 leaf crate（零内部依赖），大多是底层工具库
  • 最大的三个：tui 24.2 万行、core 18.8 万行、app-server 4.6 万行

二、关键依赖关系（谁依赖谁）

下面这张表是反向依赖（fan-in）：一个 crate 被多少其他 crate 依赖。fan-in 越高 = 改它越危险。

crate被依赖次数为什么这么高
codex-protocol69Event / ResponseItem / Op 等核心协议类型被广泛共享。
codex-utils-absolute-path54绝对路径强类型被沙箱、配置、rollout 等使用。
codex-http-client25共享 HTTP 基础能力。
codex-core24agent 内核被 app-server、专用适配器和测试支持等依赖。
codex-login24认证与账户能力。
codex-otel24OpenTelemetry 集成是横切关注点。
codex-config23配置加载与类型。
codex-exec-server18执行服务边界。
codex-git-utils16git 操作工具，diff 追踪 / PR 创建 / blame 都用它。
codex-extension-api15宿主内 extension contributor 契约。
★ 关键洞察：protocol 是真正的地基 codex-protocol 有 69 个直接 dependents，是当前快照被引用最多的内部 package。这说明共享协议类型确实位于高 fan-in 边界；但 Event / Op 是 core protocol，app-server 还有独立的版本化 RPC protocol，二者之间存在显式映射，不能混成一套“跨进程契约”。
这跟 AgentScope 不同：AgentScope 的 protocol.py 只是消息格式，没有"协议即地基"的地位。

2.1 依赖方向：package 图无环，但阅读分层不是强约束

从 fan-in 表可以看出依赖方向是：

Frontends (tui/cli/exec)
    ↓ import
Server (app-server / exec-server / mcp)
    ↓ import
Core (codex-core / tools / skills / compact)
    ↓ import
Exec & Sandbox (apply-patch / linux-sandbox / execpolicy)
    ↓ import
Foundation (protocol / config / login / utils / otel)

Cargo package 依赖图必须无环，且 core 不依赖 app-server，这个内外边界确实清楚；但“foundation / core / server”是本文标签，不是 Rust 类型系统强制的 layer rule。替换 app-server transport 通常不必重写 agent loop，却仍会影响 protocol、client 与集成测试，不能据此声称某一整层可无波及替换。

三、从入口到内核的完整调用链

以 codex-exec 为例，从 main() 到模型采样的完整 import 链：

codex-exec (前端)
  ├─ codex-app-server-client    → 连接 app-server
  ├─ codex-app-server-protocol  → RPC 类型
  ├─ codex-config               → 读 ~/.codex/config.toml
  ├─ codex-login                → ChatGPT OAuth / API key
  ├─ codex-core                 → CodexThread / Session / run_turn
  │    ├─ codex-protocol        → Event / ResponseItem / Op
  │    ├─ codex-model-provider  → 模型适配（OpenAI / Anthropic / Ollama）
  │    ├─ codex-tools           → ToolRouter / shell / apply_patch
  │    ├─ codex-compact         → 上下文压缩
  │    ├─ codex-mcp             → MCP 客户端管理
  │    ├─ codex-skills          → skill 注入
  │    ├─ codex-hooks           → 用户自定义 hook
  │    ├─ codex-guardian        → 审批 / 安全守护
  │    └─ codex-sandboxing      → 沙箱策略 → linux/windows-sandbox
  ├─ codex-apply-patch          → 结构化补丁应用
  ├─ codex-linux-sandbox        → bwrap + seccomp（默认）/ legacy Landlock
  ├─ codex-execpolicy           → 命令准入
  └─ codex-otel                 → OpenTelemetry 遥测
设计要点 这条链展示的是职责分离，不代表每个 crate 都是稳定插件点。真正可替换的边界要看 trait、协议和构造注入；例如 app-server protocol、ThreadStore trait、跨平台 sandbox transform 是显式边界，而“换成 Firecracker 完全不动 core”只是设计设想，源码没有提供这样的现成后端。

五、之前漏掉的重磅模块

①②③ 只讲了 agent loop 主干。这里补全 Codex 源码里几个重量级但没展开的子系统。

5.1 codex-core-plugins（38k 行）—— 能力包与 marketplace

Codex 不只是一个 CLI，它把可分发扩展组织成插件包。源码中的 PluginManifestPaths 明确定义了四类资源：skills、MCP servers、apps、hooks；core-plugins 负责 marketplace、安装缓存、策略和装载。

  • 自定义工具通常通过插件声明的 MCP server 接入；prompt/workflow 通过 skill，外部服务通过 app connector，生命周期动作通过 hook。
  • 只有具体的 MCP server 或 hook 脚本可能启动进程；“插件整体是一个隔离子进程”并非 manifest 或 loader 的语义。
  • 亮点是组合与分发：一个安装单元可以原子携带多种能力，并接受 marketplace policy 和版本管理，而不是发明另一套任意代码 ABI。

5.2 codex-state + codex-thread-store + codex-rollout（60k 行）—— 持久化三件套

这三个 crate 一起实现了 Codex 的会话持久化：

  • codex-state（20k）—— SQLite 状态库和可查询索引等持久状态，不等同于 core 内存中的全部 SessionState。
  • codex-thread-store（26k）—— 明确的 storage boundary：LocalThreadStore 把 canonical history 写入 rollout JSONL，把可查询 metadata 写入 SQLite（可用时）。
  • codex-rollout（14k）—— 记录经过 persistence policy 筛选的 canonical items，支持会话恢复/检查；它与 opt-in、原始证据导向的 rollout-trace 不是一回事。
设计要点 真正值得借鉴的是把运行事实分成两种存储：产品级 rollout JSONL 是可恢复的 canonical history；设置 CODEX_ROLLOUT_TRACE_ROOT 后，rollout-trace 才额外写原始事件与 payload，并用离线 reducer 生成语义图（“observe first, interpret later”）。源码支持恢复、检查和诊断，但没有提供“把同一 rollout 换模型重跑即可精确 A/B”的现成语义；科学实验若要 A/B，还必须固定环境、工具版本、随机种子和外部数据快照。

5.3 codex-extension-api（1.6k 行）—— 扩展契约

这个 crate 是宿主内扩展（host-owned extensions）的 Rust 契约，与前面的可安装 plugin package 不是同一个概念。它定义了：

  • ExtensionData / ExtensionDataInit —— session、thread、turn 等 scope 的类型化私有状态。
  • ThreadLifecycleContributor / TurnLifecycleContributor —— start、resume、idle、stop、abort、error 等宿主生命周期 gate。
  • ToolContributor、ContextContributor、McpServerContributor 等 —— 在不暴露 core runtime 对象的前提下贡献工具、上下文和服务。

源码中的 memories、web-search、image-generation、goal、guardian 等内建扩展使用它。亮点是宿主只给稳定标识和受限 capability/store，不把整个 Session 暴露给扩展；但不能据此声称所有 marketplace plugin 或第三方 skill 都直接实现这套 Rust trait。

5.4 codex-features（2.7k 行）—— Feature Flag 系统

Codex 有一套运行时 feature flag 系统。可以在配置里开关：

  • multi-agent v2（多 agent 协作）
  • code-mode（代码执行模式）
  • realtime conversation（实时语音对话）
  • managed network proxy（托管网络代理）

这解释了为什么 core 有 18.8 万行——很多功能是条件编译 + 运行时 flag 双重控制的，代码里充满了 if Feature::X.enabled() 分支。
