④ V2：先可靠接单，再安排执行

V2 的核心升级不是换 Effect 写法，而是把 prompt admission、执行所有权、provider turn 与事件投影切成可恢复边界。

Durable admission

SessionV2.prompt() 在 uninterruptible 区域内完成四件事：验证 session、解析 prompt、生成/接收 message ID、发布 PromptAdmitted。projector 同步把它投影到 session_input，带 admitted_seq；只有 durable fact 成立后，才调用 SessionExecution.wake()。

HTTP prompt
  → SessionV2.prompt
  → PromptAdmitted (durable aggregate sequence)
  → session_input(admitted_seq, delivery, promoted_seq=NULL)
  → advisory wake
  → runner 在安全边界发布 Prompted
  → projector 生成用户 message 并写 promoted_seq

相同 message ID 重试时，SessionInput.admit() 返回已有记录；上层比较 session、prompt、delivery 是否完全等价，不等价则 PromptConflictError。这把网络重试从“可能重复发消息”变成有条件幂等。

证据：packages/core/src/session.ts:360-386；session/input.ts:41-81；session/projector.ts:350-375。

steer 和 queue 的 durable 语义

delivery何时 promote循环行为
steer（默认）当前 provider/tool 边界后的下一次可见点；批量 promote 截止序号前所有 steers重置 step 为 1，并在当前 drain 仍需 continuation 时优先进入上下文
queue当前工作本可 idle 时，每次只 promote 一个 queue，再合并此前 steers形成下一段任务；处理完再检查下一 queue

这比内存数组更严谨：pending、promoted、顺序和 delivery 都可在 SQLite 中审计。resume:false 允许只 admit 不 wake，用于批处理或外部调度。

证据：packages/core/src/session/input.ts:245-287；session/runner/llm.ts:173-203,383-405。

SessionRunCoordinator：同 session 串行，不同 session 并行

coordinator 的 active: Map<SessionID, Entry> 为每个 session 持有 owner fiber 和 done Deferred。显式 resume 若已有执行就 join；wake 在执行中只设置一个 pendingWake，多次通知合并；当前 drain 成功后若 pendingWake 为真，启动 successor。interrupt 只打断本进程拥有的 active fiber，idle/missing 是 no-op。

执行层拿到 session 后才从 SessionStore 读取 location，再通过 LocationServiceMap.get(session.location) 注入 runner 服务。这为未来远端 placement 留了 seam；当前注释明确说 local coordinator 仍是 process-local，不应声称已经有集群 lease。

证据：packages/core/src/session/run-coordinator.ts:5-104；session/execution/local.ts:10-44。

V2 provider/tool loop

SessionRunner.runTurnAttempt() 每次都检查 Location ownership、选择 agent、初始化/刷新 Context Epoch、重载 runner history、解析 model 和 tool definitions，然后严格调用一次 llm.stream(request)。LLMEvent 先按顺序 durable publish；非 provider-executed tool call 在记录完成后立即 fork 本地 settlement，所有 tool fibers settle 才能进入下一 provider turn。

runTurnAttempt
  → promote durable input
  → ContextEpoch + History + Model + Tools
  → compactIfNeeded
  → capture start snapshot
  → exactly one llm.stream(request)
  → ordered EventV2 publication
  → tool call durable record → eager local settle fibers
  → await all tools → Step.Ended + snapshot/files
  → needsContinuation ? next provider turn : boundary check

工具可以并发完成，但 publish 由一个 Semaphore 串行化，避免 message projector 接收乱序生命周期事件。中断、provider error、用户拒绝都会补失败尚未 settle 的工具；step 上限时直接不 materialize tools，并把 toolChoice 设为 none。

证据：packages/core/src/session/runner/llm.ts:173-348,383-405。

System Context Epoch：把环境变化也做成可比较状态

V2 不再只在每轮拼字符串。每个 context source 有稳定 key、typed codec、load、baseline、update 和可选 removed rendering；首次生成同时持久化 exact baseline 与 structured snapshot。后续 reconcile 可产生：

  • Unchanged：继续沿用当前 generation；
  • Updated：以明确 update text 追加变化并保存新 snapshot；
  • ReplacementReady：schema 不兼容时建立全新 baseline；
  • ReplacementBlocked：旧 source 暂时不可用时不静默丢失上下文。

这很适合 AGENTS.md、skills、references、工作区状态：模型看到的不只是“最新字符串”，系统还能证明这个 turn 基于哪一版环境事实。

证据：packages/core/src/system-context/index.ts:5-89,134-214,217-290；session/context-epoch.ts。

实现完成度审计

已实现尚未完整实现
durable prompt admission 与幂等冲突检测进程崩溃后的 provider continuation 自动恢复策略
steer/queue promotion 与 per-session coordinator集群级 execution ownership / remote placement
LLM event、reasoning、tool lifecycle 的增量持久化snapshot、patch、retry notice 的全面增量持久化
本地 tool eager execution、settlement、continuation完整 plugin/progress/attachment/cancellation context

prompt、history、events、revert 等 server APISessionV2.shell/skill；部分 wait/operation 路径仍报 unavailable
恢复边界：durable admission 保证“任务已被系统接受”，不自动保证崩溃在任意 provider/tool side effect 中间后都 exactly-once 恢复。源码明确把 post-crash continuation recovery 留给后续设计；当前 coordinator 的 drain identity 也不是 durable record。
判断：V2 已经是可运行的新内核切片，不是 PPT；但它的可靠性承诺目前止于 durable acceptance、投影和受控 continuation，尚未覆盖任意崩溃点的完整恢复。
