② 工具、权限与子 Agent

工具注册是开放的，权限规则是 last-match；但它们提供的是应用层准入，不等于 OS 级隔离。

工具从哪里来

ToolRegistry 把四类来源合并：内建工具、配置目录下 {tool,tools}/*.{js,ts}、外部 plugin hooks、MCP tools/resources。内建主集合包括 shell、read、glob、grep、edit/write 或 apply_patch、task、webfetch/search、todo、skill、question；LSP、plan、code mode 受 feature flag/client 条件控制。

模型也会改变工具面：GPT 新模型偏向 apply_patch，这时隐藏 edit/write；web search 是否可见取决于 provider/flag；code mode 只有存在可见 MCP catalog 时才物化。注册表还允许 tool.definition plugin hook 改写描述和 schema。

证据：packages/opencode/src/tool/registry.ts:58-114,116-253,260-319。

执行包装器：hook、状态、附件和截断

ToolRegistry.tools()
  → SessionTools.resolve()
  → ProviderTransform.schema(model, tool schema)
  → AI SDK tool({ execute })
      → tool.execute.before hook
      → item.execute(args, Tool.Context)
      → attachments 赋予 part/session/message ID
      → tool.execute.after hook
      → processor 更新 ToolPart

Tool.Context 带 session/message/call ID、AbortSignal、agent、历史消息，并提供 metadata() 与 ask()。所以工具不仅返回文本，也能在执行途中更新 title、diff、diagnostics、附件等 UI 元数据。

插件工具仍兼容 Zod 参数，但 registry 在边界保留原始 JSON Schema；输出统一经过 truncate，大结果写到持久输出文件，再在上下文中留下摘要和 outputPath。

证据：packages/opencode/src/session/tools.ts:41-134；tool/registry.ts:116-175；tool/truncate.ts。

权限算法：多个 ruleset 展平，最后匹配者获胜

evaluate(permission, pattern, ...rulesets)
  = rulesets.flat().findLast(
      rule => wildcard(permission) && wildcard(pattern)
    )
  ?? { action: "ask", pattern: "*" }

这意味着规则顺序就是优先级。一次工具调用可以提交多个 pattern；任一 pattern 命中 deny 立即失败，全部 allow 直接执行，只要出现 ask 就发布 permission.asked 并等待 Deferred。用户回复 once 只放行当前请求；always 把规则加入当前 instance 的内存 approved 集合，并自动放行同 session 中已 pending、现在全部匹配的请求；reject 还会拒绝同 session 其他 pending 请求。

“always”不是无条件永久配置。这里的 approved 存在 InstanceState 内存中；V2 另有 PermissionSaved 数据模型。阅读 UI 的“总是允许”文字时，必须分清当前 runtime 和持久规则来源。
证据：packages/opencode/src/permission/index.ts:28-37,67-167。

默认 Agent 权限

Agent默认策略用途
build* allow；doom_loop、外部目录、敏感 .env 读取 ask；question/plan_enter allow默认可修改仓库的主 Agent
planedit deny，仅计划目录例外；限制 general task；plan_exit allow只读分析与写计划
general继承默认，作为 subagent；自身 task/todo 有额外约束多步通用子任务
explore先 * deny，再允许 grep/glob/list/bash/web/read 等只读探索面快速代码库探索
compaction/title/summary* deny隐藏的内部模型任务

用户配置最后 merge，因此可以覆盖默认项。外部目录默认 ask；skill、reference 和 truncate 输出目录被白名单化。敏感 env 文件默认 ask，而 *.env.example allow。

证据：packages/opencode/src/agent/agent.ts:98-310。

文件写入的并发与反馈

EditTool 对规范化绝对路径使用进程级 Semaphore(1)，在锁内读取、精确/模糊替换、生成 diff、询问权限、写文件和格式化，避免同一进程两个 edit 互相覆盖。写后发布 filesystem/watcher event，并触发 LSP；诊断随 tool result 回给模型。

这是很好的同路径串行化，但不是事务：权限批准后到写入期间仍可能有外部进程修改文件；snapshot 用于 diff/revert 证据，不把任意多工具批变成原子提交。

证据：packages/opencode/src/tool/edit.ts:35-45,69-213。

Task 工具：子 Agent 是子 Session

TaskTool 先沿 parentID 计算深度，默认上限 1；权限通过后选择 subagent，并创建带 parentID 的 child session。子会话继承经过推导的权限，还会默认禁用递归 task 和部分 primary-only tools。同步任务直接 await 子 session prompt，后台任务则注册 BackgroundJob，完成后向父 session 注入 synthetic prompt。

后台 subagent 受实验 flag 控制；已有 child session ID 可以继续任务。它不是共享同一 transcript 的“函数调用”，而是有独立消息历史、模型、权限和可导航 UI 的会话树节点。

证据：packages/opencode/src/tool/task.ts:81-300；background/job.ts。

安全边界的准确说法

OpenCode 源码没有内建 Codex 那样的 bwrap/seccomp/Seatbelt 执行层。“project sandboxes”在这里主要指 worktree/workspace 隔离与远端 workspace routing，不应理解为本地 shell 的 OS 强制沙箱。shell、插件和自定义工具继承 OpenCode 进程权限；权限 popup 能防止合规路径上的误执行，但恶意插件或绕过工具层的代码不受它约束。

因此风险从低到高可分为：工具 schema 校验 → wildcard permission admission → external-directory/path checks → 同路径锁/snapshot → 宿主 OS/容器。OpenCode 原生覆盖前四层的一部分，真正强隔离需要容器、远端 workspace 或外围运行环境。

判断：OpenCode 的工具系统强在“开放注册 + 细粒度状态 + 可组合准入”；安全模型则更接近 Claude Code/Pi 的进程内治理，而不是 Codex/Gemini CLI 的显式 OS sandbox 层。
