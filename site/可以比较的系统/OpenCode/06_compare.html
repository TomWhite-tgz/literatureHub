⑥ OpenCode 的突出优点与 AutoResearch 借鉴

按同一口径比较 loop、执行治理、持久化、多 Agent、上下文和接入层；把可迁移机制与不该照抄的迁移复杂度分开。

七个突出优点

  1. Server-first 的多前端一致性。本地 in-process fetch 和远程 HTTP 共用 API；TUI、run、Web、Desktop、ACP 不各自重写 agent loop。
  2. 流式状态足够细。message/part/tool lifecycle 持续投影，权限、question、reasoning、diff 和 token 都可被 UI/插件观察。
  3. 工具生态开放。builtin、目录工具、plugin tools、MCP 和 code mode 汇入同一 schema/execute 边界。
  4. 权限规则可组合。agent、用户、session 临时规则按顺序 merge，last-match 使特例覆盖通配规则，ask/once/always/reject 有明确状态机。
  5. 子 Agent 是真正的会话树。独立历史、模型、权限、深度控制和后台生命周期，比往父 transcript 塞角色前缀更清楚。
  6. V2 durable admission 很扎实。先记录接单事实，再 wake；重试用稳定 ID 对账，steer/queue 也是数据库状态，而非易丢内存队列。
  7. System Context 可审计。baseline、typed snapshot、update/removal 与 unavailable 语义，让环境变化成为 durable context epoch。

OpenCode 特别适合借鉴的地方

1. 把任务接受与任务执行拆开

AutoResearch 的实验请求应先写 run_input_admitted，返回稳定 input ID，再由 scheduler wake。客户端重试必须携带同一 ID；内容、run、delivery 任一冲突就拒绝。这样“用户是否成功提交实验”不依赖模型进程是否恰好在线。

2. 区分 steer 与 queue

科研任务中，“立即修正当前假设”和“等本轮实验后再做新分析”不是同一种消息。采用 OpenCode 的 durable delivery：

steer: 下一安全边界进入当前 run，重置 decision-step budget
queue: 当前 run 本可结束时一次提升一个，成为后续工作单元

3. Event 与 Projection 分层

把模型调用、检索、代码改动、实验、指标、人工审批写成 immutable run events；再投影成 timeline、artifact table、cost summary、paper evidence graph。UI 或查询模型变化时重建 projection，不篡改原始实验事实。

4. Context Epoch

把 dataset version、代码 commit、环境 lockfile、检索语料 cutoff、实验设备和 rubric 做成 typed context sources。每轮记录 baseline snapshot；发生变化时产生明确 update 或 replacement generation。它比在 prompt 里默默塞“当前环境”更适合可复现科研。

5. 子任务用 child run/session

文献检索、代码实现、实验执行、统计审计各自拥有 child run、权限、artifact 和预算；父 run 只接收结构化 summary + evidence refs。后台完成通知应成为 synthetic durable input，而不是 UI 内存 toast。

6. 工具输出双通道

小摘要进入模型上下文，完整日志/表格/checkpoint 写 artifact store，并把 content hash、path、mime、producer event ID 放入 metadata。OpenCode 的 truncate/outputPath 已有雏形；科研系统还应增加不可变 hash 和 lineage。

不要直接照抄的部分

  • 不要同时维护两套长期内核。OpenCode 的双轨是迁移现实，不是理想终态。AutoResearch 应先定义 event/inbox 不变量，再让旧入口通过 adapter 进入同一 runner。
  • 不要把 permission 当 sandbox。危险实验、外网、凭据和数据删除要有容器/VM、网络策略和只读挂载；应用层 ask 只负责意图准入。
  • 不要把 UI schema 当科学证据 schema。message/part 很适合呈现，但 claim、dataset、metric、artifact、negative result、review decision 应是独立 domain types。
  • 不要默认所有插件可信。研究插件应声明 capabilities；无签名的本地 JS/TS 插件不能直接继承宿主 secret 与 shell。
  • 不要只做 process-local coordinator。单机可用 per-run fiber map；跨节点需要 durable lease、heartbeat、fencing token 与幂等 side-effect protocol。

最终评价

OpenCode 是目前这组系统里最鲜明的“产品型 coding agent 向 durable service runtime 演进”案例。它的 V1 已有成熟工具、权限、多 provider、多前端和会话体验；V2 则把可靠接单、event sourcing、Location ownership 与上下文版本化推进到代码层。最应借鉴的是这些不变量，而不是 36 个 package、双插件系统和 V1/V2 并存本身。

一句话：如果 Codex 最强的是事件流内核与执行隔离，Pi 最强的是小内核，OpenCode 最有启发性的地方就是：把一个已经很重的本地产品，逐步改造成“输入先落盘、执行可调度、状态可投影、多客户端共享”的服务内核。
