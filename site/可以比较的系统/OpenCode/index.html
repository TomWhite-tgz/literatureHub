先说结论

OpenCode 当前最值得研究的是渐进式内核替换：可用产品仍由 packages/opencode 的 SessionPrompt.runLoop 驱动；与此同时，packages/core 已经长出独立的 V2 会话运行时，用 durable event + projector + inbox 把“接受用户输入”和“执行模型调用”拆开。两套实现共享数据库、事件与部分类型，却有不同的调度不变量。

一句话架构：当前主线是 CLI/TUI/App/ACP → HTTP API/SDK → SessionPrompt → SessionProcessor → LLM(AI SDK/native) → ToolRegistry；新主线是 Protocol → SessionV2.prompt(admit) → SessionExecution.wake → SessionRunner → EventV2 → Projector。

证据边界：不要把 V1、V2 和产品 UI 混成一层

层当前证据可以下的结论
V1 产品循环packages/opencode/src/session/*，默认 CLI 入口仍从 packages/opencode/src/index.ts 启动可完整解释现有 prompt、tool、permission、compaction、subagent 行为
V2 会话内核packages/core/src/session/* 已实现 durable prompt、runner、tool settlement、compaction、event projection不是空设计；但 post-crash continuation、增量 snapshot/patch/retry、部分 shell/skill/wait API 尚未完成
新包边界schema → core/protocol → server，另有 client、sdk-next、cli、tui仓库正在从旧的“大 opencode 包”向可嵌入分层迁移，不能把新 cli 包当成当前 opencode 二进制的唯一入口
关键审计结论：V2 的 runner 注释逐项列出了已完成与未完成项；源码还让 SessionV2.shell()、skill() 直接返回 OperationUnavailableError。因此本系列只把 durable admission、event projection、provider/tool loop 等写成已实现，不把完整崩溃恢复和全部产品能力写成既成事实。

最值得记住的五个判断

  • OpenCode 是 server-first，而不是 TUI-first。TUI、本地 run、远程 attach、Web 和 ACP 最终都围绕同一会话 API/事件面组织。
  • 当前 V1 也不再只是 JSON 文件存储。Session 更新先发布事件，再由 projector 写 SQLite；旧 Storage 主要承担迁移和其他遗留数据。
  • 权限是语义准入，不是 OS 沙箱。默认 build agent 大体允许工具，但敏感路径、外部目录与 doom loop 会 ask；进程本身仍继承宿主权限。
  • V2 把“收到任务”做成 durable fact。prompt 先产生 PromptAdmitted 和 inbox 行，再 advisory wake；这比把用户输入直接塞进内存队列更适合可靠服务。
  • 双轨迁移也是主要复杂度来源。V1/V2 类型、桥接事件、旧/新 server 和 plugin runtime 同时存在，阅读时必须始终问：这条代码属于当前产品路径，还是目标内核？
