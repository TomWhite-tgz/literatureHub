⑦ V2 尚未完成什么，以及应该怎样完成

这里的“未完成”特指 OpenCode 上游 V2 新内核尚未达到 V1 产品能力与生产可靠性的部分，不代表前六篇文档遗漏。以下逐项对照源码 TODO、官方规格和测试。

证据优先级 运行代码 ＞ 测试 ＞ specs/v2/session.md parity 表 ＞ specs/v2/todo.md 路线图 · 快照 d90532a595

结论：不是一个 TODO，而是五类缺口

V2 已经能可靠接收 prompt、执行 provider/tool loop、投影 durable history、自动压缩并处理中断；但它还不能完全替代 V1。缺口集中在五个层面：模型可见上下文 parity、完整工具生态、运行状态与背压、崩溃/集群恢复、产品 API 与后台维护。

量化：specs/v2/session.md 的 V1 Runtime Context Parity 表共有 21 项：3 项 complete、8 项 partial、10 项 missing。这个表只统计 model-visible context；再加上 runner、工具、恢复和 API TODO，距离切换默认产品路径仍有明显工作量。

五、最难的部分：崩溃恢复不能靠“再 wake 一次”

进程崩溃时至少有五种不同事实：

A. prompt 已 admit，尚未 promote                 → 可安全继续
B. prompt 已 promote，尚未 dispatch provider      → 理论可继续，但要有准备标记
C. provider request 可能已发出、无 durable output  → 结果未知，盲重试可能重复计费/副作用
D. tool call 已 durable，tool side effect 状态未知 → 不能自动 replay 非幂等工具
E. tool result 已 durable，缺下一 provider turn    → 可恢复 continuation，但要证明边界

当前 runner 会在显式继续前把旧的 pending/running tools 标成 interrupted，避免静默重放；但不会在启动时自动推断 C/D/E。官方规格要求把 retry 与 abandon 变成显式决定，并同时设计 provider-dispatch ambiguity、required continuation、queued/steer assignment、retry budget、backoff、visible recovery status 和 startup discovery。

正确目标不是笼统 exactly-once。网络模型调用和外部工具无法普遍 exactly-once。可证明的语义应是：durable input at-least-once admitted；每次 side-effect attempt 有稳定 identity；幂等操作可受限自动 retry；未知结果进入 recovery_required，由用户或策略选择 retry/abandon/reconcile。

六、集群所有权需要 lease + fencing，而不只是分布式锁

当前 SessionRunCoordinator 只保证同一进程内每 session 一个 drain。若两个 server 指向同一 SQLite/远端数据库，各自都可能认为自己是 owner。完整多节点方案至少需要：

  1. 按 Session 获取带期限的 durable lease，记录 owner_id、epoch/fencing_token、expires；
  2. 所有 provider attempt、tool settlement、promotion 在提交前校验 fencing token；
  3. 续租失败立即中断本地 fiber，旧 owner 的迟到写入被 projector/store 拒绝；
  4. replay consumer claim 与 execution ownership 使用不同表/namespace，不能混用；
  5. Location move 或 runtime replacement 提升 epoch，使旧 Location 的执行失效。

这也解释了源码为何只写“future remote placement”：LocationServiceMap 提供服务注入边界，但不是调度器、lease manager 或远程 RPC 本身。

八、已有测试证明了什么，没证明什么

当前测试面相当扎实：

  • session-prompt.test.ts 覆盖 durable admission、精确重试、冲突、并发 promote、resume=false；
  • session-run-coordinator.test.ts 覆盖 join、wake coalescing、interrupt race、不同 session 并发；
  • session-runner.test.ts 覆盖 context epoch、自动/overflow compaction、tool settlement、steer/queue、provider failure 和中断；
  • session-projector/history 覆盖 aggregate 顺序、cursor pagination 和 projection；
  • session-runner-tool-registry.test.ts 覆盖 scoped overlay、stale call、codec 和 output bounding。

它们能证明当前单进程 V2 slice 的局部不变量，不能证明多进程 ownership、kill -9 恢复、远端 placement、所有 V1 context parity、插件/MCP parity 或真实 provider 全矩阵。绿色测试不能把规格中明确的 missing 变成 complete。

最终判断

V2 的剩余工作并不是“把四个 unavailable 函数接上线”这么简单。真正的切换门槛是：请求语义与工具生态达到可接受 parity；单机运行状态闭合；未知 side effect 有显式恢复策略；最后才引入集群 ownership。现有 durable inbox、EventV2、projector、Location scope 和 canonical Tool Registry 已经打好了底座，后续最忌讳的是绕回 V1 loop 或为了快速上线再造第二套临时抽象。

主要证据：specs/v2/session.md、specs/v2/todo.md、specs/v2/tools.md、packages/core/src/session/runner/llm.ts、packages/core/src/session.ts、packages/core/src/tool/* 及相应测试。
