① 启动与插件树：配置就是运行时拓扑

理解 DSH 的第一步不是找 main loop，而是先看 profile 最终挂载了哪些服务，以及这些服务何时生效、何时撤销。

从命令行到 Cordis Loader

bin.ts 解析 argv→动态 import 对应 mode→composeProfile()→boot()→Loader 挂插件树

bin.ts:27-66 的 switch 分派 profile/run/web/plugin/dump-config。这里用动态 import()，所以 headless 不会先加载 Web，plugin 管理也不会把 Agent 运行时拖进来。invocation satisfies never 是编译期穷尽检查：将来给联合类型新增 mode 却忘记补 case，TypeScript 会报错。

switch (invocation.mode) {
  case 'run': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({ ... })
    break
  }
  default:
    invocation satisfies never
}
证据：apps/cli/src/bin.ts:27-66。

profile 不是一份配置，而是有优先级的 patch 栈

composeProfile() 按固定顺序合成：bundle layers → profile 自己的 cordis.patch.yml → $DSH_HOME/cordis.patch.yml → 多个 --patch → CLI flag patch → telemetry 开关。后出现的层覆盖前面的同 id row。注意 patch 替换的是该 row 的整个 config，不是深合并。

return [
  ...bundlePatches,
  ...profile.patches,
  ...homePatches,
  ...overlayAndFlags,
]

启动时会把 profile 根 cordis.yml 重写成空数组，因为真正的树完全由 patch 构造；否则 Loader 的 tree write-back 可能把已组合行烘焙进根文件，下一次启动重复插入。长运行 profile 又通过 HMR 重新读取用户层，并在每代 structuredClone()，防止 Loader 就地修改 insert 对象导致“删除 override 后默认值回不来”。这是配置系统中很具体的引用别名防御。

证据：apps/cli/src/profile-boot.ts:53-61,92-96,120-152,208-273。

base bundle 才是默认产品

包存在不代表默认启用；packages/bundle/base/cordis.patch.yml 才是 shipped composition 的权威入口。它挂载核心 llm/session/agent/tools/system-prompt/agent-loop，同时装上 JSONL persistence、sandbox/approval、filesystem、skills、goals、plan、compaction、subagents、workflow、web search、timeout、spill 与 telemetry。Web bundle 再叠加 API gateway、webserver 和几十个 browser plugins；headless bundle 叠在 base + web 上，只增加 one-shot runner 并把 webserver 设为随机端口。

审计要点：仓库中有 MCP、LSP、PTY、多个 web fetch provider，并不等于默认 profile 全部开启。比如 base 明确只开 web_search，关闭 fetch；注释说明 fetch 的 SSRF 防护仍待解决。判断能力必须看最终 row，而不是目录名。
证据：packages/bundle/base/cordis.patch.yml:15-425；packages/bundle/web-app/cordis.patch.yml；packages/bundle/headless/cordis.patch.yml。

Cordis 的五个概念如何落在源码里

概念DSH 写法运行含义
Serviceclass AgentLoop extends Service构造后占据稳定的 ctx.agentLoop
依赖注入static inject = ['agents','sessions','llm','tools','systemPrompt']依赖没就绪就不激活，不靠 YAML 行顺序
Contextctx.tools、ctx.llm、agent.ctx服务容器，也承载作用域与事件分派
Effectctx.effect(() => disposer)注册与撤销绑定，插件 reload 时能清理
Typed eventemit / waterfall / serial / parallel观察、拦截、串行 barrier、并行 fan-out 是不同契约

最容易读错的是 waterfall。监听器不是收到一个“最终值”再改，而是环绕中间件：调用 next() 才委托下游；直接 return 就短路。工具审批可用它 deny/ask，请求事件可用它改模型 route，agent/pre-step 可 reject 或重写进入步骤的消息。

证据：docs/cordis-primer.zh.md:7-48；packages/core/agent-loop/src/index.ts:276-315。

生命周期不是“new 完就算成功”

Agent 创建被拆成 prepare → setup → publish。prepare 先融合 caller cancel、owner fiber unload 与 factory teardown 三个 AbortSignal，再建立一个 memoized 反向 disposer；setup 可异步给私有 agent.ctx 装工具/提示词；publish 才依次进入 session registry、agent registry，发 created/session-start。失败会按反序停止 machine、等待 idle、释放 scope、退出 registry。

prepare resources
  → setup(agent.ctx)
  → enter session
  → enter agent
  → announce session
  → announce agent
  → agent/session-start

dispose: cancel → whenIdle → scope.dispose → detach agent → detach session

这比普通 DI 容器多做了一层“未发布资源事务”：异步 setup 期间外界还看不到半成品 Agent，而 owner 在 setup 中途销毁也不会泄漏。Promise.withResolvers() 用来显式持有 promise 的 resolve/reject；??= 把多方 teardown 收敛到同一个 Promise。

证据：packages/core/agent-loop/src/index.ts:38-89,414-539,567-670。
架构判断：DSH 的真正“主程序”是组合结果，不是某个巨大类。Cordis 使一个部署可以通过替换 row 改后端、通过事件加策略、通过 agent scope 加私有能力；代价是控制流同时分布在 YAML、Service 构造器、event listener 和 disposer 中，阅读时必须从最终 composition 反向追服务。
