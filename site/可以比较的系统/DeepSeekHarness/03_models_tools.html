③ 模型与工具：loop 只消费契约

模型 route 属于 adapter registry；工具能力、策略、审批、执行与结果整形属于 ToolRegistry；Agent loop 不知道 DeepSeek HTTP 或 Bash 的细节。

LLM seam：provider 名称映射到注册实例

LlmService 内部维护 Map<provider, AdapterRegistration>。adapter 只必须实现 stream()，也可提供 provider display metadata、retry policy、model catalog 与 exact-model capabilities。注册是 all-or-nothing，并返回同时可调用的 disposer；handle 上的 replace() 原子替换 route 集合，使动态 settings 更新不会出现短暂的“无 adapter”窗口。

abstract class LlmAdapter {
  providerInfo(provider: string): LlmProviderInfo
  listModels(provider: string): Promise<readonly LlmModelInfo[]>
  resolveModel(provider: string, model: string, signal?: AbortSignal): Promise<...>
  abstract stream(options: GenerateOptions): AsyncIterable<StreamChunk>
}

abstract 表示基类规定接口但不能直接完成核心行为；readonly 约束调用方不可改返回数组；AsyncIterable 让 adapter 自然表达流式 chunk，而无需把网络事件塞进 callback。

证据：packages/llm/llm/src/index.ts:182-292,338-430,768-918。

prepareCall() 是注册绑定点

直接 llm.stream(request) 会在 dispatch 时按 provider 查 adapter；Agent loop 则先用 prepareCall(config)。后者在解析模型默认值和 context window 时就捕获当前 registration，返回 one-shot PreparedLlmCall；其 stream() 要求请求 config 精确匹配且不能复用。这样热更新 adapter 时，已记录的 header 和真正发请求的 adapter 不会分裂。

模型默认 maxTokens 与 reasoning effort 在 seam 中解析：显式不支持的 effort 会拒绝，不做静默 clamp；catalog 缺少模型只代表“不展示”，不能被调用方误用作 routing deny。

证据：packages/llm/llm/src/index.ts:170-180,207-240,720-918；packages/core/agent-loop/src/agent.ts:394-471。

证据：packages/llm/llm-deepseek/src/{adapter,serialize,sse,translate}.ts；packages/llm/llm-pi-ai/src/adapter.ts:1-20,54-75,177-300。

DSH 如何把自己的消息翻译给 Pi

toPiContext() 将 DSH 单个 system option 映射到 Pi 的 systemPrompt；历史中的 system message 因 Pi 只有单一槽位，被折成 user text 以保序。DSH tool-result block 不带工具名，所以转换器先扫描 assistant tool-call，以 CallId → name Map 恢复 Pi 所需的 toolName。这正说明二者的消息协议相似但不相同。

重要边界：DSH 的 llm-pi-ai 包是“design-verification twin”。它复用 Pi 的 provider 生态，但 DSH 的 session event、tool policy、loop retry 和 UI 都留在 DSH 侧；不能据此说 DSH 运行 Pi Agent。
证据：packages/llm/llm-pi-ai/src/context.ts:12-85；packages/llm/llm-pi-ai/package.json:36-38。

工具定义同时服务模型、执行器与 UI

ToolDefinition 不只是 name + execute。它包含模型 schema、execution mode、timeout、结果内容 finalizer，以及展示意图（generic/terminal/diff、locations）。注册表又支持全局与 agent-scoped 两层工具；ToolRestriction 对全局层做 allow/deny 交集，本地 scoped 工具仍可覆盖。prompt assembler 读取当前视图产生模型 schema，executor 在调用点重新读取，避免只靠“没告诉模型”做安全控制。

证据：packages/core/tools/src/index.ts:196-424,613-739,739-1058；docs/core-data-structures/tools.zh.md:9-170。

工具执行是分阶段、单调收紧的 pipeline

lossless JSON snapshot + deepFreeze(arguments)
  → tools/pre-execute waterfall: allow | deny | ask
  → approval service（只有 allowed-once 放行）
  → monotonic guards（只能再 deny，不能反向 allow）
  → tools/execute waterfall（环绕真正 body）
  → tools/post-execute: accept | block
  → definition.finalizeContent
  → deep-frozen tools/result notification

参数只在入口做一次 lossless-JSON 物化，随后冻结；policy 不能偷改模型看到的参数。ask 若没有 approval service、没有 Agent/session 或通道不可用，一律降为 deny。guard 返回 undefined 只能保持已有决策，返回 string 只能拒绝，因此后注册插件不能撤销前面的安全限制。

工具 body 和 listener 抛错通常被 materialize 为 isError result，仍进入 post-execute 并闭合 call/result。只有 scheduler 基础设施失败才上抛到 turn。工具还可 deferContext()，将结构化上下文交给下一 step，而不是把所有机器信息混入用户可见输出。

证据：packages/core/tools/src/index.ts:1086-1460；docs/core-data-structures/tools.zh.md:170-395。

Code Mode 不是另一套工具实现

工具 registry 支持 native/code/both presentation。Code Mode 让模型写一段程序，通过桥接调用已注册工具；每个 sub-dispatch 仍经过同一 ToolRegistry policy、timeout、scope 与 result pipeline，并记录 tool/code-dispatch。所以它改变模型调用工具的表示和批处理方式，不应绕过原有权限边界。

设计判断：DSH 比 Pi 多出来的不是“更多工具名”，而是一条正式的工具治理管线：schema 可见性、运行时 scope、审批、单调 guard、并发分类、结果整形、持久配对和 UI intent 有各自 owner。复杂度更高，但策略不需要侵入每个工具 body。
