⑦ DeepSeek Harness vs Pi：不是“大而全 vs 小而美”这么简单

二者共享 provider/message/tool 的不少设计直觉，但对“运行时应拥有多少协议”给出了相反答案。

一句话定位

Pi

以极小 pi-agent-core loop 和强 pi-ai provider 层为底座，高层 coding-agent 用 AgentSession、JSONL session tree、resource loader 和 extension API 形成产品。优先可读、可嵌入、可自由扩展。

DeepSeek Harness

以 Cordis 服务图和 event-sourced Session 为底座，loop 只是众多插件之一；把持久化、策略、作用域、压缩、subagent、目标、SDK/UI 都纳入可组合协议。优先可替换、可恢复、可审计。

真正相同的设计直觉

  • provider 负责 wire 行为。loop 不应包含某家 API 的序列化、认证和 SSE 细节。
  • 工具可以并行，但给模型的结果必须稳定。两者都不把网络完成顺序误当对话顺序。
  • 上下文不是原始历史的简单尾截断。Pi 用 tree/compaction entries，DSH 用 event surface replacement。
  • stream 必须以闭合终态表达错误/取消。不能让半条 tool call 悄悄变成可执行输入。
  • TypeScript 类型承载协议。消息块、工具 schema、事件和 provider 结果都大量使用 discriminated unions 与泛型。

最根本的不同：谁拥有产品语义

Pi 把最低层 loop 压到很薄：模型、工具与 queue 的正确闭合是核心，高级能力在 coding-agent 和 extension 里。DSH 则认为“会话持久性、策略拦截、作用域与 teardown”也属于 harness 基础协议，但把它们拆成 Cordis plugins，而不是全塞进 loop。

Pi:  tiny loop → Agent → AgentSession → product/extensions

DSH:              ┌─ policy plugins
profile → Cordis ─┼─ AgentLoop ↔ event Session ↔ persistence/projections
                  ├─ capability services
                  └─ Web/ACP/SDK consumers

所以 DSH 并非传统“monolithic big loop”；它的复杂度是横向分布的协议复杂度。Pi 的风险是不同扩展各自实现 policy/durability 后语义分叉；DSH 的风险是理解一个行为必须跨 package、event 和 config row，局部改动也可能触发全局不变量。

一个非常直接的血缘证据

DSH 的 dsh-llm-pi-ai 依赖 Pi 的 pi-ai ^0.82.1。这不是概念类比，而是真实适配：DSH message 转 Pi Context，Pi model events 再转 DSH chunks。适配层特意把内部 retry 设为 0，因为 DSH 的 agent/request-error + llm-retry 拥有用户可见 attempt；credentials 也由 DSH seam 每请求解析后作为 pi-ai 的最高优先级 override 传入。

这个包恰好展示两种架构如何拼接：Pi 更强的 provider 层可以被 DSH 复用，DSH 更强的 runtime/durability 层无需接受 Pi 的 AgentSession。

证据：packages/llm/llm-pi-ai/package.json:36-38；packages/llm/llm-pi-ai/src/{adapter,context,stream}.ts。

对 AutoResearch 最值得组合的部分

  • 从 Pi 借小而确定的执行内核与 provider-owned wire conversion，避免科研策略污染每次模型调用。
  • 从 DSH 借权威事件日志 + 可替换 reasoning surface，让原始证据、模型上下文和压缩摘要分层。
  • 从两者共同借并发执行、稳定提交：搜索/实验按 action ordinal 归并，而非完成时间。
  • 从 DSH 借capability seam 与单调 policy：搜索源、代码执行、实验平台、审批和 sandbox 各有 owner。
  • 谨慎控制 DSH 式包/事件数量：只有确实需要独立替换、生命周期或持久协议的能力才升格为 Service；普通内部函数不要插件化。
最终判断：Pi 展示了一个 Agent 内核能有多薄；DSH 展示了当产品要求热组合、审计、恢复、多 Agent 和多前端时，复杂度应如何被结构化地放到 loop 外。最有价值的比较不是评谁“更先进”，而是看清何时简单性本身是正确边界，何时简单只是在把策略与失败语义推给每个调用方。
