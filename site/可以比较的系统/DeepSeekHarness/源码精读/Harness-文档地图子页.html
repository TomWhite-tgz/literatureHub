0 · 这页解决什么

主导读 §13 学习路径 已经给了一条读代码的路线。这一页补的是另一件事：在读代码之前，先看清仓库自己的文档地形。因为 docs/ 有三个非直觉之处，不知道会白走路。

陷阱 1

中文版存在，但不显眼

所有手写文档都有 .zh.md。主导读全篇引用的是英文名（docs/architecture.md），很容易以为没有中文版——其实 architecture.zh.md 就在同一目录，内容对等。

陷阱 2

生成物和手写物混放

docs/ 顶层 18 篇 .md 里，9 篇是机器生成的，和手写的并排躺着、扩展名一样。改错了会被 gate 打回，而且下一次 gen-* 直接覆盖你的编辑。

陷阱 3

四条学习线互不引用

Cordis 在这个仓库里被讲了四遍，四份材料风格、体量、语言、可执行性全不同，而且彼此几乎不交叉引用。不知道有四条，就会以为自己读的那条是全部。

1 · 四条平行的 Cordis 学习线

这是这一页最重要的一节。同一个 Cordis，仓库里有四份材料在讲，其中第 ④ 条主导读完全没有提到。

1.1 ④ 号线：被漏掉的那条中文原生材料

docs/user/develop/ 是一条面向插件开发者的完整教程，9 篇、1,211 行、全部双语，分三组：

framework/ 那三篇（427 行）和 Cordis 内核子页 讲的是同一批概念，但角度不同：子页是拆源码，它是给使用者的精确说明。而且它有一处比我在子页里写得更准——

一条值得单独记住的语义，出自 develop/framework/index.zh.md:63：

「插件卸载时，处置器按注册顺序的逆序开始调用，但多个异步处置器会并发执行，不保证逐个完成。存在顺序依赖的清理步骤必须放进同一个 ctx.effect() 返回的处置器中，由该处置器负责串行等待。」

我回源码核对过，这句是对的，而且比常见的说法"disposer 逆序执行"精确得多。证据在两处：vendor/cordis/src/utils.ts:28-32——DisposableList.clear() 返回 values.reverse()，所以确实是逆序；vendor/cordis/src/fiber.ts:674——await Promise.all(this._disposables.clear().map(async dispose => …))，Promise.all 意味着全部并发等待，没有任何东西让第 N 个等第 N-1 个跑完。

顺带还有第三个事实：fiber.ts:675-683 每个 disposer 各自包在 try/catch 里，异常只 ctx.logger.error(reason)。所以一个 disposer 抛异常既不会中断其他 disposer，也不会让卸载失败。这是"卸载必须永远成功"的实现代价：错误被降级成日志。

⚠ 这一条已回填到 Cordis 子页 §3.2，原先那里写的"逆序跑 disposer"不够准确。

2 · 中文版地图：一条零例外的规律

手写的一定有中文，生成的一定没有

我把 docs/ 顶层 18 篇 .md 逐一核对过：9 篇手写的，9 篇全部有 .zh.md；9 篇生成的，9 篇一个都没有。子目录同样成立——core-data-structures/ 32 篇英文对 32 篇中文，cordis-tutorial/ 8 对 8，cookbook/ 7 对 7，postmortem/ 4+README 全双语，user/ 整棵树全双语；而 cordis-catalog/ 一篇中文都没有。

规律背后是制度：仓库的 i18n 契约要求双语成对更新并重新录制（docs/i18n/README.md，由 verify-translation-pairing 把关），机制是 .md / .zh.md / .i18n.yaml 三元组——第三个文件记录录制状态。生成物没有"翻译源"这个概念，所以整个机制不适用于它们。

3.1 verify-* 就是 gen-* --check

看 package.json:97-115 会发现一个统一的形状：

"gen-cordis-catalog":    "tsx scripts/gen-cordis-catalog.ts",
"verify-cordis-catalog": "tsx scripts/gen-cordis-catalog.ts --check",
"gen-tool-catalog":      "tsx scripts/gen-tool-catalog.ts",
"verify-tool-catalog":   "tsx scripts/gen-tool-catalog.ts --check",
"gen-doc-graphs":        "tsx scripts/gen-doc-graphs.ts",
"verify-doc-graphs":     "tsx scripts/gen-doc-graphs.ts --check",

校验的方式就是重新生成一遍再比对。这意味着生成物不可能相对生成器漂移——只要 pnpm run doc-sync 过了，磁盘上的内容必然等于当前代码投影出来的内容。这是这套文档体系可信度的来源。

一个容易记错的细节：gen-cordis-api 不是另一个生成器。scripts/gen-cordis-api.ts 全文只有 9 行，是个兼容入口——import { main } from './gen-cordis-catalog.ts' 然后调用。它自己的 JSDoc 写着 "Compatibility entry point for the unified Typert-backed Cordis catalog projection… all extraction, validation, and rendering live in one implementation."

所以 docs/cordis-catalog/** 和运行时那个 API 模块出自同一次 Typert FaceModel 投影。这就是为什么 cordis_inspect 工具可以拿"提交进仓库的 catalog"去和"运行时真实的 service store"求交集——两边不可能对不上。

3.2 但是：生成 ≠ 正确

生成器只保证"文档与生成器一致"，不保证"生成器与代码语义一致"。

仓库里有一个现成的反例，主导读 §5.4 已经抓出来了：docs/agent-lifecycle.md 把 turn/start 画在 agent/pre-step 之后，并写着 "claimed batch stays removed, no turn opens"。而代码是反的——agent.ts:234 早于 :245，pre-step 拒绝时照样写 turn/end.reason = {kind:'blocked'}。

这个错误能通过所有 gate，因为 verify-doc-graphs 只检查"文件内容 == 生成器输出"。要修得改 scripts/gen-doc-graphs.ts 里那段手工维护的 Mermaid（该文件末尾自己写着 "Maintenance mode: curated Mermaid sequence"——curated 意思就是人手写的）。

因此读法是：生成物当索引和签名字典可以完全信任（它们是机械提取的）；生成物里的"叙事性内容"（时序图、顺序、因果）要回代码核对。

怎么一眼分辨？看第一行。所有生成物都以注释横幅开头，例如：

<!-- Generated by scripts/gen-doc-graphs.ts - do not edit by hand. Run `pnpm run gen-doc-graphs` to regenerate. -->

看到这行就三件事：别手改、没有中文版、叙事部分存疑。

4 · 无 API key 的动手路线

主导读 §13.4 给的三个动手入口（demo:headless / demo:acp / demo:cordis）全都需要 DEEPSEEK_API_KEY。而 cordis-tutorial 这条线不需要——docs/cordis-tutorial/index.zh.md:13-34 明确写了准备工作只有 clone + pnpm install。

# 一次性准备
cd test-skyllwt
pnpm install                       # node ^22.19 || >=24
mkdir -p tmp/cordis-tutorial       # tmp/ 已被 gitignore，可以随便写
cd tmp/cordis-tutorial

# 每一章都是同一条命令
node --import tsx ../../vendor/cordis/bin.js

4.1 那个启动器只有 16 行，全文如下

它值得整篇贴出来，因为这 16 行就是"一个 Cordis 应用的最小可能形态"——vendor/cordis/bin.js：

#!/usr/bin/env node

import { Context } from 'cordis'
import { pathToFileURL } from 'node:url'
import Loader from '@cordisjs/plugin-loader'

const ctx = new Context()
ctx.baseUrl = pathToFileURL(process.cwd()).href + '/'

await ctx.plugin(Loader)
await ctx.loader.create({
  name: '@cordisjs/plugin-include',
  config: {
    path: './cordis.yml',
  },
})
CODE-CONFIRMED

逐行看它做了什么

① new Context() —— 建根上下文，也就是你在 子页 §2 读到的那个 Proxy。② ctx.baseUrl = 当前工作目录 —— 所以"从哪跑"决定"加载谁"，这也是为什么每章都要先 cd 进去。

③ await ctx.plugin(Loader) —— Loader 自己就是个普通插件，装完 ctx.loader 这个服务才存在。④ ctx.loader.create(...) 挂 @cordisjs/plugin-include 去读 ./cordis.yml。

注意第 ④ 步的形状：连"读配置文件"本身都是一个插件（plugin-include），不是启动器的内建能力。

CODE-CONFIRMED

为什么它不需要 API key

这 16 行里没有任何 harness 内容——没有 ctx.llm、没有 ctx.agents、没有 ctx.tools。它只装了 Cordis 内核 + Loader。

整个 harness（@deepseek-ai/dsh-* 那 194 个包）在这条路径上一个都没加载，所以既没有模型请求，也就不需要凭据。你在 tmp 目录里跑的是纯净的 Cordis。

--import tsx 则让 Node 无构建步骤直接执行配置指向的 TS 文件——和 dsh CLI 的源码启动（node --import tsx/esm）同一条路子，因此途中模块必须是 ESM。

4.2 七章顺序，以及每章对应 Cordis 子页哪一节

教程的章序几乎和 Cordis 内核子页一一对应。建议对照读：教程给能跑的最小例子，子页给源码级的"为什么"。

章教你什么对照子页
01-first-plugin插件就是一个函数，由 loader 挂载§6 Registry
02-lifecycle-and-effectsCordis 管理的注册会在插件卸载时撤销；ctx.effect() 包裹外部资源§3 Fiber / effect
03-services在 ctx 上公开能力，用 inject 依赖它§4 Service
04-events类型化事件、广播分发、waterfall 短路§5 Events
05-config读 cordis.yml 校验后的配置，输错要明确报错—（子页未覆盖）
06-composition-and-hmr配置文件即插件树、热重载、诊断"永远加载不上"的插件§7 级联唤醒

第 2 章的例子值得单独看一眼，因为它演示的正是仓库那条铁律「Registrations are effects」。它让你写一个 heartbeat 插件用 ctx.effect() 包一个 setInterval，然后——关键在这里——把 demo 自己用来触发卸载的那个 setTimeout 也包成 effect，注释说明了原因：如果这个插件先被卸载，待执行的回调会被取消，而不是在一个已死的 app 上触发。

这就是"为什么连一次性定时器也要走 effect"的完整答案，而且是能跑出来看的。

第 7 章之后如果想接着玩 demo:cordis（它需要 key），先明白一件事。原文在 packages/cordis/tool-cordis/README.zh.md:87：

「沙箱只用于约束诚实代码，并非安全边界：可以访问沙箱全局变量上的 host realm helper，因此挂载代码可以触达 Node；加载该插件时，应当像授予 bash 工具一样慎重。」

同一份 README 的 :21 补充了机制：Node 全局变量不存在或被重定向到 ctx.fs / ctx.web / ctx.bash，写入 globalThis 保持局部，但 host realm helper 使逃逸成为可能；已挂载插件拿到的是不含框架内部的 façade，而获准的服务仍会影响存活运行时。这句话也硬编码在工具描述里给模型看（tool-cordis/src/index.ts:116）。

换句话说：那个沙箱防的是"模型写错代码"，不是"代码有恶意"。别在不该有 shell 的环境里挂它。
