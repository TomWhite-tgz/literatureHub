DOC-CLAIM

⑤ 注册是可撤销的副作用

prompt section、工具 schema、adapter、provider、listener，一律通过 ctx.effect() / ctx.on() 安装，所以卸载和热重载能可预测地回退。仓库规约把这条写成硬性要求："Registrations are effects: every contribution goes through ctx.effect() / ctx.on(); a registry's register() returns the disposer."（AGENTS.md Conventions）

为什么"注册是副作用"这一条最重要

因为它把"扩展"从永久的全局改动变成了有生命周期的租约。一个 subagent 可以在自己的 agent.ctx 上注册三个私有工具，agent 一销毁全部自动消失；HMR 能热换插件；测试能"注册-断言-销毁"验证没有泄漏。仓库甚至为此设了一条 gate："Registry contributions prove disposal"——每个注册表贡献都必须有一个"销毁 fiber 后观察它消失"的测试。

2.1 四种分发模式：什么时候用哪个

模式是事件公开契约的一部分，新事件必须用 @mode JSDoc 标注，生成的目录会拿声明去核对真实的分发点。这意味着你不能"偷偷换一种方式发事件"。

最容易写错的一件事。仓库规约里有一条用了大写："Waterfall listeners MUST call next() to delegate; returning without it is the veto." 一个只想"顺便记个日志"的监听器，如果忘了 return next(...)，就静默地否决了整条链——模型不会收到工具结果，step 不会进入，而且没有任何报错。这是本仓库唯一一个"写法失误直接变成语义灾难"的地方。

2.2 一个反直觉的 Loader 陷阱

值得单独列出，因为它已经造成过真实事故，并写进了 primer：

# ❌ 永远被禁用，而且不报错
- name: dsh-something
  disabled: !!js process.env.NODE_ENV === 'production'

# ✅ 只有 config 会被插值
- name: dsh-something
  config:
    threshold: !!js Number(process.env.T ?? 8)

@cordisjs/plugin-include 确实会把 !!js 解析成表达式节点，但 Loader 只对条目的 config 做插值。条目元数据（id/name/group/disabled/inject/intercept/isolate）保持字面量——于是 disabled: !!js … 是一个永远为真的对象，条目永远被禁用。环境切换必须用 config overlay（见 §10 的分层机制）。

4 · 数据骨架：为什么整个系统是"事件溯源"的

如果只允许我讲一个子系统，我会选 dsh-session。因为这个 harness 的所有"高级能力"——压缩、fork、回放、崩溃修复、时间旅行查询、审计——都不是各自实现的功能，而是同一个数据结构的自然推论。

一条规约撑起整个数据层

Model-visible ⟺ logged.（模型可见 ⟺ 已记录）任何进入模型请求的东西，都必须能从 session 日志重建；反过来，加一个新的模型可见输入就必须加一个 session 事件。这是双向的等价，不是单向的"最好记一下"。

后果非常具体：为什么 request/header 要把整个系统提示词和工具 schema 都存进日志？因为不存就无法重建那次请求。为什么压缩不能删事件？因为删了就破坏了等价。为什么 todo 列表是 todo/write 事件而不是内存字段？因为它要在 UI 上重放。

4.1 三层数据视图：log / surface / messages

初读代码最容易混淆的是"到底哪个是真相"。答案是三层，各有各的职责：

4.2 SurfaceOp：全仓最优雅的一个类型

export type SurfaceOp =
  | 'append'                                        // 正常追加到尾部
  | { op: 'replace'; start: number; end: number }   // 用本节点替换 [start, end] 闭区间

export interface SurfaceIntent {
  surfaceOp: SurfaceOp
  /** 完整的已知来源集合。assistant/message 可以是"存在但为空数组"（provider 返回空流）；
   *  字段缺失表示"来源未被记录"——这两者语义不同。 */
  sourceEventSeqs?: number[]
}

两行类型定义解决了三个问题：

  • 压缩是替换，不是删除。被遮蔽的节点必须全部出现在新节点的 sourceEventSeqs 里——溯源是强制的，不是可选的元数据。你可以随时问"这段摘要是从哪 20 条消息压出来的"。
  • 类型层面禁止误用。SessionEvent 用条件类型让 surfaceOp 和 sourceEventSeqs 只存在于三种 SurfaceEventType 上。给一个 turn/start 加 surfaceOp 是编译错误，不是运行时校验。
  • "人类逐字稿"与"模型视图"的分离有了明确定义。人类 transcript 要投影 append 来源的事件（看到完整历史），模型侧消费者读 session.surface（看到压缩后的视图）。同一份日志，两种读法。
展开：为什么 SessionEvent 要写成映射类型而不是普通联合？ 
export type SessionEvent<T extends SessionEventType = SessionEventType> = {
  [K in SessionEventType]: {
    type: K
    seq: number
    time: number
    data: SessionEventMap[K]
  } & (K extends SurfaceEventType ? {
    sourceEventSeqs?: number[]
    surfaceOp?: SurfaceOp
  } : object)
}[T]

三个理由，源码 JSDoc 里都写了：

  • 它是 type 上的真·可辨识联合（而不是 type 和 data 两个独立联合的笛卡尔积），所以 switch (event.type) 能不加 cast 地收窄 event.data。
  • 条件交叉把 surface 字段限制在三种事件上，编译器在 Session.append() 调用点就强制这一点。
  • SessionEventMap 是接口，所以能被声明合并。插件加一行 'compact/start': {...}，整个联合、所有 switch 的穷尽性检查、持久化编解码都自动跟上。这就是仓库规约里说的"merge-extensible sum type"模式，全仓复用：TurnEndReasonMap、SessionEventMap、事件表本身都是这个套路。

4.3 request/header：让每一次请求都可重建

这是"Model-visible ⟺ logged"最硬核的落地。每个 step 在真正发请求之前，把完整的请求头写进日志：

interface EpochHeader {
  config: LlmCallConfig                            // provider / model / effort / 采样参数
  adapterDefaults?: LlmCallConfigAdapterDefaults   // 由具体 adapter 落实的字段（不是调用方提议的）
  system?: string                                  // 渲染后的系统提示词全文
  tools?: ToolSchema[]                             // 装配后的全部工具 schema
}
// 事件： 'request/header': { header: EpochHeader; reason: 'initial' | 'resume' | 'change' }

'initial'

日志的第一个头 —— 一段新对话。

'resume'

一个循环实例在已有头事件的日志上发的第一个请求：进程重启、fork seed。

'change'

后续请求用了不同的头（换模型、工具集变了、提示词变了）。

注意这个设计的经济性：头只在变化时才写（靠 canonicalHeader / headerEquals 判等），所以日志不会因为每个 step 重复几 KB 的 schema 而膨胀；但"最新一条快照"永远足以重建当前请求。foldRequestHeader() 就是那个折叠函数。

这一切被一条运行时不变量守着。dsh-agent-loop/invariant（packages/core/agent-loop/src/invariant.ts，63 行）会在真实事件流上断言"每个 step 都能被重建"。仓库规约要求"Runtime invariants assert owned relationships"——检查权威事件流或可变数据的关系，而不是检查"某个方法存在"。每个包都必须有 ./invariant 伴生模块，没有可断言关系的包要写明理由（No runtime invariant: …），空的、没解释的、被忽略的都过不了 verify-package-invariants gate。

4.4 崩溃修复：日志格式如何自我治愈

进程在工具执行到一半时被杀掉，日志里就会留下一个有 tool/call 没有 tool/result 的洞。模型 API 不接受这种消息序列。持久化后端在重载时负责补齐，并且——关键点——补齐的文本是模型可见契约的一部分，被逐字钉死在 README 里：

情形错误码补进日志的模型可见文本
工具体从未开始TOOL_NOT_STARTED告诉模型这次调用没有执行，可以安全重试
工具体可能已经跑了，结果丢失TOOL_OUTCOME_UNKNOWN告诉模型结果未知，重试前需要先核实副作用
崩溃时 turn 未闭合{ kind: 'interrupted' }后端补一个 turn/end；循环自己永远不会发这个 reason，崩溃前的事件保持原样

区分这两个错误码是一个语义设计决定，不是实现细节。"没开始"和"不知道有没有开始"对模型来说是完全不同的两件事——前者可以直接重试，后者必须先查。把这个区别做进错误码，等于把"崩溃恢复的正确性"从人的判断转移到了数据结构上。

    this.dispatch.emit('agent/status', { status })
  }
}

顺带一个小而精彩的细节（agent.ts:92）：turn 编号不是存在内存里的计数器，而是从日志里恢复的——

const lastTurn = session.events.findLast(e => e.type === 'turn/start')?.data.turn ?? 0

于是"进程重启后 turn 号接着数"这件事不需要任何额外机制。这就是事件溯源的复利：只要日志是真相，派生状态永远不需要单独持久化。

5.2 收件箱：一个 2×2 表格解决所有"插话"需求

各种 agent 框架里最容易长成一团乱麻的部分是"用户中途说话怎么办"。这个 harness 的答案是把它归约成两个正交的布尔维度：

// agent.ts:113-131 —— 全部投递逻辑
send(message: UserMessage, target: InboxTarget, wakeup: boolean): void {
  // Waking input cannot join an aborted activity, so it starts the next turn.
  const wakingAfterAbort = wakeup && this.phase.kind !== 'idle' && this.phase.abort.signal.aborted
  const resolvedTarget = wakingAfterAbort ? 'next-turn' : target
  this.inbox.splice(resolvedTarget, Infinity, 0, [message])
  if (wakeup) this.wakeDriver()
}

followup(input) { this.send(input, 'next-turn', true) }   // 用户新一轮
steer(input)    { this.send(input, 'next-step', true) }   // 中途转向
inject(input)   { this.send(input, 'next-step', false) }  // 系统注入上下文

claim()：所有权的不可逆转移

循环在每个 turn 开始时"认领"消息。规则很短但每一条都有意图：

  • 拿走 全部 next-step 消息，加上最多一条 next-turn 消息。（为什么 next-turn 只拿一条？因为一条用户消息 = 一个 turn，这是 turn 的定义。）
  • 两个改动都是纯删除型 splice：discardRemoved=false、没有 outcome、不发 discarded 通知。
  • claim 是不可逆的所有权转移——即便随后 agent/pre-step 判决为 reject，消息也不会退回收件箱。

"拒绝不退回"看起来很反直觉，但它是正确的。如果 reject 会退回，一个持续 reject 的策略插件（比如"权限不足"）就会造成无限循环：认领 → 拒绝 → 退回 → 再认领。让所有权单向转移，把"这条消息怎么办"的责任明确交给拒绝方——它可以选择记日志、通知用户、或者用 inject() 换个形式重新投递。循环不替策略做兜底，这是全仓反复出现的态度。

两个容易被日志消费者踩到的边界（都已核对源码）：

  • 空 inbox 上的 claim 在日志里完全不可见。mutate() 在 actualDeleteCount === 0 && inserted.length === 0 时提前 return，不写任何 durable 事件（inbox.ts:178）。所以不存在"claim 了 0 条"这样一条 spliced 事件——想从日志重建"这一步认领了什么"的消费者，必须接受「没有事件」＝「空批次」这个约定。
  • cancel() 在 idle 下不是完全的 no-op。它分两半：abort 那一半在 idle 下确实什么都不做（if (this.phase.kind !== 'idle')），但清空 inbox 那一半照做——除非显式传 {keepInbox: true}（agent.ts:133-139，types.ts:39）。实际后果：resume 一个还有 pending inject() 的 session，然后 cancel 一下，那些注入会被永久删掉（两次带 outcome:'canceled' 的 durable splice）。

5.3 agent/pre-step：唯一的入场判决

这是整个 harness 扩展性密度最高的一个点。签名很小，但它是 12 个插件的共同挂载处：

监听器它做什么它为什么必须在这里而不是别处

一个必须知道的顺序陷阱：prompt 装配发生在 pre-step 判决之前。

所以 pre-step 监听器无法影响本 step 的系统提示词——它的 section 改动要下个 step 才生效。但压缩仍然有效，因为压缩改的是 session surface，而 deriveMessages() 是在 buildRequest 里晚一步才调用的。

这个非对称性是真实的、有意的、且容易踩坑。如果你写一个 pre-step 插件想改提示词，你会发现"改了但没生效"，而同一个位置改消息却立刻生效。记住这条分界：系统提示词已定，消息还没定。

5.4 turn 与 step 的括号纪律

循环里最"死板"的部分，也是最重要的部分：括号必须配对，即使出错也必须配对。turn/start … turn/end 的闭合写在 finally 里（agent.ts:225-307）。

turn/start —— 在认领输入和跑 pre-step 之前就开。为什么这么早？因为"一个被拒绝的 turn"也是一个真实发生过的 turn，它必须在日志里留痕。

claim → agent/inbox/claimed × N → pre-step 判决。若 reject / 输入为空 / 被取消 / 监听器抛异常：认领的那批消息保持已删除，关掉这个"零 step 的 turn"，停掉 driver。

⚠ 这里仓库自己的生成文档画错了：docs/agent-lifecycle.md:29-32 把 turn/start 画在 pre-step 之后，并写着 "claimed batch stays removed, no turn opens"。代码是反的——agent.ts:234 早于 :245，reject 照样写 turn/end.reason = {kind:'blocked'}。该文件是生成物，改它要改 scripts/gen-doc-graphs.ts。以代码为准。

step/start → 把 entered 批次作为各自独立的 user/message 事件追加（不是合并成一条）→ 装配 prompt 和工具 schema → 快照 derived messages。

agent/request（仅 config）→ 落实 adapter 默认值与上下文容量 → 记 request/header（路由变了再加 request/context）→ llm/stream（冻结的、绑定注册的）。

assistant/chunk × N → assistant/message —— 每一次成功的调用都记录 assistant/message，即使它只有 usage 没有内容（max-tokens 的情况）。

按 ctx.tools.executionMode 调度工具（见 §6）→ 按模型给出的顺序做 post-execute 和 tool/result。注意：执行可以并发，但结果处理必须按模型顺序——否则日志不可复现。

step/end → 判断是否继续：工具是否欠一次请求，或 next-step 收件箱是否非空。是 → 再 claim、再 pre-step、再进一个 step（同一 turn 内）。

否则 agent/turn-stopping → 再检查一次 next-step 收件箱（给"最后一刻插话"一个机会）→ turn/end → 启动下一条 waking 排队消息，或 emit agent/status(idle)。

"继续与否"看数据，不看返回码

循环判断要不要再来一个 step，问的是两个数据问题：「有工具调用还欠着一次请求吗？」「next-step 收件箱空了吗？」——而不是「上一步返回了什么枚举值」。

这个选择的价值在扩展时才显现：一个插件想让 agent 多跑一步，它不需要改循环、不需要新增一个 ContinueReason 枚举值、不需要在某个 switch 里加分支。它只要 inject() 一条消息进 next-step 收件箱。控制流被表达成了数据，于是控制流的扩展点变成了数据的扩展点。

5.5 取消与失败：两个正交的概念

CODE-CONFIRMED

aborted —— 取消

有人主动喊停。原因是一个闭合联合 AgentCancelCause：user（用户按了 Esc）/ parent（父 agent 撤销委派）/ hook（外部 hook 否决，带 reason 字符串）/ disposed。

持久化时还多一个 legacy —— 专门给那些"旧格式导入进来、原始记录没写原因"的情况。把"未知"显式建模成一个变体，而不是让 reason 变成可选字段。

CODE-CONFIRMED

disposed —— 拆卸

整个 agent 要被销毁。它会等待静默（quiescence）——不是"立刻杀死"，而是"停止接受新工作，等在跑的收尾"。

取消和拆卸的区别：取消后 agent 还活着，可以接新输入；拆卸后它不存在了。AgentHandle = { agent, dispose() } —— 销毁权是一个消费者能力，只给创建者，不放在 agent 自己身上。

TurnEndReasonMap 六个变体，覆盖了一个 turn 能怎么结束的全部情况：

reason含义值得注意的细节
completed正常跑完—
aborted取消请求打断了活跃 turn带 TurnEndCancelCause，四种（+legacy）
blockedpre-step 拒绝，没有进 step这个 turn 里没有 step/start、没有 user/message
errorturn 失败error 永远是结构化的 LlmFailure：要么是 LlmError 的原始事实，要么是 {message: errorChain(e), code:'UNKNOWN'} 压平的。不存在"裸 Error"进日志。
max-tokens至少有一个 step 撞到输出 token 上限即使有插件让 turn 继续跑下去了，这个标记也会保留
interrupted持久化后端在重载时关闭了一个崩溃遗留的 turn循环永远不会发这个。它是后端的专属标记，见 §4.4

重试：agent/request-error

请求失败也是一个 waterfall 扩展点，payload 携带：请求坐标 + 归一化后的 LlmFailure + 该注册项自己的 retryPolicy + signal。一个重试插件返回 {kind:'retry'} 而不调 next()（还记得 §2.1 吗——不调 next 就是接管决定）。

注意 retryPolicy 是随注册项走的，不是全局配置：不同 provider adapter 可以有不同的重试策略，而做重试的插件不需要知道它们的区别。这又是一次"策略与机制分离"。

重试留在同一个 turn、同一个 step 里——而三份仓库文档说的是相反的。

代码：step() 外层是 while(true)，返回 {kind:'retry'} 就 continue，重新走 buildRequest。测试把这一点钉死了（agent-loop/tests/request-error.spec.ts:78-93）：两次恢复的坐标都是 {turn:1, step:1}，整个 session 只有 1 条 turn/start。

但 .agents/notes/implemented/ 下至少三份笔记仍写着"关闭失败 turn 并开启一个重试 turn"，其中两份还提到一个叫 agent/settled 的终态事件——这个事件在 packages/ 下 0 命中，已经不存在了。最危险的一份是 architecture/2026-07-10-after-call-compaction-pressure-and-overflow-recovery.md:27，因为它是 compact-basic 的设计权威，照着它写代码的人会去监听一个不存在的事件。

这正好演示了 §11 那套 gate 的边界所在：26 个 doc-sync gate 覆盖 docs/，但 .agents/notes/implemented/ 是历史决策记录，不受同步检查约束。仓库自己也知道这一点——所以规约里写了"归档笔记是冻结的，永不作为现行权威"。教训是：笔记读设计意图，代码和测试读当前事实。

6 · 工具流水线：七道闸门与它们的所有权

ctx.tools 是全仓契约密度最高的一个包。它的核心主张是：把"执行一个工具"拆成七个阶段，每个阶段有明确的所有者、明确的能力上限、明确的失败语义。

6.1 取消分类学：一个"具体性偏序"

工具被取消时该报什么码？这个 harness 定义了一个明确的优先级——越具体的原因越优先，取消是最不具体的那一档：

拒绝 / 包装器失败 / 工具失败 / post 策略失败 / TOOL_TIMEOUT　＞　ABORTED　＞　ABORTED_BEFORE_DISPATCH
CODE-CONFIRMED

ABORTED_BEFORE_DISPATCH

body 还没被调用就取消了。没有副作用，模型可以放心重试。预先就 aborted 的调用会materialize 并冻结参数，然后跳过所有策略和分发阶段，只发布一个结果。

CODE-CONFIRMED

ABORTED

body 已经被调用了。它只能替换"成功"这一种结局——如果工具本身已经失败了，那个更具体的失败原因胜出。

为什么"只替换成功"这么重要？因为如果取消能覆盖失败，你就永远查不出"工具是真的坏了，还是只是被取消了"。保留最具体的失败原因 = 保留可诊断性。这一条和 §4.4 的 TOOL_NOT_STARTED vs TOOL_OUTCOME_UNKNOWN 是同一个思路的两次应用：把"我知道什么"和"我不知道什么"编码进类型，而不是丢失它。

timeoutMs 是一个陷阱。工具定义可以声明 timeoutMs，但这纯粹是声明式的——注册表自己不掐表。真正执行超时的是 dsh-timeout-policy，一个挂在 tools/execute 上的独立包。如果你的部署里没装它，所有 timeoutMs 都不生效，而且不会有任何警告。这是"机制与策略分离"付出的代价，仓库把它明确列进了 Known Limitations。

6.2 并发：fail-closed 的分类

// packages/core/tools/src/index.ts:1054-1063
executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  const tool = this.get(exec.name, exec.agent)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }   // 没声明 → 独占
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }                                // 抛异常 → 独占
  }
}

九行代码，但语义很讲究：只有严格等于 true 才并行。未知的、被隐藏的、没声明的、返回了非布尔值的、抛异常的——统统当作独占。而且分类是按调用做的（传入 exec.arguments），所以同一个工具可以"读文件时并行、写文件时独占"。

循环拿到分类后（tool-calls.ts，289 行）：exclusive → 屏障，独自跑完；parallel → 滚动池，上限 maxParallelToolCalls（默认 10，来自 constants.ts:6，可配置且校验为正整数）。启动时重新分类——因为在排队期间工具集可能变了。

别把两个并发上限搞混。原生路线用的是 ctx.agentLoop.config.maxParallelToolCalls（agent-loop/src/index.ts:133-137，由 tool-calls.ts:131 读取）；Code Mode 子调用用的是 ctx.tools 自己的 maxParallelSubCalls（tools/src/index.ts:632, 728-732, 744）。两个默认值都是 10，但它们是两个独立的配置项，分属两个包——调了一个不会影响另一个。

并发执行，顺序落地。工具可以并行跑，但 tools/post-execute 和 tool/result 严格按模型给出的调用顺序处理。这保证了日志可复现：同一批工具调用，无论实际完成顺序如何，日志永远长得一样。这是"并发是实现细节，不是可观察语义"的典型做法。

6.3 Code Mode：让模型写程序而不是发工具调用

这是 ctx.tools 最有野心的部分。mode: native | code | both 决定了工具怎样呈现给模型：

Code Mode 的契约细节为什么这样定
子调用携带父 token，记录 tool/code-dispatch-start + tool/code-dispatch，确定性 id <parent>:code:<n>可审计：一次 run_code 里发生的每次工具调用都在日志里，且 id 可预测——回放能对齐。

tools/code-dispatch-log waterfall 让 spill 策略裁剪耐久副本精妙：程序已经拿到了完整的值，模型根本看不到这个值，所以只有"写进日志的那份拷贝"需要被限制大小。三方的信息可见性各不相同，而流水线为此专门开了一个缝。

runtime 语言没有对应 SDK renderer → prompt 装配大声失败符合"Misconfiguration fails loud"规约：宁可启动就崩，不要让模型面对一个不完整的 SDK。

6.4 值 / 内容 / 展示：一次调用有三种"结果"

这是初读 ToolExecutionResult 时最容易困惑的地方，但分清后受益很大：

CODE-CONFIRMED

value：规范 JSON 值

工具 body 的真实返回，必须符合 output.schema。程序化消费者读这个（比如 Code Mode 里的 SDK 调用）。

CODE-CONFIRMED

content：模型可见内容块

由 output.render(args, value) 纯函数投影出来。模型读这个。可以被 post-execute 替换。

CODE-CONFIRMED

meta：工具私有展示载荷

核心对它完全不透明，但必须可 JSON 序列化（Session.append 用 isJsonValue 运行时校验）。UI 读这个，通过工具自己的 presentResult。

README 里一句容易被忽略但极其重要的话："Content replacement is not a confidentiality boundary: block or replace the value when programmatic consumers must not receive it."

翻译：如果你写一个脱敏插件，只改 content 把密钥打码——模型看不见了，但 Code Mode 里的程序仍然拿到完整的 value。真正要保密必须 block 或替换 value。这是一个安全性上的真实陷阱，仓库选择了把它写进契约而不是悄悄修复，因为"content 是展示、value 是数据"这个分层本身是对的，需要修的是使用者的理解。

9 · Scope 与 Subagent：多 agent 如何共存

当一个进程里同时活着 5 个 agent，"注册一个工具"到底注册给谁？dsh-scope 的答案是两级、扁平、最具体者胜。

9.1 两级扁平作用域

tools.restrict 是可见性，不是权限。README 里明确标注了 "scope security non-goal"：它是"活的可见性组合"，多个 mask 取交集，scope-local 工具在过滤之后合并。它不是一道授权边界——一个能拿到 plain ctx 的插件可以绕过它。真正的授权在 tools/pre-execute + ctx.tools.guard() 那一层，而且规约要求 "test denial through the executor"（要通过执行器测试拒绝，而不是测试 schema 里没有它）。

9.2 setup 窗口与 AgentHandle

创建一个 agent 时有一个精确的"组装窗口"：CreateAgentOptions.setup(agentCtx)。它发生在——scope 和 agent 对象已存在，但 agent 与 session 尚未发布、agent/session-start 尚未触发、第一个 prompt 尚未装配之前。

规矩只有一条但很关键：setup 只负责注册，绝不驱动 agent。它是"可信的、纯组装的同进程代码"。要驱动，等 create 返回之后。

创建的返回值是 AgentHandle = { agent, dispose() }。注意 dispose() 不在 agent 对象上——它是给创建者的一个能力。任何拿到 ctx.agents.get(id) 的插件都能操作这个 agent，但只有创建者能销毁它。这是把"所有权"编码进了 API 形状。

有序拆卸：prepare → enter → announce

session store 和 agent registry 都用同一套三段式生命周期原语：

prepare

构造未发布的对象。校验、冻结、转移所有权（持久化恢复走 seedSource:'persistence' 路径，避免二次序列化拷贝）。

enter

做权威的 ID 冲突检查、插入但不广播。返回的 detach 是绑定到具体条目对象的幂等操作——所以一个过期的 detach 句柄删不掉后来的同 ID 替代者。

announce

发出 agent/created，恰好一次。这是唯一的"创建边"。

为什么要拆三段？因为 enter 和 announce 之间需要一个"已存在但还没人知道"的窗口——在这个窗口里可以完成跨注册表的原子性协调。而"创建监听器同步请求的 detach 会被推迟到该次分发展开之后"这种细节，正是把生命周期拆开才有地方安放。

Initiator scope：异步链里"我是谁"

一个进程里多个 driver 并发跑，异步回调里怎么知道当前属于哪个 agent？答案是 AsyncLocalStorage：

ctx.agents.withInitiator(agent, operation)  // 在这个 Agent 的边界里跑
ctx.agents.currentInitiator()               // 读取，可能没有
ctx.agents.requireInitiator()               // 读取，没有就抛 'no initiating agent is active'
ctx.agents.withoutInitiator(operation)      // 显式隐藏，做无关的进程本地工作

但仓库对这个机制的态度非常警惕，值得学。README 原文："Ambient presence is neither liveness proof nor authorization; explicit Agent fields remain authoritative at service, worker, process, persistence, and wire boundaries."

翻译：环境里能读到一个 Agent，既不证明它还活着，也不构成授权。在服务、worker、进程、持久化、wire 这五类边界上，必须显式传 Agent / Session 参数。配套的包级规约是 "Initiator-owned private chains derive, then capture"——在编排入口取回 Agent，派生出 agent.session，让操作局部的 helper 闭包捕获它；不要为了少传一个参数就把叶子 helper 从 Session 拓宽成 Context。

这是对"隐式上下文"这种便利机制的正确使用姿势：用它省掉参数传递的样板，但绝不用它做决策。

9.4 自指：agent 修改自己的运行时

packages/cordis/ 提供三个工具：cordis_inspect / cordis_mount / cordis_unmount。它们让模型能够检视自己所在的 Cordis 运行时，并挂载新插件——而挂载进来的插件可以注册新的模型可见工具。

一个 agent 可以给自己长出新能力

这在架构上是"一切皆插件"的逻辑终点：如果所有能力都是运行时可挂载的插件，而 agent 又能调用工具，那么 agent 调用一个工具来挂载一个提供新工具的插件 就是一个自然的、无需特殊支持的操作。它不需要任何"元编程"机制——只需要把 Cordis 的 mount API 包装成一个普通工具。

仓库对此保持克制：这套工具是 opt-in 的，不在任何发布树里，只有 pnpm run demo:cordis 会演示它。但它的存在本身就是对整个架构的一次压力测试——能支持这个，说明插件边界是真的干净。

DOC-CLAIM

Agent Notes：1132 条

790 已实现 / 52 提案 / 22 已否决 / 268 已归档。非平凡改动必须在同一个 PR 里附一条 Note。已归档的 Note 是冻结的：永不编辑，也不能当作现行权威。——把"历史决策"和"当前契约"分开，避免旧文档误导。

12 · 设计思想：把这套架构压缩成七条

前面十一节是"它是什么"。这一节是"它为什么是这样"——如果你只带走一样东西，带走这一节。

12.1 七条贯穿全仓的设计原则

CODE-CONFIRMED

① 编排者拥有顺序，不拥有策略

agent-loop 只有 1581 行，因为它拒绝做决定。要不要进 step、要不要压缩、要不要审批、要不要重试、要不要超时——全部外包给 waterfall 监听器。循环只保证：括号配对、日志完整、顺序正确。

后果：换策略不动循环；读循环不用理解策略。

CODE-CONFIRMED

② 模型可见 ⟺ 已记录

一条双向的等价，不是单向的"尽量记日志"。任何进入模型请求的东西必须能从 session log 重建，ctx.invariants 在运行时断言这一点。

后果：可 resume、可 fork、可回放、可审计——全是同一条不变量的免费推论。

CODE-CONFIRMED

③ 只追加，从不删除

压缩不是删消息，是往 surface 里写一个带 sourceEventSeqs 的 replace。原始事件永远在日志里。人类 transcript 和模型视图从同一份日志的不同投影得来。

后果："模型现在看到什么"和"当时发生了什么"是两个可分别回答的问题。

DOC-CLAIM

④ 缝划在"怎么做"，不划在"是什么"

24 个能力缝全是实现可换（模型、shell、沙箱、存储、审批 UI）。而 session 结构、prompt 装配、工具注册表、agent 接口是 core——契约本身不可换。

后果：可换的东西真的能换；不可换的东西是所有人共同的地面。

CODE-CONFIRMED

⑤ 能力上限编码进类型，不靠文档约束

tools/execute 只能换 signal；tools/post-execute 只能换 content 或 value（永不同时）；finalizeContent 只能碰 content 且必须同步。这些不是"请不要"，是签名做不到。

后果：拦截器权力越靠后越小，形成一条单调收敛的信任链。

CODE-CONFIRMED

⑥ 不确定就选最严的那一档

executionMode() 只有恰好返回 true 才允许并发，未知/隐藏/抛异常一律 exclusive。取消分类学里 ABORTED 只覆盖成功、不覆盖任何失败。凭据永不内联，只存命名引用。

后果：错误的默认值不会造成损害，只会造成性能损失——这是正确的代价方向。

DOC-CLAIM

⑦ 规约必须可执行，否则它会腐烂

58 个 gate、26 个文档同步 gate、逐文件 100% 覆盖、无 key 快照回放、REAL-composition 测试、每包必须有 ./invariant 与 ## Known Limitations。这个仓库不相信"我们约定了"，只相信"CI 会红"。在一个由 agent 大量参与编码的代码库里，这是唯一能防止架构慢性侵蚀的机制——agent 会忠实遵守它读得到的规则，但只有 gate 能保证规则本身没被悄悄改写。

12.2 六条"血换来的"防御性规则

docs/defensive-patterns.md 的开头一句话定义了它的性质："each pattern below is a class of defect that actually shipped or nearly shipped here"——每一条都对应一次真实（或差点）上线的缺陷。这六条脱离 DSH 也完全适用：

规则它防的那类 bug
正交的结果要独立上报一个进程可以同时超时且退出码为 0（它捕获了信号）。把 timedOut/signal/exitCode 各报各的，绝不把一个标志嵌进另一个的分支——否则调用方会把一次被腰斩的运行读成干净的成功。
跨缝契约要两边都守LlmAdapter.stream() 的实现可以抛异常，也可以发 finish{kind:'error'}；但 LlmService.stream() 对外只以终止 finish chunk 暴露模型请求失败，中间件和消费者的缺陷仍然是抛出。在公开缝上归一化，消费者才不用猜"我捕获的这个异常来自 provider、包装器、chunk 日志，还是我自己的装配代码"。
异步状态 ≠ 同步状态followup() 没有"这条消息完成了"这回事。多条 followup、steering、injected work 可能共享同一段 running 区间。想要归因，必须显式定义自己的区间（从durable inbox 回执到下一次整体 idle），并把输出描述成"区间级的"而非"这条消息导致的"。反向的坑同样要处理：如果等待的状态转移永远不会发生，await 就永远挂着——"没什么可等"这个分支必须显式写。
dispose 要到达静止，不只是发出请求发了 kill/abort 就返回 = 留下孤儿。cleanup 必须是 async 且 kill → await done；并且先关监听器/通知注册表，再 kill，这样迟到的完成事件是安静的。
回调异常必须在边界处兜住一个用户提供的监听器抛异常，不能让它所在的 promise reject，也不能饿死它后面的监听器。分发循环包 try/catch 并记日志——一个坏订阅者永远不该打断核心生命周期。
不给不可信输出环境变量和可预测路径spawn 出去的命令拿到的是清洗过的 env（丢掉 *KEY*/*SECRET*/*TOKEN*/*PASSWORD*），所以 harness 的凭据不会漏进输出、env 或 spill 文件。临时/溢出文件用 0700 私有目录 + 随机名 + 独占 owner-only 打开（'wx', 0o600）——可预测的世界可读路径就是在邀请符号链接竞争和信息泄露。

12.3 四份事后复盘：这个仓库怎么面对自己的失败

docs/postmortem/ 里有四份，每一份都公开写在仓库里、双语、有 Status 字段。它们的价值不在于"出了什么事"，而在于每一份都以一条架构改动收尾：

0001 · ACP 的 default export 吞掉了 inject

单测全绿、产品是坏的。教训直接变成了测试政策里的一条硬规矩：没有 inject 的插件（bundle/composition 类）光靠 Loader smoke 会假绿，必须加 expect('default' in mod).toBe(false) 和 unwrapExports 往返断言，并且要先制造回归、看它变红、再还原。

0002 · !!js 表达式禁用了文件系统工具

就是 §2.2 那个陷阱的真实事故。修复不是"注意点"，是把它写进 primer 并加 verify-cordis-config gate。

0003 · Web agent 验证了一个"替代服务器"

最有意思的一份：agent 改了 GUI 源码，但不知道自己的会话跑在哪个 URL / 哪个进程上。它把一次裸 Vite 的 HTTP 200 当成成功（页面其实是白屏），最后在另一个端口验证了一个替身服务器。修复是把当前 URL 和 runtime mode 变成模型可见、shell 可查——一个纯粹的"给 agent 补上自我定位能力"的架构改动。

0004 · Landlock 的善意提示被当成了失败

老内核会打印一行无害的 partial-enforcement 提示，harness 把"这行前缀 + 任何非零退出码"当成 launcher 失败——于是 ripgrep 的"无匹配退出 1"变成了 SANDBOX_UNAVAILABLE。修复：分类必须先做精确的信息性排除，再要求状态门控的致命证据。

0003 值得单独想一想

它的根因不是代码 bug，是上下文缺失：模型请求里既没有说明这是 GUI、也没有说明源码 checkout、URL、进程、更新模式。"一次源码编辑、一次成功构建、一个 HTTP 200、一份注入的 boot manifest、用户已经打开的那个页面"——这五个事实被当成了可互换的。

这提示了一件关于 agent 系统设计的普遍事实：当 agent 的行动空间大到可以改变自己的运行环境时，"它知道自己在哪"就变成了一条安全属性，而不是一个便利功能。DSH 的回应是把它做成模型可见的上下文——和 dsh-workspace-context、dsh-time-context 是同一类插件。

13.4 动手：先跑那条不需要 API key 的

13.4.1 七章教程：零 key、零网络

七章教程跑的是 vendor/cordis/bin.js——七章教程跑的是 vendor/cordis/bin.js，它只加载 cordis + @cordisjs/plugin-loader，一个 @deepseek-ai/dsh-* 包都不碰，更不会发出任何 LLM 请求：

# 一次性准备
cd test-skyllwt
pnpm install                       # node ^22.19 || >=24
mkdir -p tmp/cordis-tutorial       # tmp/ 已被 gitignore，可以随便写
