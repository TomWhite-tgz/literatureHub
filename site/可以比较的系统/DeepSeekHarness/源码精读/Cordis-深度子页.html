0 · 这份子页怎么读

如果你读过主导读，会记得它的核心命题：dsh 的一切都是插件。而插件机制本身来自 vendored 的 Cordis。这份子页把 Cordis 从「用」推进到「造」——我们不满足于「ctx.on 会注册监听器」，而是看监听器到底存在哪、为什么能随 fiber 自动清理、服务消失为什么会让依赖它的插件退回 PENDING。

1 · 六个概念、一个闭环

先把六个抽象之间的拥有关系画出来——这是读源码前必须先建立的地图。记住一句话：fiber 拥有资源，context 解析资源，registry 创建 fiber，reflect 支撑解析，service 是资源的壳，events 是资源间通信。

一句话记住每个概念

Context 是你唯一会用的东西，它是个代理。Fiber 是「一个插件跑起来时」的那一撮状态，负责活着和死掉。Service 是「有名有姓的能力」，挂在 ctx.名字 上。Registry 决定「插件怎么进来」。Reflect 决定「服务怎么被找到」——它同时是代理的实现。Events 是插件之间解耦通信的广播。

读源码时最容易犯的错：把 ctx.plugin、ctx.on 当成「内置方法」。它们都不是。它们是被 mixin 转发上来的（reflect.ts:219-223），真正的本体是 ctx.registry.plugin、ctx.events.on。理解这一点，很多「这方法哪来的」的疑惑会立刻消失。

2 · Context：为什么是一个 Proxy

看 context.ts:42，类定义旁边直接写着注释「Root and child dependency containers」。但它不是一个普通的类实例——构造函数返回的不是 this，而是一个代理（context.ts:74）：

constructor() {
  this[symbols.isolate] = Object.create(null)      // 隔离映射：服务名→作用域 label
  this[symbols.intercept] = Object.create(null)     // 拦截映射：服务名→合并进 config
  const self = new Proxy<this>(this, ReflectService.handler)  // ← 关键：返回代理
  this.root = self
  this.baseUrl = undefined
  this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])  // root fiber
  this.reflect = new ReflectService(self)
  this.registry = new RegistryService(self)
  this.events = new EventsService(self)
  this.logger = new LoggerService(self)
  this.fiber._disposables.clear()
  return self                                              // ← 构造返回代理
}

2.1 为什么必须是代理，而不是普通对象

核心矛盾在于：服务是动态出现、动态消失的。插件 A 提供的 ctx.bash，在 A 加载之前不存在、在 A 卸载之后又消失。普通 JS 对象做不到两件事：

CODE-CONFIRMED

① 拦截「读取不存在的东西」

读一个对象不存在的属性只能得到 undefined。代理可以拦截 get，把它变成一次服务解析——甚至报「cannot get property without inject」（reflect.ts:144）。

CODE-CONFIRMED

② 拦截「写入」并转给对应服务

写 ctx.foo = v 会走 set 陷阱（reflect.ts:173），最后调 ctx.reflect.set——而 set 有个所有权检查：只有提供该服务的 fiber 能改它（reflect.ts:260）。

2.2 三种派生：不改父级，返回新孩子

Context 的「不可变扩展」是最反直觉也最关键的设计。三个方法全都不修改父级，而是用原型继承造一个 child（context.ts:99-145）：

方法签名造出的 child 额外拥有典型用途
extend(meta)context.ts:99meta 的 own 属性（含 symbol key），遮蔽父级同名属性给一个子上下文加元数据，如 fiber 引用（fiber.ts:233）
isolate(name, label)context.ts:121隔离映射里 name→新 label symbol；同 label 可 join 作用域同名服务在不同子树指向不同实现
intercept(name, config)context.ts:139拦截映射里 name→config，合并进下游插件的服务配置为某个服务注入配置而不改它本身

为什么用原型继承？因为 agent/subagent 需要「我自己的私有服务空间」，又需要能读到父级的服务。原型链天然就是「先找自己、找不到往上看」的语义。而 isolate 用 symbol 当 label 就更有意思了——两个调 isolate('bash', 同一个label) 的上下文会共享一个 bash 作用域，等于「我们在同一个 bash 世界里」。这正是 dsh 让多 agent 隔离服务、又允许 join 共用的基石。

一个关于 is() 的冷知识。Context.is(value)（context.ts:61-68）能跨 realm、跨多份 cordis 副本识别上下文，因为它用全局 Symbol.for('cordis.is') 做品牌，而不是 instanceof。这很重要——dsh 在 vm 沙箱里求值模型写的插件时，那份代码看到的 ctx 是另一 realm 的对象，但 Context.is 依然认得它。

3 · Fiber：生命周期引擎与「租约」模型

Fiber 是 Cordis 里最值得细读的类（fiber.ts:184，743 行，占整个核心的近三分之一）。它回答两个问题：一个插件从请求加载到彻底清理，中间经历了什么？以及——为什么「清理」能这么可靠？

3.1 状态机：六态一图

状态定义在 fiber.ts:147 是一个 const enum：PENDING, LOADING, ACTIVE, FAILED, DISPOSED, UNLOADING。注意枚举顺序不是时间序——真正的语义在 _getState()（fiber.ts:579-584）：

private _getState() {
  if (this.uid === null) return FiberState.DISPOSED
  if (this._error) return FiberState.FAILED
  if (this._runner.epoch !== INACTIVE) return FiberState.ACTIVE
  return FiberState.PENDING
}

这是理解 fiber 的一把钥匙：「当前状态」不是存出来的，是算出来的。它只看三件事——是否已 dispose（uid === null）、是否曾出错、以及 epoch（epoch 见 §7 级联机制）。「ACTIVE vs PENDING」的区别，本质就是「它声明的依赖是否全部在位」。一旦某个依赖消失，epoch 变 INACTIVE，状态就「被算出」退回 PENDING。

3.2 effect：一切注册的归宿，也是自动清理的保证

这是 Cordis 的命门。effect()（fiber.ts:423）把一段「会返回 disposer 的代码」注册到 fiber 上。看它的核心骨架：

effect(execute, label = 'anonymous') {
  this.assertActive()                      // 已 dispose 就抛 INACTIVE_EFFECT
  if (this.state === FiberState.UNLOADING) throw new CordisError('INACTIVE_EFFECT')

  const disposables = []                   // 本 effect 产生的 disposer 列表
  // … disporer: 逆序跑 disposables，且只跑一次（disposing 标志）……
  const runner = { execute, collect: (dispose) => disposables.push(dispose), … }
  const wrapper = defineProperty(() => { …清理逻辑… }, symbols.effect, meta)

  this._disposables.push(wrapper)          // ← 关键：effect 本体进 fiber 的全局表
  task = this._execute(runner)             // 立即执行 execute，收集 disposer
  // …
  return wrapper
}

拆开看，effect 做四件事：

  1. 守卫：已在卸载或已 dispose 时拒绝（抛 INACTIVE_EFFECT）。这是「不能在僵尸 fiber 上注册东西」的保证。
  2. 立即执行 execute，把它的返回值解释成 Disposable（一个函数）或 promise / 迭代器（_execute，fiber.ts:361）。
  3. 收集 disposer 进 disposables，并把整个 wrapper 压进 this._disposables（fiber 的全局清理表）。
  4. 返回一个单次失效的 disposer——调用它逆序清理，再调是空操作。

「Registrations are effects」为什么是硬性规约

因为只有把注册放进 effect()，卸载才有抓手。ctx.on 注册的监听器、ctx.provide 提供的服务、ctx.accessor 定义的属性——它们全部最终是某个 fiber 的 _disposables 里的一项。fiber 卸载时（_unload，fiber.ts:673）就一行：

await Promise.all(this._disposables.clear().map(dispose => … runDisposable(dispose)))

把 fiber 名下所有 disposer 清空跑掉，就是这个插件的一切被可预测地回收的全部秘密。没有手动 dispose 的义务，没有「忘了清理」的泄漏——只要遵守「注册走 effect」，卸载就必然干净。这就是 dsh 规约里 "Registry contributions prove disposal" 那条 gate 存在的原因。

3.2.1 一个必须说准的细节：逆序启动，但并发完成

「disposer 逆序执行」是一句流传很广但不够准确的话，而不准确的地方恰好会害人。把上面那行代码和 DisposableList 的实现放在一起看就清楚了：

// vendor/cordis/src/utils.ts:28-32
clear() {
  const values = [...this.map.values()]
  this.map.clear()
  return values.reverse()          // ← 逆序：确实是后注册的先返回
}

// vendor/cordis/src/fiber.ts:674-684
await Promise.all(this._disposables.clear().map(async (dispose) => {
  try {
    await composeError(async (info) => {
      await Promise.resolve()       // ← 每个 disposer 各自让出一个微任务
      info.error = new Error()
      await runDisposable(dispose)
    }, this._runner.getOuterStack)
  } catch (reason) {
    this.ctx.logger.error(reason)   // ← 异常只记日志，不外抛
  }
}))
你可能以为实际是出处
逆序执行逆序启动：clear() 返回 reverse 后的数组，.map() 按这个顺序逐个调用utils.ts:30
一个跑完再跑下一个全部并发：Promise.all 同时等待所有 disposer，没有任何东西让第 N 个等第 N-1 个完成。异步 disposer 之间会重叠fiber.ts:674
某个 disposer 抛异常会中断卸载不会：每个 disposer 各自包在 try/catch 里，异常只 ctx.logger.error()。既不中断兄弟 disposer，也不让卸载失败fiber.ts:675-683

实践后果：如果你的清理步骤之间有顺序依赖，把它们拆成两个 ctx.effect() 是错的。

因为两个 effect 的 disposer 会并发跑，「先关连接再落盘」这种约束不成立。正确做法是放进同一个 ctx.effect() 返回的那一个 disposer 里，由它自己 await 着串起来。

这条规约仓库自己写在了 docs/user/develop/framework/index.zh.md:63：「处置器按注册顺序的逆序开始调用，但多个异步处置器会并发执行，不保证逐个完成。存在顺序依赖的清理步骤必须放进同一个 ctx.effect() 返回的处置器中，由该处置器负责串行等待。」——那份中文文档在这一点上比大多数说法都准，详见 ↗ 文档地图子页 §1.1。

第三条（异常被降级成日志）也有它的道理：卸载必须永远成功，否则一个写坏的 disposer 就能把整个 fiber 卡在 UNLOADING，级联唤醒（§7）从此死锁。代价是清理失败只在日志里可见。

3.3 卸载与重载：_unload / _reload / _setEpoch

这三个私有方法构成了 fiber 的「心脏泵」。先看它们如何协同（fiber.ts:616-694）：

_refresh()（fiber.ts:616）——重新计算 epoch。遍历自己 inject 的每个依赖，拼出一个 epoch 字符串（如 :5:8，由各依赖提供者的 fiber.uid 组成）；只要有任一依赖缺失，epoch 直接 INACTIVE。

_setEpoch(epoch)（fiber.ts:630）——epoch 变了才动手。若 epoch 从 INACTIVE 变「有效」→ 进 _reload()（LOADING）；反之 → 进 _unload()（UNLOADING）。若 epoch 没变，什么都不做（这是幂等/去抖的关键）。

_reload()（fiber.ts:646）——快照 store，await Promise.resolve() 让出一轮微任务，然后若 epoch 仍是旧的（没被中途作废），就跑插件回调 this._execute(runner)。回调跑完才把状态设成 ACTIVE。

_unload()（fiber.ts:673）——disposables.clear() 拿到逆序数组，Promise.all 并发等待全部 disposer（见 §3.2.1，不是逐个串行）；清完 store 置 undefined，再检查：若 epoch 已被唤醒（有依赖回来了）就反过来 _reload()，否则定成 DISPOSED。

一个细节很值得体会：_reload 里那句 await Promise.resolve()（fiber.ts:650）不是随便写的。它让出当前同步执行栈，使得「上一个 disposer 排队、还没执行」的清理任务有机会先落地，避免插件在旧 epoch 还活着时就被新 epoch 的代码启动——这就是 _setEpoch 里 if (this.inertia) return（fiber.ts:634）防重入的那套协调：同一时刻只有一个 load/unload 在跑（inertia 这个 pending promise 就是「正在转换中」的旗标）。

4 · Service：依赖注入的载体

Service（service.ts）是「有名有姓的能力」的抽象基类。它的构造函数非常短，却一口气做了三件事（service.ts:42-59）：

constructor(protected ctx: Context, name: string) {
  name ??= this.constructor['provide'] as string   // 名字缺省用静态 provide 字段
  let self = this
  const tracker = { associate: name, property: 'ctx' }
  if (self[symbols.invoke]) {                      // 若声明了 invoke，包成可调用对象
    self = createCallable(name, joinPrototype(Object.getPrototypeOf(this), Function.prototype), tracker)
  }
  self.ctx = ctx
  self.name = name
  defineProperty(self, symbols.tracker, tracker)
  self.ctx.reflect.provide(name, self, this[symbols.check])   // ← 立即注册到 ctx
  return self
}
CODE-CONFIRMED

构造即注册

super(ctx, name) 的一瞬间就调 ctx.reflect.provide(name, self, check) 把自己注册成服务。所以一个 Service 子类「new 出来」就是「装进 ctx」，不需要额外登记。

CODE-CONFIRMED

可调用服务

若类声明了 [symbols.invoke]，createCallable 把它包成「既是对象又可调用」——这就是 ctx.logger()、ctx.get() 能当函数用的原因。服务可以既是命名空间又是函数。

CODE-CONFIRMED

自动卸载

reflect.provide 返回的 disposer 本身是 effect（见 §7），所以服务随提供它的 fiber 卸载而消失，不需要手动删。

INFERENCE

拦截配置

[symbols.resolveConfig]（service.ts:86）把 ctx.intercept 链上的配置合并起来。这解释了 dsh 里「对某个服务的配置拦截」是如何下发给下游插件的——合并顺序是「越靠近 root 越先」，可被 head 覆盖。

Service 与 Fiber 的关系一句话：Service 是「公共的、可注入的能力」；Fiber 是「私有的、一次运行的实例」。一个 Service 被 ctx.provide 后，会在 reflect.store 里留一条 Impl（reflect.ts:116-125），它记录着 name / value / fiber / check——尤其 fiber 字段，是「谁提供的、死了就要消失」的所有权锚点。

5 · Events：五种分发与 waterfall 的源码真相

主导读已经讲了四种模式的「怎么用」。这里补上源码层的关键——分发模式不是装饰，是硬编码在 dispatch() 之后各走各的路径。看 events.ts:165-243：

dispatch() · events.ts:165

把事件名、this、参数剥出来，按 internal/dispatch 广播（非 internal 事件），再过滤监听器（见 §5.2 的 filter），最后 bind(thisArg) 返回回调数组。所有模式共用这一步。

emit() · events.ts:194

同步把每个回调跑一遍，不 await、不取返回值。「通知」用。

parallel() · events.ts:183

Promise.allSettled 并发跑，全部 settle 后若有失败抛 AggregateError。「落地」用。

serial() · events.ts:204

按序 await，isBailed(result)（非 null/false/undefined，events.ts:13）即返回。「异步抢答」用。

bail() · events.ts:217

同步按序跑，第一个 bail 值即停。「同步短路」用。

waterfall() · events.ts:234

把 next() 串成链，每个监听器包住下一个；不调 next() 即否决。「中间件」用。

waterfall 的实现在 events.ts:234-243，是理解「中间件」最精确的一段：

waterfall(...args) {
  const cbs = this.dispatch('waterfall', args)   // 拿到所有监听器
  const inner = args.pop()                        // 最后一个参数是内层 next（内置行为）
  const next = () => {
    const cb = cbs.shift() ?? inner               // 弹出下一个监听器，没了就用内置行为
    return cb(...args)
  }
  args.push(next)                                 // 把 next 放回参数末尾
  return next()                                   // 从最外层开始
}

这段代码的精妙在于 args 的复用：next 闭包捕获了 args，而 args.push(next) 又把它放回参数末尾。于是每个监听器都收到「(…原始参数, next)」，而 next 一旦被调，就递归弹出下一个监听器。这就是「洋葱模型」的极致简版——比 Koa 的 middleware 还更接近本质。

5.1 监听器为什么能自动清理

ctx.on 的落点是 events.ts:288，它把监听器交给 register()（events.ts:254）：

register(label, hooks, callback, options) {
  const method = options.prepend ? 'unshift' : 'push'
  return this.ctx.fiber.effect(() => {            // ← 这就是"自动清理"的来源
    hooks[method]({ ctx: this.ctx, callback, ...options })
    return () => this.unregister(hooks, callback)  // disposer：反注册
  }, label)
}

看清楚：监听器注册本身就是一个 fiber.effect。它在 execute 里往钩子表 push 监听器，返回的 disposer 负责 unregister。所以——监听器随 fiber 卸载自动消失，不需要 ctx.on 的返回值被手动调用。这跟 §3.2 的「Registrations are effects」完全咬合：events 是 effect 机制最大的消费者之一。

5.2 上下文过滤：只给自己的 scope 发事件

在 dispatch()（events.ts:171-175）里有一个过滤：

const filter = thisArg?.[Context.filter]
return (this._hooks[name] || [])
  .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
  .map(hook => hook.callback.bind(thisArg))

每个监听器记录了它注册时的 ctx（Hook.ctx，events.ts:121）。分发时若 dispatch 的 thisArg 带了一个 Context.filter，就只放行匹配的监听器。ReflectService.notify（reflect.ts:314）正是用这个机制给事件做作用域过滤——所以一个 agent 自己的服务变化，不会误唤醒另一个 agent 的插件。这就是「scoped events」的物理实现。

一次注册的特殊事件。on('internal/listener', …)（events.ts:140）内部用 bail 分发（events.ts:296）——监听器注册本身也可以被拦截/接管。这是「框架核心服务也用同样的插件钩子互相扩展」的最典型例子：连「注册监听器」这个动作，本身也是一次可被拦截的事件。

6 · Registry：插件形态归一与 runtime 共享

Registry（registry.ts）是「插件怎么进来」的入口，也是「每插件只对应一个 runtime」的保证。核心是 plugin()（registry.ts:316-336）：

plugin(plugin, config, getOuterStack = buildOuterStack()) {
  const callback = this.resolve(plugin)          // 归一成回调
  if (!callback) throw new Error('invalid plugin…')
  this.ctx.fiber.assertActive()                  // 父 fiber 不能已死

  let runtime = this._internal.get(callback)     // 以回调为 key 查 runtime
  if (!runtime) {
    runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
    this._internal.set(callback, runtime)        // 第一次见 → 建 runtime
  }
  const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
  const wrapped = Object.create(fiber) as Fiber & PromiseLike
  wrapped.then = (onFulfilled, onRejected) => fiber.await().then(onFulfilled, onRejected)
  return wrapped                                  // 返回的 fiber 可 await
}

6.1 三种插件形态归一到一个回调

resolve()（registry.ts:222-228）负责归一：

  • 函数插件 → 它就是回调本身
  • 类插件 → 它本身是函数（构造器），直接当回调
  • 对象插件 { apply } → 取 plugin.apply

所以 Cordis 的「插件」只有一种本质：一个 (ctx, config) 回调。函数、类、对象只是三种皮。而 fiber 的 _execute（fiber.ts:247-260）在跑回调时用 isConstructor 判断——是类就 new 出来并跑它的 [init] 钩子，否则直接调用。

6.2 runtime：一个插件、多个 fiber、一次共享

关键在 _internal 这个 Map（registry.ts:197）以 callback 为 key。同一个插件回调被 ctx.plugin() 多次加载时：

  • 第一次 → 建一个 runtime（含 Config 校验器、fibers 列表）
  • 之后 → 复用同一个 runtime，只新建 fiber

这带来一个重要性质：一个插件可以同时有多个活跃 fiber（比如在多个隔离作用域里各加载一次）。它们共享 Config schema，但各自独立生命周期。而 `uid` 由 registry.counter 全局递增（registry.ts:207）——每个 fiber 有唯一 id，_refresh 正是用这些 uid 拼 epoch（§7）。

还有一个值得注意的细节：inject 依赖解析靠 Inject.resolve（registry.ts:71-88），它处理数组形式（['bash','llm']）和对象形式（{ bash: config }），还处理类继承来的 inject 合并（checkProto 标记）。这就是「声明依赖」从声明到真正的注入映射的最后一公里。

7 · 级联唤醒：Cordis 的灵魂机制

到这里所有零件都有了，可以拼出整台机器最漂亮的部分——依赖消失/出现时，如何级联唤醒所有相关插件。这一节把 §3 的 epoch、§4 的 store、§5 的 notify、§6 的 runtime 串成一条完整的时间线。

起点：某 fiber 调 ctx.provide('bash', impl)（reflect.ts:277）。它自身也是一个 effect：push 进 reflect.store，把 Impl 记到「提供者 fiber」名下，若当前已 ACTIVE 就立即 this.notify(['bash'])（reflect.ts:294-296）。

notify(['bash']) 扫描全局 runtime（reflect.ts:314-336）。遍历 registry.values() 的每个 runtime、每个 fiber，只挑 inject 里含 bash 的；对命中者调 fiber._checkImpl('bash')（fiber.ts:602）——重新核对这个依赖当前是否可用（含 check 谓词）。

命中者 _refresh()（fiber.ts:616）。把所有依赖的提供者 uid 重新拼成 epoch。若 epoch 变了，_setEpoch 驱动一次 _reload 或 _unload（§3.3）。这就是「服务出现 → 等待的插件启动」「服务消失 → 运行中的插件退回 PENDING」的瞬间。

provide 的 disposer 反向通知。卸载时 delete this.store[key]，再 this.notify([name]) 唤醒依赖者，await Promise.allSettled(fibers.map(f => f.await()))（reflect.ts:297-303）——等所有下游都停稳了，才删掉自己 fiber 里的 store[name]。顺序保证「先让依赖者撤，再撤自己」。

epoch：把「依赖集合」哈希成一个可比较的字符串

fiber 不保存「当前依赖在不在」的布尔值，而是保存一个 epoch 字符串（_runner.epoch）。_refresh（fiber.ts:616-628）把每个依赖提供者的 fiber.uid 串起来，如依赖 bash(uid 5)、llm(uid 8) → epoch :5:8。任何一个依赖变了 uid，epoch 就变。_setEpoch 只在 epoch === oldEpoch 时短路返回（fiber.ts:632）。

这个设计的妙处：它把「哪个依赖变了」压缩成「集合变没变」，从而做到幂等去抖——一百个依赖同时变化，只触发一次 reload。而 uid 的唯一性保证了「同一个服务换成另一个实现」也必然改变 epoch（新提供者 uid 不同），实现自然被替换。这是依赖注入框架里极干净的一个哈希方案。

把它和 §1 的拥有闭环连起来，整台机器就通了：

provide/on/register ──effect──► fiber._disposables ──unload──► 逆序清理 ──notify──► 依赖者的 _refresh ──► epoch 变 ──► _reload/_unload ──► 级联

8 · 接回 dsh：自引用工具集如何利用这些原理

读懂了内核，再回看 dsh 的 packages/cordis/tool-cordis/ 就豁然开朗了。它实现了三个面向模型的工具（cordis_inspect / cordis_mount / cordis_unmount），本质是把整个内核暴露给 agent 去自省和改造。几个设计直接对应本文的内核概念：

INFERENCE

「一切注册都自动清理」→ cordis_unmount 可靠

mountDynamic 把一个临时插件挂到一个 cordis-dynamic 组 fiber 下（index.ts 的 group）。卸载只要 fiber.dispose()，它名下的工具、监听器、服务、定时器全部逆序清光——这正是不必手写逐项 cleanup 的原因。

INFERENCE

「inject 缺失就 PENDING」→ 组合等待

工具文档强调「一个插件 provide，另一个 inject 消费，消费者保持 pending 直到提供者出现」——这正是 §7 的级联机制。模型不用自己轮询，fiber 会自动在依赖出现时唤醒。

INFERENCE

「Context.is 跨 realm」→ vm 沙箱可用

模型写的代码在 vm 沙箱（另一 realm）里求值，却要调用真运行时。§2.2 提过 Context.is 用全局 symbol 品牌，就是为此——尽管沙箱不是安全边界（工具文档明说），但身份识别跨 realm 是通的。

INFERENCE

「waterfall 必须 next」→ 工具文档警告

工具文档专门警告「waterfall 事件不调 next 就否决」，因为 agent 写的临时插件很可能挂 waterfall 监听器。这份警告就是 §5 的语义直接翻译成给模型的约束。

9 · 设计思想与学习路径

9.1 五个设计思想

设计思想源码证据它带来什么
一切皆可卸载的租约effect()（fiber.ts:423）、_disposables无需手动清理，卸载即干净；「Registrations are effects」由此而来
状态是算出来的，不是存的_getState()（fiber.ts:579）依赖集合（epoch）决定了 ACTIVE/PENDING，无需手动同步状态
依赖集合哈希成 epoch_refresh()（fiber.ts:616）多依赖变化幂等去抖，同一服务换实现必换 epoch
代理拦截一切ReflectService.handler（reflect.ts:135）服务动态出现/消失；读/写/查询全可拦截
scoped 一切isolate()（context.ts:121）、Context.filter同名服务多实现、事件按作用域过滤、多 agent 共存

9.2 建议的深入路线

这份子页是「读源码前的地图」。要真正吃透，建议按顺序做三件事，每件都回到真实源码再读一遍：

最后一句

Cordis 的全部复杂度，本质上只回答一个问题：「一个插件，如何知道自己该活、该等、还是该死？」答案是：把「我依赖的东西齐不齐」压成一个 epoch，epoch 变了就重新评估一次生命周期，而清理永远走 effect 这条唯一的路。理解了这一句话，vendor/cordis/src/ 里 2,676 行代码就不再是九份文件，而是一个想法。

当你回去读 dsh 那 165,000 行时，会发现它只是把这个内核的五个设计思想，在 24 条能力缝上重复了——每一处都是「可卸载的租约 + 可换的实现 + scoped 的上下文」。
