⑤ 能力、安全与前端：接口、实现、消费方

DSH 把“大功能”拆成 capability seam；安全决定与 OS enforcement 分层；前端驱动同一 Agent/Session，而不是各自复制 loop。

三包模式：接口 / 实现 / 模型工具

Bash 是最清楚的范本：

dsh-bash 定义服务契约→dsh-bash-local 实现进程→dsh-bash-sandbox 包装策略→dsh-tool-bash 暴露模型 schema

同一形状用于 subprocess、PTY、filesystem、LSP、skill、web、subagent 等。consumer 不把 UI schema 或 model wording 塞进底层 provider；实现也不偷加默认参数，默认值在拥有 deployment config 的 resolve 边界显式完成。这样远程/容器实现可替换 local 实现。

权限不是一个 allowShell 布尔值

层回答的问题默认 base 接线
Tool visibility/restriction模型能看到/调用哪些工具？ToolRegistry 全局 + scoped 视图
pre-execute/guard这次具体调用 allow、deny 还是 ask？policy listeners + monotonic guards
ApprovalService人或自动化通道是否对该操作一次性授权？ask；无通道 fail closed
Sandbox policy子进程能读写哪些文件？workspace-write
OS backend谁真正强制 argv 的文件效果？Linux bwrap/Landlock，macOS Seatbelt

ctx.sandbox.confine(argv, policy) 返回包装后的 argv；受限模式若无可用 backend 会抛 SANDBOX_UNAVAILABLE，不允许静默透传。容器、microVM、远程执行被视为完整 capability 的替代实现，不是假装成 local sandbox provider。审批 outcome 是闭合联合：只有 allowed-once 放行，rejected/cancelled/unavailable 都拒绝；never policy 在 responder waterfall 之前执行，prepend listener 也绕不过。

边界：DSH 的默认 sandbox 主要约束进程 argv/file effects，不等于网络、内核、凭据和所有 in-process JavaScript 都隔离。插件本身运行在宿主进程；信任第三方 bundle 仍是代码执行信任。
证据：docs/core-data-structures/sandbox.zh.md；docs/core-data-structures/approval.zh.md；packages/bundle/base/cordis.patch.yml:151-203。

Subagent：统一 provider seam 下的多种身份语义

providerchild 从哪里开始边界
spawn新 session，新 Agent进程内，可设 persona/tool filter/depth
fork父 session 的已完成 turn 前缀进程内，child 有独立后续历史
acp外部 ACP agent受管子进程与协议
codex/claude-code真实产品的一次完整委托外部 SDK/CLI provider
dsh-sdk独立 DSH runtimeJSON-RPC SDK child

服务先检查 provider 声明的 capabilities（output schema、depthLimit、toolFilter、persona），再接受启动；delegation depth 同时写入 session header，不能靠 prompt 自律。continuable child 具有持久 descriptor 和 activation，父 Agent 可 list/send/继续；one-shot provider 只返回一次结果。subagent/descriptor 是权威事实，UI/list query 从日志投影，不从临时 Map 猜。

证据：packages/subagent/subagent/src/{types,descriptor,continuation,depth}.ts；packages/subagent/subagent-{spawn,fork,acp,codex,claude-code,dsh-sdk}/src；docs/core-data-structures/subagent.zh.md。

Workflow 与普通 subagent 的区别

workflow 让模型提交一段可 top-level await 的 JavaScript 编排脚本，由 worker-thread engine 执行，通过受限桥接调用 subagent provider；它适合 fan-out/fan-in、多轮结构化流程。普通 subagent tool 是一次声明式启动。两者都不把并发编排塞进 Agent loop，终态和 fatal/nonfatal failure 由各自 seam 表达。

默认 composition 的几个现实取舍

  • 默认开启原生 DeepSeek adapter，pi-ai adapter 以零 route dormant mount，用户 settings 加 profiles 后动态注册。
  • 默认 JSONL persistence；session-query SQLite 默认内存且 first-search 才打开，不等于 durable session 用 SQLite。
  • 默认 telemetry 挂载并有 OTLP endpoint；任意非空 DSH_TELEMETRY_DISABLED（包括字符串 "false"）关闭。base 注释明确当前没有 record redaction，部署时要审查。
  • 默认 web search 走 DeepSeek server-side retrieval，fetch 关闭；这体现“存在 provider 包”与“安全默认挂载”不同。
  • plan/goal/todo/skills/subagent 都是插件与 session events，不是 AgentLoop 的硬编码 mode。
证据：packages/bundle/base/cordis.patch.yml:71-149,210-389。
架构判断：DSH 的能力面更像一个可组装平台：同一核心可以变成 Web 产品、自动化 server 或 SDK child。Pi 的 coding-agent 产品也有多前端和强扩展，但它倾向于让扩展直接操作高层 AgentSession/UI；DSH 更强调每项能力有服务所有者、持久事件和可释放 registration。
