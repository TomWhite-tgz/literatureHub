1 它是什么：三层数据接口

论文的核心论点：LLM agent 做科研的真正瓶颈是数据接入，不是推理 —— agent 缺现成检索工具，被迫解析 HTML/PDF 这类给人看的格式，既烧 token 又让证据定位变脆。

论文声称

覆盖范围

arXiv 全量语料，每日同步新发布；计划扩展 PubMed Central、bioRxiv、medRxiv、chemRxiv。

论文声称

渐进式访问

持久化多种物化视图（overview / section / evidence 三种粒度）+ provenance 字段（来源类型、抽取时间、更新时间），按需取粒度以控成本。

论文声称

合规声明

仅取 arXiv 描述性元数据（标题/作者/摘要/分类/时间戳），依据 arXiv API 条款 —— e-print 元数据为 CC0 1.0。

2 论文自评：注意它测的是什么

这 50 条查询"每条只对应唯一一篇目标论文"

论文原文：50 multi-constraint queries "each mapped to a single target paper (unique answer)"，指标是 Recall@1/10。也就是说，DeepXiv 自评的是"把那一篇找出来"的导航式精度任务。记住这一点 —— 第 5 节会看到，它在第三方评测里的"失败"其实主要是被换到了一个相反的任务口径上。

它自报的另一组数字是效率：相比"下载 PDF 再转 Markdown"的基线（8×A100，全流程 120m01s / 7.20s 每篇），DeepXiv 的端到端加速为 54.6×（Local）/ 39.6×（Remote）（warm 缓存）。deep research 侧的说法是"避免默认全文摄入、用结构化可按节寻址的接口替代脆弱的页面解析"，从而同时降工具成本与延迟。

4 两次引用的真实语境 —— 都不是背书

两篇引用它的论文都不是自引，而且来自很强的组，这点是正面信号。但读了全文之后，语境是负面或中性的。

5 关键反差：捞得到，但排不出来

把两边的数字并排看，会得出一个两篇论文都没说的结论。

评测任务口径金标规模DeepXiv 表现
论文自评（Fig. 2a）导航式：找出那一篇每条查询 1 篇唯一答案Recall@1/10 优于 Google Scholar / PaSa / ASTA，延迟显著更低
ScholarQuest（Table 2）穷尽式：把整个集合找全每条查询 5–200 篇R@25 0.054（全表最低）、R@All 0.288（≈ 稠密检索 0.290，是其他外部 API 的 2.5 倍）

它不是"检索能力差"，是被换到了相反的口径上 —— 但排序确实是真短板

合理推断 R@All 0.288 说明它的 agent 确实把大量金标论文捞进了候选池（召回能力接近专门的稠密检索）；R@25 0.054 说明它完全没把它们排到前面。这与它自评任务是"唯一答案 + Recall@1/10"高度一致：系统是为"命中那一篇"调的，不是为"枚举一个集合并排好序"调的。

但这不能全算脱罪。对一个主打"给 agent 用的数据接口"的系统，排序失效是致命的 —— agent 的上下文装不下 300 篇，它必须依赖接口把最相关的放在前面。而且 scope-controlled（排除约束）那一档它的 R@25 是 0.007，接近完全失效。

审计发现 ScholarQuest 对这个反差一个字都没分析；DeepXiv 自己的 Limitations 里也没有"排序 / 集合枚举"这一项。

6 依赖风险：先验数据新鲜度

维护有放缓迹象。repo 最后一次 push 是 2026-05-22，PyPI 最新版 0.3.1 同日，至今约 2.5 个月无更新。而论文核心卖点之一是"arXiv 全量 + 每日同步"以及"后续扩展 PubMed Central / bioRxiv"。一个宣称 daily sync 的托管服务停更两个多月 —— 如果要把它作为依赖，先自己验 data.rag.ac.cn 的数据新鲜度和接口可用性，别信论文里的 daily。

2026-08-04 补测修正：repo 停更属实，但数据管道仍在运转 —— live /api/status 最新收录 2608.02567（2026-08-03 发布），自带监控连续 75 天全 PASS（详见第 8 节）。同步是仅工作日：跨周末实测为 T+2，工作日约 T+1，论文的 "T+0" 不成立。风险应从"服务可能失修"修正为：代码维护停滞、数据服务存活，但论文的实现描述已开始与线上脱节（后端已从 Elasticsearch 换为 Qdrant）。

定位建议

不属于"包装"档

有真服务、真 SDK、真用户，不是空仓库论文。但也不是方法创新 —— 是基础设施 / 竞品交叉品。

定位建议

对 AutoSci 的意义

是「文献数据接入层」的一个可复用依赖或需要对标的对象，而不是算法层面的对手。引用它成本很低、收益也低（引用数说明学界还没把它当必引基线）。

注意

真正的竞品在别处

如果关心"给 agent 的标准化文献工具环境"这条线，参照点是 AstaBench（ICLR 2026, AI2）而不是 DeepXiv —— 不过 Asta 的语料不可自托管，两者各有硬约束。

证据等级说明。论文声称 来自本地 PDF 与 assets/2603.00084_fulltext.md；引用/下载/star 数为 2026-08-02 实测（Semantic Scholar Graph API、OpenAlex API、GitHub API、pypistats）；审计发现 为对两篇施引论文全文（含 SciAtlas 的 LaTeX 源码，因其 arXiv HTML 参考文献渲染为空）逐句核对后的认定；合理推断 为跨论文比较得出、两篇论文均未言明。

7 技术栈全景

全部是现货开源组件 + 自部署，没有一个自研或微调的模型，也没有一件必须购买的第三方服务。唯一的真金白银是离线管道的一次性 GPU 算力（解析 4,608 + 富化 6,400 ≈ 11,008 H100-时），以及无法事后回填的 X.com 日采热度。

离线管道：每篇论文过一次（论文 §A.1，多为论文自述）

实测印证 arXiv OAI-PMH 元数据同步 —— 仅工作日（周一~周五），周末停摆周一补齐

论文声称 HTML 优先 / PDF 兜底抓取正文

论文声称 MinerU 把 PDF 解析成 Markdown（8×8 H100 约 72h，4,608 H100-时）

论文声称 启发式标题切分 → canonical JSON，章节化 271万/295万 ≈ 92%

论文声称 Qwen3-4B-Instruct-2507 富化：章节 TL;DR + 最多 5 个关键词 + 机构，只读每篇前 2048 token（6,400 H100-时）

论文声称 tiktoken 标注每节 token_count；regex + LLM 验证 GitHub 链接（219,717 条）；挂载 S2 引用与 X.com 热度（448,825 篇，日采、不可回填）

对复刻者的含义：这个栈没有任何"买不到"的东西

MinerU、Qwen3-4B、BGE-m3、Qdrant、PostgreSQL、Redis、FastAPI、Caddy —— 全部开源、可自行部署。DeepXiv 的差异化只剩三样：① 一次性算力（在你的 3–5k 篇规模下是一块 4090 跑两三天的量）；② 271 万条已生成的章节 TL;DR；③ 448,825 篇 X.com 日采热度（无法回填）。模型和检索引擎本身，零壁垒。

三处架构描述需要修正（来自 OpenAPI，非论文）

审计发现

retrieve 是独立微服务

/arxiv/ 的 description 原文：retrieve 接入 jianlv retrieval 服务（/api/retrieval），支持 arxiv/biorxiv/medrxiv。这同时解释了分页排名漂移、间歇性 "Retrieval service is temporarily unavailable"、以及后端为何能脱离论文描述从 ES 迁到 qdrant。

审计发现

部署面不止"单台 64 核 + 热备"

线上至少扇出到 4 处：/api/retrieval（jianlv）、api2.rag.ac.cn（websearch，OpenAPI 明写"使用第三方 API"）、api.rag.ac.cn/trending（SDK 源码）。论文的"单节点"只是 API 节点本身。

审计发现

短信验证根本没实现

/api/send_verification_code 的 description 里挂着 "TODO: 集成真实的短信服务（Twilio / 阿里云短信）"。这解释了 SDK 为何在包里硬编码 shared secret 走 /api/register/sdk 静默注册。

排序短板的机制层注脚（呼应第 5 节）

返回的 score 不含语义置信度。retrieve 实测返回分数全是 1.0 / 0.5 / 0.3333 / 0.25 这类纯倒数 —— 是 RRF 融合的名次分，不是相关性分。调用方无法用它做阈值过滤，agent 拿到候选后必须自己重排。top_k ≤ 100 / offset ≤ 10000 是 pydantic schema 的硬边界（越界返 422，非静默截断）。

缓存与计价（文档明写 + 实测）：Redis /cache/stats 实测 keyspace_hits 641,458 / misses 3,402,486 ≈ 15.9% 命中率，与"按需抓取"架构一致。/webrag/search 每次扣 1000 额度、/websearch 扣 50、注册默认日限额 10000，均为 OpenAPI 原文。另有未文档化的 /webrag/search/stream（NDJSON 流，含 billing 事件）。

本节证据等级。"实测"= 2026-08-04 对 data.rag.ac.cn 的真实调用（/api/status、/cache/stats、三组 retrieve 探针：标题词对照 / 结论节原句 / 附录 A 原句）与 OpenAPI 快照（assets/openapi_snapshot_2026-08-02.json）的 description/schema 原文；模型栈、2048 token 富化窗口、11,008 H100 工时等仍为论文自述，API 面上不可验证。queue_pending（8-02: 2,990,129 → 8-04: 2,993,794，缓慢增长且与 served_papers 解耦）性质未定论。
